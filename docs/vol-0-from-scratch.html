Part 69 — Programming Fundamentals in JavaScript and TypeScript

Welcome to Volume 0. This volume exists for one reader: the person who wants to become a backend engineer and is starting close to zero. Maybe you have written a little JavaScript in a browser, maybe you have followed a tutorial once, maybe you have never written a line. Either way, this volume takes you from "I can run node file.js" to "I can build a small, correct NestJS API backed by PostgreSQL". The rest of the book (Parts 1 to 68) assumes you already have that foundation. This volume builds it.

This Part is about the language. Not toy JavaScript, and not clever tricks. We teach the parts of JavaScript and TypeScript that you will actually use every day in a backend: values and variables, the type system, functions, objects, arrays, control flow, modules, and error handling. We deliberately build toward the backend. The examples use orders, users, products and payments from the first page, because those are the nouns you will model for the rest of your career, not foo and bar.

A note before we start. JavaScript is the language that runs in the browser and, through Node.js, on the server. TypeScript is JavaScript with a type checker bolted on top. You write TypeScript, a compiler checks it and strips the types away, and what actually runs is plain JavaScript. Every backend in this book is written in TypeScript, so we teach both together: the JavaScript mechanism first, then the TypeScript type that describes it.

69.1 Values, variables and types

69.1.1 What a value is, and the primitive types

Concept

A value is a piece of data your program works with. The number 4200, the text "pending", the fact true — each is a value. JavaScript has a small set of built-in kinds of value called primitive types. You will use these constantly.

The primitives are: number (every number, whole or decimal, like 42 or 19.99), string (text, like "alice@example.com"), boolean (true or false), null (a deliberate "no value"), undefined (a value that was never set), bigint (for integers too large for number), and symbol (rare, a unique marker). For a backend developer, the first five matter every day; bigint and symbol you can learn later.

Why does it exist?

A program is useless if it cannot hold data. An order has a total, a status, a flag for whether it is paid. Those are a number, a string and a boolean. The type system exists so the language — and later, TypeScript — knows what kind of thing it is holding, which decides what you are allowed to do with it. You can add two numbers. Adding two booleans is almost always a bug.

Mental model

Imagine a warehouse with labelled bins. Each bin holds one thing. Some bins hold weights (numbers), some hold written notes (strings), some hold a yes/no switch (boolean). The label on the bin tells the warehouse worker what kind of thing is inside without opening it. A type is that label. A value is the thing in the bin. A variable is the bin itself with its name painted on the front.

How it works

JavaScript figures out the type of a value automatically from how you write it. 42 is a number. "42" with quotes is a string. true is a boolean. There is no step where you declare "this is a number" in plain JavaScript — the quotes, or their absence, decide.

// Plain JavaScript. Node figures out each type from the literal.
const orderTotalCents = 4299;        // number
const currency = 'USD';              // string
const isPaid = false;                // boolean
const cancelledAt = null;            // null: we deliberately have no cancel time
let discountCode;                    // undefined: declared but not yet assigned

console.log(typeof orderTotalCents); // "number"
console.log(typeof currency);        // "string"
console.log(typeof isPaid);          // "boolean"
console.log(typeof cancelledAt);     // "object"  <-- a famous JavaScript quirk
console.log(typeof discountCode);    // "undefined"

The typeof null returning "object" is a 25-year-old bug in the language that can never be fixed without breaking the web. Memorize it as a quirk and move on.

Practical example

Here is a tiny piece of order logic written with primitives only. It decides whether an order qualifies for free shipping.

const orderTotalCents = 4299;        // $42.99
const freeShippingThresholdCents = 5000; // $50.00
const isPrimeMember = true;

const qualifiesForFreeShipping =
  orderTotalCents >= freeShippingThresholdCents || isPrimeMember;

console.log(qualifiesForFreeShipping); // true, because the member flag is set

Notice we store money in cents as an integer, not 42.99 as a decimal. This is the first real backend habit: floating-point numbers like 0.1 + 0.2 do not equal 0.3 exactly in any language that uses the IEEE 754 standard, and JavaScript does. Storing money as integer cents avoids rounding errors that turn into off-by-a-penny bugs and angry customers.

console.log(0.1 + 0.2);              // 0.30000000000000004, not 0.3
console.log(0.1 + 0.2 === 0.3);      // false

Production scenario

A real payment service receives an order total, a tax amount and a shipping fee, all in cents, and sums them. Because every value is an integer number of cents, the sum is exact. If the same service had stored 42.99 and 3.50 as floating-point dollars, a few million additions per day would accumulate fractional-cent errors, and the daily reconciliation job that compares your totals against the payment provider's totals would fail by a few cents — which, to a finance team, is an all-hands incident, because a payment system that cannot add up is a payment system nobody trusts.

Edge cases & failure modes

  • NaN ("not a number") is itself of type number. It appears when a calculation makes no sense, like Number("abc"). Worse, NaN === NaN is false; use Number.isNaN(x) to test for it.
  • undefined means "never set"; null means "set to nothing on purpose". Mixing them up causes real bugs. A database column that is NULL maps to null; a function argument you forgot to pass is undefined.
  • Numbers lose precision above Number.MAX_SAFE_INTEGER (about 9 quadrillion). Database IDs that large must be handled as bigint or strings, which is why some APIs return IDs as strings.

How a Senior Backend Engineer thinks about this

A senior picks the representation that makes wrong states impossible. Money is integer cents. A status is a small fixed set of strings, never a free-form string. A timestamp is stored as a proper date type, never "March 3rd" as text. The type you choose on day one decides which bugs are possible for the life of the system, so you choose it on purpose, not by accident.

Common mistakes

  • Storing money as floating-point dollars. Use integer cents.
  • Using == instead of === (covered in 69.1.3); == does surprising type coercion.
  • Treating undefined and null as interchangeable, then crashing on cancelledAt.getTime() when cancelledAt is null.

Interview questions

  1. Why is 0.1 + 0.2 !== 0.3 in JavaScript? Because numbers are IEEE 754 doubles and 0.1 cannot be represented exactly in binary, so the sum carries a tiny error. Follow-up: how do you store money? Integer cents, or a dedicated decimal type in the database.
  2. What is the difference between null and undefined? undefined is the absence of assignment; null is an intentional empty value. Why it matters: database NULLs map to null, and conflating the two causes crashes.
  3. What does typeof NaN return, and how do you test for NaN? "number"; test with Number.isNaN. Why it matters: a stray NaN from bad input silently poisons every calculation downstream.

Practical exercise

Write a function-free script (just variables and console.log) that computes the grand total of an order: subtotal 3499 cents, tax 280 cents, shipping 599 cents, minus a discount of 500 cents. Print the grand total in cents and also as a dollar string like $38.78. Acceptance criteria: the dollar string must always show exactly two decimal places, even for a total like 4000 cents ($40.00).

69.1.2 Variables: let, const and the ghost of var

Concept

A variable is a named bin that holds a value. In modern JavaScript you declare variables with const or let. const means the bin's contents will not be reassigned. let means they might be. There is an older keyword, var, which you should never use in new code; we explain why so you recognize it in old code.

Why does it exist?

You need names so you can refer to a value more than once and so your code reads like a description of a problem rather than a soup of literals. const freeShippingThresholdCents = 5000 tells the next reader (often you, in six months) what 5000 means. A magic number 5000 buried in a condition tells them nothing.

Mental model

const is a bin welded shut around one value — you can look inside, but you cannot swap the value for a different one. let is a bin with a lid you can open to put something new in. var is a bin that, bizarrely, teleports itself to the top of the room the moment the room is entered, which is why it causes confusing bugs.

How it works

const maxRetries = 3;      // cannot be reassigned
let attempt = 0;           // will be reassigned in a loop
attempt = attempt + 1;     // fine

// maxRetries = 4;         // TypeError: Assignment to constant variable.

A crucial subtlety: const stops you from reassigning the variable, not from changing the contents of an object it points to. An object held by const can still have its properties changed.

const order = { id: 'ord_1', status: 'pending' };
order.status = 'paid';     // ALLOWED: we changed a property, not the binding
// order = { id: 'ord_2' }; // NOT ALLOWED: reassigning the variable itself

This confuses every beginner once. const protects the arrow from the bin to the object, not the object.

var has two traps. It is function-scoped, not block-scoped, so a var declared inside an if block leaks out of the block. And it is hoisted: the declaration is moved to the top of the function, so you can reference a var before the line that declares it and get undefined instead of an error. Both behaviors cause bugs that let and const simply do not have.

// Why var is dangerous:
function demo() {
  if (true) {
    var leaked = 'I escape the block';
  }
  console.log(leaked); // works with var; would be a ReferenceError with let
}

TypeScript angle

In TypeScript, const and let behave the same but the type checker infers tighter types for const. A const status = 'paid' has the literal type 'paid', while let status = 'paid' has the wider type string, because let might be reassigned. This matters when you build the small fixed sets of values we meet in 69.1.4.

Practical example

// A retry loop for calling a flaky payment provider.
const maxAttempts = 3;
let lastError: unknown = null;

for (let attempt = 1; attempt <= maxAttempts; attempt++) {
  try {
    // callProvider() is defined later in the book; imagine it here.
    // const result = await callProvider(order);
    // return result;
    break;
  } catch (err) {
    lastError = err;
    // wait and retry (covered in Part 70)
  }
}

maxAttempts is const because the policy does not change mid-loop. attempt and lastError are let because they change on every pass.

How a Senior Backend Engineer thinks about this

Default to const. Reach for let only when a value genuinely must change, which is less often than beginners expect — most loops that mutate a let accumulator can be written more clearly with array methods (69.4). A codebase full of const is a codebase where the reader knows, at a glance, which things move and which do not. That is a small, free form of documentation, and seniors value it.

Common mistakes

  • Using var in new code. It has no advantage and several traps.
  • Thinking const makes an object immutable. It does not; it only stops reassignment of the variable.
  • Declaring let for values that never change, which forces the reader to wonder whether they do.

Interview questions

  1. What is the difference between let, const and var? let and const are block-scoped and not hoisted in a usable way; const cannot be reassigned. var is function-scoped and hoisted, which causes leaks and confusing bugs.
  2. Can you mutate an object declared with const? Yes — const protects the binding, not the object's contents. Follow-up: how do you make the contents read-only? Object.freeze, or TypeScript's readonly and as const.

Practical exercise

Take a buggy snippet that uses var inside a for loop to register three callbacks and prints 3, 3, 3 instead of 0, 1, 2. Rewrite it with let so it prints 0, 1, 2. Acceptance criteria: explain in one sentence why let fixes it (a fresh binding per iteration).

69.1.3 Equality, truthiness and coercion

Concept

JavaScript has two equality operators. === (strict equality) compares value and type with no conversion. == (loose equality) converts the operands to a common type first, with rules so surprising that professionals simply never use it. "Truthiness" is the set of rules for which values count as true in an if.

Why does it exist?

Early JavaScript tried to be forgiving, so "5" == 5 is true. That forgiveness causes bugs: 0 == "", null == undefined and [] == false are all true, none of which you want. === exists to give you the predictable behavior you actually need.

How it works

console.log(5 === 5);       // true
console.log('5' === 5);     // false: different types, no conversion
console.log('5' == 5);      // true: == converts the string to a number
console.log(null == undefined); // true (a rare useful case)
console.log(null === undefined); // false

Truthy and falsy: in an if, these eight values are falsy — false, 0, -0, 0n, "" (empty string), null, undefined, and NaN. Everything else is truthy, including "0", "false", [] (empty array) and {} (empty object). That last pair trips up everyone: an empty array is truthy.

if ([]) console.log('empty array is truthy'); // this prints
if ('0') console.log("the string '0' is truthy"); // this prints

Practical example

A common bug: checking whether a quantity was supplied.

function describeQuantity(quantity) {
  // Bug: if quantity is 0, this treats it as "not supplied".
  if (!quantity) return 'no quantity';
  return `quantity is ${quantity}`;
}
console.log(describeQuantity(0)); // "no quantity" -- WRONG, 0 is a real quantity

Because 0 is falsy, !quantity is true for a legitimate zero. The fix is to test for the thing you actually mean:

function describeQuantity(quantity) {
  if (quantity === undefined || quantity === null) return 'no quantity';
  return `quantity is ${quantity}`;
}

TypeScript helps here: quantity ?? 'no quantity' (the nullish coalescing operator ??) falls back only for null or undefined, never for 0 or "". This is one of the most useful operators in backend code.

const shippingNote = order.note ?? 'no note';   // keeps '' if note is ''
const retries = config.retries ?? 3;            // keeps 0 if retries is 0

Edge cases & failure modes

  • !value to check "is it missing" treats 0, "" and false as missing. Use === undefined, === null, or ??.
  • NaN === NaN is false, so === cannot detect NaN.
  • Comparing objects with === compares identity, not contents: {a:1} === {a:1} is false because they are two different objects.

How a Senior Backend Engineer thinks about this

A senior reads if (!x) as a smell and asks "what exactly is being tested — null, undefined, zero, or empty?" Vague truthiness checks are a top source of production bugs where a legitimate zero or empty string is dropped. Be explicit about the condition you mean, and prefer ?? over || whenever 0, "" or false are valid values.

Common mistakes

  • Using == and getting bitten by coercion.
  • Using || for defaults when 0 or "" are valid (count || 10 turns a real 0 into 10); use ??.
  • Comparing arrays or objects with === and expecting content comparison.

Interview questions

  1. What is the difference between == and ===? === compares without coercion; == coerces types first, with surprising rules. Always use ===.
  2. Which values are falsy in JavaScript? false, 0, -0, 0n, "", null, undefined, NaN. Follow-up: is [] truthy? Yes.
  3. When would you use ?? instead of ||? When 0, "" or false are legitimate values and only null/undefined should trigger the fallback.

Practical exercise

Write a function getPageSize(requested) that returns requested if it is a number between 1 and 100, and 20 otherwise. It must accept 0? No — 0 is invalid here, so it falls back. But it must not accidentally reject a valid 1. Acceptance criteria: getPageSize(0) returns 20, getPageSize(1) returns 1, getPageSize(500) returns 20, getPageSize(undefined) returns 20.

69.2 TypeScript types: the second half of the language

69.2.1 Why types, and basic type annotations

Concept

TypeScript lets you write down what type a variable, parameter or return value is supposed to be, and then a compiler checks that you never violate it. The types are erased before the code runs — Node never sees them — so types cost nothing at runtime. Their entire value is catching mistakes before the code ever runs.

Why does it exist?

In plain JavaScript, a typo like order.totl (missing an a) is undefined at runtime and crashes three functions later with a useless stack trace. A function that expects a number but receives a string fails deep inside some library. TypeScript catches both at the moment you write them, in your editor, with a red underline. On a backend of any size, this turns a whole category of 2 a.m. incidents into a squiggle you fix in two seconds.

Mental model

Think of TypeScript as a spell-checker for data shapes. A spell-checker does not change what you write; it underlines words that cannot be right. TypeScript underlines data flows that cannot be right — passing a string where a number is required, reading a property that does not exist, forgetting that a value might be null.

How it works

You add a type after a colon:

const orderTotalCents: number = 4299;
const currency: string = 'USD';
const isPaid: boolean = false;

function applyDiscount(totalCents: number, percent: number): number {
  return Math.round(totalCents * (1 - percent / 100));
}

applyDiscount(4299, 10);     // fine
// applyDiscount('4299', 10); // Error: string is not assignable to number

Most of the time you do not need to write the type, because TypeScript infers it. const currency = 'USD' is already known to be a string. The rule professionals follow: let TypeScript infer local variables, but always annotate function parameters and return types, because those are the contracts other code depends on.

The any escape hatch and why it is dangerous

any turns the type checker off for a value. It is the single most misused feature in TypeScript. The moment a value is any, every mistake involving it becomes invisible again.

let data: any = JSON.parse('{"total": 4299}');
data.total.toUpperCase(); // no error at compile time, crashes at runtime

Prefer unknown when you genuinely do not know the type yet. unknown forces you to check the type before using it, which is exactly what you want for data coming from the outside world (a request body, a JSON file, a third-party API).

let data: unknown = JSON.parse('{"total": 4299}');
// data.total;          // Error: data is unknown, you must narrow first
if (typeof data === 'object' && data !== null && 'total' in data) {
  // now TypeScript lets you proceed, after you have proven the shape
}

Practical example

A function that parses a price from a request. With unknown and narrowing, bad input is caught at the boundary instead of corrupting the database.

function parsePriceCents(input: unknown): number {
  if (typeof input !== 'number' || !Number.isInteger(input) || input < 0) {
    throw new Error('price must be a non-negative integer number of cents');
  }
  return input;
}

How a Senior Backend Engineer thinks about this

A senior treats any as technical debt and unknown as the honest tool for untrusted data. They turn on strict mode in tsconfig.json on day one, because without it TypeScript allows null to sneak into everything and most of the value is lost. The slogan is "parse, don't trust": every piece of data entering the system from outside is unknown until a validator has proven its shape, after which it is a precise type for the rest of its life.

Common mistakes

  • Sprinkling any to make red squiggles disappear; this just defers the crash to runtime.
  • Not enabling strict mode, which leaves null and undefined holes everywhere.
  • Over-annotating obvious local variables, which adds noise without value.

Interview questions

  1. What is the difference between any and unknown? any disables checking; unknown requires you to narrow the type before use. Use unknown for external data.
  2. Do TypeScript types exist at runtime? No — they are erased during compilation. You cannot check x instanceof SomeInterface; interfaces do not exist at runtime.
  3. Why enable strict mode? It turns on strictNullChecks and other flags that catch the largest class of real bugs (null/undefined access).

Practical exercise

Write a function coerceStatus(input: unknown): 'pending' | 'paid' | 'cancelled' that accepts an unknown value, checks it is one of the three allowed strings, and throws otherwise. Acceptance criteria: the return type is the exact union of three strings, and the function throws a clear error for any other input, including 'PAID' in the wrong case.

69.4 Functions

69.4.1 Declaring and calling functions

Concept

A function is a named, reusable block of code that takes inputs (called parameters), does something, and usually gives back an output (the return value). Functions are how you break a big problem into small, nameable pieces. Almost everything you write in a backend lives inside a function.

Why does it exist?

Without functions, you would copy the same logic everywhere it is needed, and fixing a bug would mean fixing it in twenty places. A function is a single place where one idea lives. "Calculate the order total" should exist once; every part of the system that needs an order total calls that one function. When the tax rules change, you change one function.

Mental model

Imagine a vending machine. You put in coins and a code (the inputs), the machine does its internal work, and a snack drops out (the return value). You do not need to know how the machine is wired inside; you only need to know what it takes and what it gives back. A well-named function is a vending machine with a clear label.

How it works

There are two main ways to write a function. A function declaration uses the function keyword. An arrow function uses => and is stored in a variable. In modern backend code you will see both; arrow functions are more common for small helpers and callbacks.

// Function declaration
function orderTotalCents(subtotal: number, tax: number, shipping: number): number {
  return subtotal + tax + shipping;
}

// Arrow function stored in a const
const orderTotalCents2 = (subtotal: number, tax: number, shipping: number): number => {
  return subtotal + tax + shipping;
};

// Calling them is identical
const total = orderTotalCents(3499, 280, 599); // 4378

The parts of a function: the name (orderTotalCents), the parameters in parentheses with their types, the return type after the colon, and the body in braces. The return statement sends a value back to whoever called the function. A function with no return gives back undefined.

Parameters: default, optional and rest

// Default parameter: used when the caller omits the argument.
function paginate(page: number, pageSize: number = 20): { skip: number; take: number } {
  return { skip: (page - 1) * pageSize, take: pageSize };
}
paginate(3);        // pageSize defaults to 20 -> { skip: 40, take: 20 }
paginate(3, 50);    // { skip: 100, take: 50 }

// Optional parameter: may be undefined. Marked with ?.
function greet(name: string, title?: string): string {
  return title ? `${title} ${name}` : name;
}

// Rest parameter: collects any number of trailing arguments into an array.
function sumCents(...amounts: number[]): number {
  return amounts.reduce((acc, n) => acc + n, 0);
}
sumCents(100, 200, 50); // 350

Practical example

A function that decides shipping cost. Notice it takes typed inputs and returns a typed output, and that it has one job.

function shippingCostCents(
  subtotalCents: number,
  isPrimeMember: boolean,
  country: string,
): number {
  if (isPrimeMember) return 0;
  if (country !== 'US') return 2500;          // flat international rate
  if (subtotalCents >= 5000) return 0;        // free over $50 domestic
  return 599;                                  // standard domestic
}

NestJS example

This is a sneak peek at Part 74. In NestJS, the methods on a service are just functions with a decorator on the class. The function below is pure business logic; the framework calls it.

import { Injectable } from '@nestjs/common';

@Injectable()
export class ShippingService {
  // A method is a function that belongs to a class.
  cost(subtotalCents: number, isPrimeMember: boolean, country: string): number {
    if (isPrimeMember) return 0;
    if (country !== 'US') return 2500;
    return subtotalCents >= 5000 ? 0 : 599;
  }
}

The business rules did not change at all. They moved into a class so NestJS can share one instance of ShippingService across the whole application. We explain that machinery in Part 74 and, in depth, in Part 6 (dependency injection).

Edge cases & failure modes

  • A function that returns undefined implicitly (no return) when the caller expected a value is a classic bug. TypeScript's return-type annotation catches it: declaring : number forces every path to return a number.
  • Passing arguments in the wrong order (shippingCostCents(country, isPrime, subtotal)) compiles only if the types happen to line up. This is why a single argument object is often safer than many positional parameters (see 69.4.3).
  • A function that both returns a value and changes something outside itself (a "side effect") is harder to test and reason about. Prefer functions that only transform their inputs where you can.

How a Senior Backend Engineer thinks about this

A senior aims for functions that are small, named for what they produce, and free of hidden side effects where possible. The test they apply: "Can I describe this function in one sentence without the word 'and'?" If the sentence needs an "and", the function is doing two jobs and should be split. They also prefer pure functions — same input always gives same output, no side effects — for business rules, because pure functions are trivial to unit-test (Part 24) without a database or network.

Common mistakes

  • Giant functions that do ten things; impossible to name, test or reuse.
  • Forgetting a return, so the function silently yields undefined.
  • Too many positional parameters, so callers pass them in the wrong order.
  • Mutating a parameter that is an object or array, surprising the caller (covered in 69.5).

Interview questions

  1. What is a pure function and why is it desirable? A function whose output depends only on its inputs and which has no side effects. It is easy to test and reason about, and safe to call repeatedly.
  2. What is the difference between a function declaration and an arrow function? Beyond syntax, arrow functions do not have their own this and are not hoisted. For most backend helpers the difference rarely matters; this matters inside classes.
  3. When would you pass an options object instead of positional parameters? When there are more than two or three parameters, or several are optional, to avoid order mistakes and make call sites self-documenting.

Practical exercise

Write a pure function orderSummary that takes subtotalCents, taxCents, shippingCents and discountCents and returns an object { subtotalCents, taxCents, shippingCents, discountCents, grandTotalCents }. Acceptance criteria: the grand total never goes below zero (clamp it), and the function has no side effects.

69.4.2 Scope, closures and the call stack

Concept

Scope is the set of variables a piece of code can see. A closure is a function that remembers the variables from where it was created, even after that place has finished running. The call stack is the list of functions currently in progress. These three ideas explain a lot of otherwise-mysterious behavior.

Why does it exist?

Scope exists so that two functions can both use a variable named i without colliding — each has its own. Closures exist so a function can carry some private state with it, which is how you build things like a counter, a rate limiter, or a configured client. Understanding the call stack is how you read a stack trace, which is the single most useful debugging skill (Part 36).

Mental model

Imagine nested rooms. Code in an inner room can see out through the open doors into the rooms that contain it, but code in an outer room cannot see into the inner rooms. A closure is like taking a photograph of what the outer rooms held at the moment you walked into the inner room — even after those rooms are torn down, the function still has the photo.

How it works

function makeCounter(): () => number {
  let count = 0;                 // this lives in makeCounter's scope
  return () => {
    count = count + 1;           // the inner function "closes over" count
    return count;
  };
}

const next = makeCounter();
console.log(next()); // 1
console.log(next()); // 2  -- count survived, private to this counter
const other = makeCounter();
console.log(other()); // 1  -- a separate count

makeCounter finished running after the first call, yet count is still alive, held by the returned function. That is a closure. Each call to makeCounter creates a fresh count, which is why next and other are independent.

The call stack: when a() calls b() which calls c(), the stack is a -> b -> c. When c returns, it is popped off. If c throws an error, the error message includes the whole stack, so you can see the exact path that led to the failure.

Error: payment declined
    at chargeCard        (payment.service.ts:42)   <- where it threw
    at processOrder      (orders.service.ts:88)    <- who called that
    at OrdersController   (orders.controller.ts:23) <- who called that

Read a stack trace top to bottom: the top line is where the error happened, and each line below is the caller.

Practical example

A closure that builds a configured API client. The base URL and key are captured once and reused by every call.

function makePaymentClient(baseUrl: string, apiKey: string) {
  // baseUrl and apiKey are private to the returned functions.
  return {
    charge: async (amountCents: number) => {
      // uses baseUrl and apiKey without them being global
      return fetch(`${baseUrl}/charges`, {
        method: 'POST',
        headers: { Authorization: `Bearer ${apiKey}` },
        body: JSON.stringify({ amountCents }),
      });
    },
  };
}

Edge cases & failure modes

  • The classic loop-closure bug. With var i in a for loop, all closures share the one i and see its final value. With let i, each iteration gets a fresh i. This is the single most common closure bug and the reason let exists.
  • Stack overflow. A function that calls itself with no stopping condition fills the call stack until Node crashes with Maximum call stack size exceeded. Every recursive function needs a base case (Part 2).
  • Memory leaks via closures. A closure keeps its captured variables alive. If a long-lived closure captures a huge object, that object cannot be garbage-collected (Part 3). This is a real source of slow memory growth in long-running servers.

How a Senior Backend Engineer thinks about this

Closures are not an exotic trick; they are everywhere in backend code — every event handler, every middleware, every configured client is a closure. A senior is comfortable reading them and is alert to the memory implication: a closure captured by something long-lived (a cache, a global event emitter) can quietly pin large objects in memory. When they read a stack trace, they read it as a story: this called that called the thing that broke.

Common mistakes

  • The var-in-a-loop closure bug (use let).
  • Recursion with no base case, causing a stack overflow.
  • Capturing large objects in long-lived closures, leaking memory.
  • Not reading the stack trace and guessing at the cause instead.

Interview questions

  1. What is a closure? A function bundled with the variables from the scope where it was created, which it can access even after that scope has returned. Follow-up: give a use (private state, configured client, memoization).
  2. Why does the classic for loop with var print the final value in every callback? All iterations share one var binding; let creates a new binding each iteration.
  3. How do you read a stack trace? Top line is where it threw; each line below is the caller up the chain.

Practical exercise

Write makeRateLimiter(maxPerMinute) that returns a function allow() which returns true the first maxPerMinute times it is called within a rolling minute and false afterward, using a closure to hold the timestamps privately. Acceptance criteria: two separate limiters created by two calls to makeRateLimiter do not share state.

69.4.3 Typing functions well

Concept

TypeScript lets you describe a function's shape as a type: what it takes and what it returns. This lets you pass functions around safely (as callbacks) and define contracts that many functions must satisfy.

How it works

// A type for a function value.
type PriceRule = (subtotalCents: number) => number;

const tenPercentOff: PriceRule = (subtotal) => Math.round(subtotal * 0.9);
const fiveDollarsOff: PriceRule = (subtotal) => Math.max(0, subtotal - 500);

// A function that takes another function as an argument (a "higher-order function").
function applyRules(subtotalCents: number, rules: PriceRule[]): number {
  return rules.reduce((total, rule) => rule(total), subtotalCents);
}

applyRules(5000, [tenPercentOff, fiveDollarsOff]); // 4000, then 3500

A function that takes or returns another function is called a higher-order function. applyRules is one. The array methods you meet next (map, filter, reduce) are all higher-order functions: you hand them a function and they call it for you.

Function overloads and the options-object pattern

When a function takes many parameters, pass a single typed object instead. It is self-documenting at the call site and immune to argument-order mistakes.

interface CreateOrderInput {
  userId: string;
  items: { productId: string; quantity: number }[];
  couponCode?: string;
  giftWrap?: boolean;
}

function createOrder(input: CreateOrderInput): void {
  // input.userId, input.items, etc. -- order of fields does not matter
}

createOrder({
  userId: 'usr_1',
  items: [{ productId: 'p1', quantity: 2 }],
  giftWrap: true,
}); // clear and order-independent

How a Senior Backend Engineer thinks about this

A senior types callbacks and higher-order functions precisely, because a wrong callback signature is a bug that only shows up at runtime otherwise. For any function with more than two or three parameters, or with optional ones, they switch to an options object, because six months later nobody remembers whether createOrder(a, b, c, d) puts the coupon before or after the gift-wrap flag.

Common mistakes

  • Untyped callbacks (rules: Function[]), which lets any shape of function through.
  • Long positional parameter lists that callers get wrong.

Interview questions

  1. What is a higher-order function? One that takes a function as an argument or returns a function. Examples: map, filter, reduce, and any function that accepts a callback.
  2. Why prefer an options object over many positional parameters? Self-documenting call sites, order-independence, and easy optional fields.

Practical exercise

Define a type Validator = (value: unknown) => boolean and write a higher-order function validateAll(value, validators) that returns true only if every validator passes. Acceptance criteria: it short-circuits (stops) at the first failing validator.

69.5 Objects and arrays

69.5.1 Objects: grouping related data

Concept

An object is a collection of named values. Each name is a property (or key), and each property holds a value. Objects are how you represent a thing with several attributes — an order has an id, a status, a total and a list of items, so an order is naturally an object.

Why does it exist?

Primitives hold one value each. Real things have many attributes that belong together. Passing around five separate variables for one order (orderId, orderStatus, orderTotal, ...) is error-prone; passing one order object keeps them together and named. Objects are the backbone of every API request and response, because JSON — the format APIs speak — is objects and arrays.

Mental model

An object is a labelled drawer unit. Each small drawer has a label on the front (the key) and holds one thing (the value). You open the drawer by its label: order.status opens the drawer labelled status.

How it works

const order = {
  id: 'ord_1001',
  status: 'pending',
  totalCents: 4299,
  customer: {                      // a nested object
    id: 'usr_42',
    email: 'alice@example.com',
  },
};

// Reading properties: two ways.
console.log(order.status);          // dot notation: "pending"
console.log(order['status']);       // bracket notation: same thing
console.log(order.customer.email);  // reaching into a nested object

// Writing properties
order.status = 'paid';              // change an existing one
// order.trackingNumber = 'XZ99';   // in plain JS you can add new ones freely

Bracket notation matters when the key is in a variable: order[fieldName] where fieldName is 'status'. Dot notation needs a literal key.

Destructuring pulls properties out into variables in one line. You will use this constantly.

const { status, totalCents } = order;      // two new variables
console.log(status, totalCents);           // "paid" 4299

// Rename while destructuring, with a default:
const { status: orderStatus, giftWrap = false } = order;

Spread copies properties from one object into another. It is the standard way to make a changed copy without mutating the original.

const paidOrder = { ...order, status: 'paid', paidAt: new Date() };
// order is unchanged; paidOrder is a new object with status overridden

Typing objects with interfaces and type aliases

In TypeScript you describe an object's shape with an interface or a type alias. They are nearly interchangeable for this purpose; teams usually pick one and stay consistent.

interface Order {
  id: string;
  status: 'pending' | 'paid' | 'cancelled';  // a union of literals
  totalCents: number;
  customer: Customer;
  trackingNumber?: string;                    // optional
  readonly createdAt: Date;                   // cannot be reassigned
}

interface Customer {
  id: string;
  email: string;
}

// The same thing as a type alias:
type OrderStatus = 'pending' | 'paid' | 'cancelled';

Now TypeScript enforces the shape. Reading order.totl is an error. Assigning status = 'shipped' is an error, because 'shipped' is not in the union. Forgetting totalCents when building an order is an error. This is the type system doing its job: the shape of your core nouns becomes impossible to get wrong.

Practical example

Turning a database row into an API response, dropping internal fields.

interface OrderRow {
  id: string;
  status: OrderStatus;
  total_cents: number;    // snake_case from the database
  internal_notes: string; // must NOT go to the client
  created_at: Date;
}

interface OrderResponse {
  id: string;
  status: OrderStatus;
  totalCents: number;     // camelCase for the API
  createdAt: string;      // ISO string for JSON
}

function toResponse(row: OrderRow): OrderResponse {
  return {
    id: row.id,
    status: row.status,
    totalCents: row.total_cents,
    createdAt: row.created_at.toISOString(),
    // internal_notes is deliberately not copied
  };
}

This "mapper" pattern — convert a database row to a response shape — is one you will write hundreds of times. Doing it explicitly (rather than returning the raw row) is how you avoid leaking internal fields like internal_notes or a password hash to clients, which is a real and common security bug.

Edge cases & failure modes

  • Mutation surprises. Objects are passed by reference. If function A changes a property of an object that function B still holds, B sees the change. The spread copy ({ ...order }) makes a shallow copy — one level deep. Nested objects are still shared. For a deep copy use structuredClone(order) (built into modern Node).
  • Accessing a property of null/undefined throws Cannot read properties of undefined (reading 'email'). Use optional chaining order.customer?.email, which yields undefined instead of throwing if customer is missing.
  • Key order is mostly preserved but should not be relied on for logic. Treat objects as unordered maps of key to value.

How a Senior Backend Engineer thinks about this

A senior defines the core domain objects (Order, Customer, Product) as interfaces first, before writing much logic, because those shapes are the contract everything else depends on. They keep separate types for the database row, the internal domain object, and the API response, and they map between them on purpose — never returning a raw database row to a client, never trusting a raw request body as a domain object. They prefer making changed copies with spread over mutating in place, because shared mutable objects cause the bugs that are hardest to trace.

Common mistakes

  • Returning raw database rows to clients, leaking internal or sensitive fields.
  • Mutating an object that other code still holds, causing spooky action at a distance.
  • Forgetting that spread is a shallow copy and mutating a nested object inside the "copy".
  • Crashing on obj.a.b when a might be missing; use obj.a?.b.

Interview questions

  1. What does spread ({ ...obj }) do, and is it a deep copy? It copies top-level properties into a new object; it is a shallow copy, so nested objects are shared.
  2. How do you safely read a deeply nested property that might be missing? Optional chaining: a?.b?.c, which yields undefined instead of throwing.
  3. Why map a database row to a response object instead of returning it directly? To control which fields leave the system (security) and to translate naming and date formats for the API contract.

Practical exercise

Write a function publicProfile(user) where the user object has id, email, passwordHash and createdAt. Return an object with only id, email and createdAt (as an ISO string), and prove with a TypeScript type that passwordHash cannot appear in the return type. Acceptance criteria: changing the function to include passwordHash must cause a compile error.

69.5.2 Arrays and the methods you will actually use

Concept

An array is an ordered list of values. An order has a list of items; a page of results is a list of orders; a user has a list of addresses. Arrays hold those lists. The array methods — functions that live on every array — are how you transform lists without writing manual loops, and they are the single most-used tool in day-to-day backend code.

Why does it exist?

Almost all backend work is "take a list, turn it into another list, or boil it down to one value". Take the order items, turn each into a line total (a transform), keep only the in-stock ones (a filter), and sum them (a reduction). You could write for loops for all of this, but the array methods say what you mean in one readable line and avoid the off-by-one errors manual loops are famous for.

Mental model

Imagine an assembly line. map is a station that does the same operation to every item and passes each along (10 items in, 10 items out). filter is a gate that lets some items through and drops others (10 in, maybe 6 out). reduce is the station at the end that combines everything into a single result (10 in, 1 out). find is a worker who grabs the first item matching a description and stops looking.

How it works — the core methods

interface Item { productId: string; quantity: number; priceCents: number; inStock: boolean; }

const items: Item[] = [
  { productId: 'p1', quantity: 2, priceCents: 1000, inStock: true },
  { productId: 'p2', quantity: 1, priceCents: 2500, inStock: false },
  { productId: 'p3', quantity: 3, priceCents: 500, inStock: true },
];

// map: transform each element. Here, item -> line total in cents.
const lineTotals = items.map((item) => item.quantity * item.priceCents);
// [2000, 2500, 1500]

// filter: keep elements that pass a test.
const available = items.filter((item) => item.inStock);
// [p1, p3]

// reduce: collapse to one value. The 0 is the starting accumulator.
const subtotalCents = items.reduce((sum, item) => sum + item.quantity * item.priceCents, 0);
// 6000

// find: first element matching a test, or undefined.
const expensive = items.find((item) => item.priceCents >= 2000);
// the p2 item

// some / every: do any / do all match?
const hasOutOfStock = items.some((item) => !item.inStock); // true
const allHaveQuantity = items.every((item) => item.quantity > 0); // true

// sort: reorder. The comparator returns negative, zero or positive.
const byPriceAsc = [...items].sort((a, b) => a.priceCents - b.priceCents);

Two rules that save you from bugs: map, filter, some, every, find, reduce do not change the original array — they return a new array or value. But sort and reverse mutate the original, which is why we copy first with [...items] before sorting. Forgetting this and sorting an array that other code depends on is a real production bug.

Chaining

Methods return arrays (except reduce/find/some/every), so you can chain them into a readable pipeline:

const inStockSubtotalCents = items
  .filter((item) => item.inStock)
  .map((item) => item.quantity * item.priceCents)
  .reduce((sum, n) => sum + n, 0);
// filter to in-stock, turn each into a line total, sum them -> 3500

Read it top to bottom as a sentence: "of the items, keep the in-stock ones, turn each into a line total, and add them up." That readability is the whole point.

Typing arrays

const ids: string[] = ['a', 'b', 'c'];       // array of strings
const totals: number[] = [100, 200];          // array of numbers
const orders: Order[] = [];                    // array of Order objects
const matrix: number[][] = [[1, 2], [3, 4]];   // array of arrays

Practical example — building an order summary

interface CartLine { productId: string; name: string; unitCents: number; qty: number; }

function summarize(lines: CartLine[]) {
  const subtotalCents = lines.reduce((s, l) => s + l.unitCents * l.qty, 0);
  const itemCount = lines.reduce((s, l) => s + l.qty, 0);
  const names = lines.map((l) => l.name);
  return { subtotalCents, itemCount, names };
}

Production scenario

An endpoint returns the top 10 products by revenue for a dashboard. You fetch the raw sales rows, map each to { productId, revenue }, reduce into a per-product total using an object keyed by product id, turn that back into an array, sort by revenue descending, and slice(0, 10). The whole transformation is maybe eight lines and reads like its own description. The alternative — nested for loops with manual index bookkeeping — is longer, harder to read, and where off-by-one bugs live.

Failure scenario

At 09:00 a reporting endpoint starts returning the wrong order of results intermittently. The cause: the code called allOrders.sort(...) on an array that was also cached and shared across requests. sort mutated the shared array in place, so two concurrent requests sorting by different fields corrupted each other's data. The fix was one character of intent: [...allOrders].sort(...), sorting a copy. The lesson — know which methods mutate — is exactly the kind of thing that separates working code from correct code.

Edge cases & failure modes

  • sort without a comparator sorts as strings, so [10, 2, 1].sort() gives [1, 10, 2]. Always pass (a, b) => a - b for numbers.
  • find returns undefined when nothing matches; using the result without checking throws.
  • reduce with no initial value throws on an empty array; always pass the initial accumulator.
  • map over a huge array builds a whole second array in memory; for millions of rows, stream instead (Part 3).

How a Senior Backend Engineer thinks about this

A senior reaches for map/filter/reduce by default and writes a manual for loop only when they need early exit for performance, or index arithmetic, or when the loop body has side effects that read awkwardly in a method. They always pass a comparator to sort, always copy before sorting shared data, and always provide reduce's initial value. They are also aware of the cost: these methods create new arrays, which is fine for a cart of 20 items and wrong for a stream of 20 million, where they switch to streaming.

Common mistakes

  • sort without a comparator (string sort) on numbers.
  • Sorting a shared array in place and corrupting other code.
  • Using find's result without handling undefined.
  • reduce with no initial value on a possibly-empty array.
  • Reaching for forEach to build a result, mutating an outer variable, when map or reduce says it more clearly.

Interview questions

  1. What is the difference between map and forEach? map returns a new array of transformed values; forEach returns nothing and is used only for side effects. Prefer map when you want a result.
  2. Which array methods mutate the original? sort, reverse, splice, push, pop, shift, unshift, fill. The transforming methods (map, filter, slice, concat) do not.
  3. How does sort order values by default, and why is that a trap? Lexicographically (as strings), so numbers sort wrong without a comparator.
  4. What does reduce do and what is its initial value for? It collapses an array to one value by repeatedly combining; the initial value seeds the accumulator and prevents errors on empty arrays.

Practical exercise

Given an array of order objects each with status and totalCents, write one chained expression that computes the total revenue of only the 'paid' orders. Then write a second expression that returns the three highest-value paid orders. Acceptance criteria: the original array is not mutated, and both handle an empty input array without throwing.

69.5.3 Maps, Sets and when to use them

Concept

A Map is a collection of key-value pairs where keys can be any type (not just strings). A Set is a collection of unique values. They complement objects and arrays: use a Map for a lookup table, a Set for "have I seen this before?".

How it works

// Map: fast lookup by key.
const priceByProduct = new Map<string, number>();
priceByProduct.set('p1', 1000);
priceByProduct.set('p2', 2500);
priceByProduct.get('p1');        // 1000
priceByProduct.has('p3');        // false
priceByProduct.size;             // 2

// Set: uniqueness and membership tests.
const seenOrderIds = new Set<string>();
seenOrderIds.add('ord_1');
seenOrderIds.add('ord_1');       // ignored, already present
seenOrderIds.has('ord_1');       // true
seenOrderIds.size;               // 1

// De-duplicate an array in one line:
const unique = [...new Set(['a', 'b', 'a', 'c'])]; // ['a', 'b', 'c']

How a Senior Backend Engineer thinks about this

Reaching the right collection is a small decision with a real performance consequence. Checking array.includes(x) scans the whole array every time (slow for large lists); a Set.has(x) is near-instant. Building a lookup by scanning an array inside a loop is accidentally quadratic; building a Map once and looking up is linear. For the data structures behind these (hash tables), see Part 1; here, the habit is: list of things to iterate is an array, lookup by key is a Map, uniqueness or membership is a Set.

Interview questions

  1. When would you use a Map instead of a plain object? When keys are not strings, when you need reliable insertion order and size, or when you add and remove keys frequently. Objects are fine for fixed, string-keyed shapes.
  2. Why is Set.has better than array.includes for repeated membership tests? Set.has is roughly constant time; array.includes scans the array each call, which is slow for large lists and can make an algorithm quadratic.

Practical exercise

You have 100,000 order IDs already processed (in an array) and a new batch of 10,000. Write code that returns only the new batch IDs not already processed, using a Set so it runs in linear time. Acceptance criteria: do not use array.includes inside a loop.

69.6 Control flow

69.6.1 Conditionals and branching

Concept

Control flow is how a program decides what to do next. Conditionals (if, else, switch) choose between paths. Loops (for, while) repeat. Together they turn a static list of statements into a program that reacts to its data.

Why does it exist?

Real logic is full of decisions. Is the order paid? Then ship it. Is the user an admin? Then allow the delete. Is the inventory zero? Then reject the purchase. Without branching, every program would do exactly the same thing every time regardless of its input, which is to say it would not be a program at all.

How it works

function describeOrder(status: OrderStatus): string {
  if (status === 'paid') {
    return 'ready to ship';
  } else if (status === 'pending') {
    return 'awaiting payment';
  } else {
    return 'closed';
  }
}

The ternary operator is a compact if/else that yields a value:

const label = isPaid ? 'Paid' : 'Unpaid';

switch is cleaner than a long if/else if chain when branching on one value:

function nextStatus(status: OrderStatus): OrderStatus {
  switch (status) {
    case 'pending':
      return 'paid';
    case 'paid':
      return 'paid';        // already paid, no change
    case 'cancelled':
      return 'cancelled';
    default:
      // With a union type, TypeScript ensures every case is handled.
      throw new Error(`unknown status: ${status}`);
  }
}

The default case with a union type gives you exhaustiveness checking: if someone later adds 'refunded' to OrderStatus and forgets to handle it, TypeScript can flag the gap (with the never trick shown in 69.7). This is a quiet superpower — the compiler reminds you to update every switch when the set of statuses grows.

Guard clauses

A guard clause handles the exceptional or invalid case first and returns early, so the main logic is not buried inside nested ifs. Senior code is full of guard clauses.

// Nested, hard to read:
function charge(order: Order) {
  if (order.status === 'pending') {
    if (order.totalCents > 0) {
      // ... the real work, two levels deep
    }
  }
}

// Guard clauses, flat and clear:
function chargeBetter(order: Order) {
  if (order.status !== 'pending') throw new Error('order not pending');
  if (order.totalCents <= 0) throw new Error('nothing to charge');
  // ... the real work, at the top level
}

Practical example — an order state machine

A state machine lists which transitions are allowed. This pattern prevents illegal states, like shipping a cancelled order. We draw it as a diagram because that is how backend engineers reason about states.

stateDiagram-v2
    [*] --> pending
    pending --> paid: payment succeeds
    pending --> cancelled: user cancels
    paid --> shipped: warehouse dispatches
    paid --> refunded: refund issued
    shipped --> delivered: carrier confirms
    cancelled --> [*]
    delivered --> [*]
    refunded --> [*]
type Status = 'pending' | 'paid' | 'shipped' | 'delivered' | 'cancelled' | 'refunded';

const allowed: Record<Status, Status[]> = {
  pending: ['paid', 'cancelled'],
  paid: ['shipped', 'refunded'],
  shipped: ['delivered'],
  delivered: [],
  cancelled: [],
  refunded: [],
};

function canTransition(from: Status, to: Status): boolean {
  return allowed[from].includes(to);
}
canTransition('pending', 'shipped'); // false: must be paid first

This data-driven approach (a lookup table of allowed transitions) is cleaner than a tangle of ifs and is easy to extend. We return to state machines in Part 67.

How a Senior Backend Engineer thinks about this

A senior keeps the happy path at the top indentation level and pushes error and edge cases into guard clauses at the top of the function. They prefer switch with exhaustiveness checking over long if/else chains on a single value, because the compiler then forces every branch to be handled when the set of values grows. They model important state changes as explicit state machines rather than scattering if (status === ...) checks across the codebase, because scattered checks drift out of sync and allow illegal states.

Common mistakes

  • Deeply nested ifs instead of guard clauses; hard to read and easy to get the logic wrong.
  • switch with a missing break in plain JavaScript (falling through to the next case unintentionally); in the return-per-case style above this cannot happen.
  • Scattering status checks everywhere instead of one state machine, so illegal transitions slip through.

Interview questions

  1. What is a guard clause and why use it? An early return for an invalid or edge case, keeping the main logic unindented and readable.
  2. What is exhaustiveness checking in a switch? Using a union type and a never default so the compiler forces you to handle every case, catching missed branches when the union grows.

Practical exercise

Implement transition(order, to) that uses the allowed table above, throws a clear error for an illegal transition, and returns a new order object (not mutated) with the updated status. Acceptance criteria: adding a new status to the Status union without updating allowed must cause a TypeScript error.

69.6.2 Loops

Concept

Loops repeat a block of code. The main forms are for (counted), for...of (over the values of an array or other iterable), for...in (over the keys of an object — use sparingly), and while (until a condition is false).

How it works

const ids = ['a', 'b', 'c'];

// for...of: the modern default for iterating values.
for (const id of ids) {
  console.log(id);
}

// Classic for: when you need the index.
for (let i = 0; i < ids.length; i++) {
  console.log(i, ids[i]);
}

// while: when you do not know the count in advance.
let remaining = 3;
while (remaining > 0) {
  remaining--;
}

// for...in iterates object KEYS (as strings). Rarely what you want for arrays.
const prices = { p1: 1000, p2: 2500 };
for (const key in prices) {
  console.log(key, prices[key as keyof typeof prices]);
}

break exits a loop early; continue skips to the next iteration. Use break when you have found what you are looking for and need not continue — this is the main reason to write a manual loop instead of an array method.

When to use a loop vs an array method

Transform every element into a new value        -> map
Keep some elements                               -> filter
Combine into one value                           -> reduce
Find the first match, then stop                  -> find (or for...of + break)
Do a side effect for each (log, call an API)     -> for...of
Need the index, or step by 2, or go backwards    -> classic for
Repeat until a condition with no fixed count     -> while

Practical example — retry with a loop

async function withRetry<T>(fn: () => Promise<T>, maxAttempts = 3): Promise<T> {
  let lastError: unknown;
  for (let attempt = 1; attempt <= maxAttempts; attempt++) {
    try {
      return await fn();           // success: return immediately
    } catch (err) {
      lastError = err;
      // backoff would go here (Part 70)
    }
  }
  throw lastError;                 // all attempts failed
}

A counted for loop is the right tool here because we need the attempt number and an early return on success.

Edge cases & failure modes

  • Infinite loops. A while (true) with no break, or a for whose condition never becomes false, hangs the process. On a single-threaded Node server, an infinite loop freezes the entire server for every user, not just one request (Part 3).
  • for...in over arrays iterates indices as strings and includes inherited properties; use for...of for array values.
  • Modifying an array while iterating it with a classic for can skip or repeat elements. Build a new array instead.
  • await inside a loop runs iterations one after another (serial). If they are independent, that is needlessly slow; use Promise.all (Part 70) to run them together.

How a Senior Backend Engineer thinks about this

A senior defaults to array methods for data transformation and reserves explicit loops for early exit, index math, and side effects that read more clearly as a loop. They are acutely aware that on Node a long synchronous loop blocks the event loop and therefore every concurrent request (Part 3), so a loop over a million rows gets rewritten to stream or to yield control. They watch for the accidental-serial-await-in-a-loop pattern, one of the most common causes of a slow endpoint.

Common mistakes

  • await in a loop for independent work, making an endpoint 10x slower than needed.
  • A long synchronous loop blocking the event loop and freezing the server.
  • for...in on arrays.
  • Mutating the array being iterated.

Interview questions

  1. Why can a long synchronous loop freeze an entire Node server? Node runs your JavaScript on one thread; while the loop runs, the event loop cannot handle any other request (see Part 3).
  2. What is wrong with for (const x of items) { await save(x); } when saves are independent? It runs serially; await Promise.all(items.map(save)) runs them concurrently and is far faster.
  3. When do you write a manual for loop instead of map/filter? When you need early exit (break), the index, custom stepping, or side effects that are clearer as a loop.

Practical exercise

Rewrite a serial loop that fetches 20 product details one at a time (for...of with await) into a concurrent version using Promise.all, and explain in one sentence why the concurrent version is faster. Acceptance criteria: the concurrent version preserves the order of results.

69.7 Modules, interfaces and generics

69.7.1 Modules: splitting code across files

Concept

A module is a single file of code that explicitly states what it shares (export) and what it needs from other files (import). Modules are how a backend of thousands of lines stays organized — each file does one job and declares its public surface.

Why does it exist?

One giant file is unmaintainable. Modules let you put the order logic in orders.service.ts, the shipping logic in shipping.service.ts, and have each use the other through clear imports. The export/import boundary is also where you decide what is public (part of the module's contract) and what is private (an internal helper nobody else should call).

How it works

Modern JavaScript and TypeScript use ES modules (import/export). You will also see the older CommonJS (require/module.exports) in Node code; recognize it but write ES modules in new code.

// money.ts  -- a module that exports helpers
export function formatCents(cents: number): string {
  return `$${(cents / 100).toFixed(2)}`;
}

export const USD = 'USD';

// A default export (one per file, imported without braces):
export default function sum(amounts: number[]): number {
  return amounts.reduce((a, b) => a + b, 0);
}
// orders.ts  -- imports from money.ts
import sum, { formatCents, USD } from './money';   // default + named imports

const total = sum([1000, 2500]);
console.log(formatCents(total)); // "$35.00"

Named exports (in braces) are the common case; prefer them because they are explicit and tooling can rename them safely. The file path in the import is relative (./money) for your own files and a bare name ('@nestjs/common') for installed packages.

Barrel files and import organization

A "barrel" is an index.ts that re-exports from several files so callers import from one place. Useful in moderation; overused, it creates circular imports.

// orders/index.ts
export * from './orders.service';
export * from './orders.controller';

How a Senior Backend Engineer thinks about this

A senior treats a module's exports as its public API and keeps it small: export the service, not every helper. They avoid circular imports (file A imports B which imports A), which cause subtle undefined bugs at startup, by keeping dependencies flowing in one direction — controllers depend on services, services depend on repositories, never the reverse. The module boundary is the first and cheapest form of architecture, long before you reach for layers or microservices (Part 5).

Common mistakes

  • Circular imports, causing values to be undefined during module initialization.
  • Exporting internal helpers that should stay private, widening the contract accidentally.
  • Mixing CommonJS require and ES import in ways that break under the module system configured in tsconfig.json.

Interview questions

  1. What is the difference between a named export and a default export? Named exports are imported by name in braces and there can be many; a default export is imported without braces and there is one per file. Named exports are generally preferred for clarity and tooling.
  2. What problem do circular imports cause and how do you avoid them? A value may be undefined when first accessed because one module is still initializing. Avoid them by keeping dependency direction one-way.

Practical exercise

Split a single file containing money formatting, order totalling and a main that prints a summary into three modules (money.ts, orders.ts, main.ts) with explicit exports and imports. Acceptance criteria: main.ts imports only from orders.ts, and orders.ts imports only from money.ts — no circular imports.

69.7.2 Interfaces, type aliases and unions

Concept

We met interfaces in 69.5. Here we complete the picture: interfaces and type aliases describe object shapes; unions describe "one of several"; intersections combine shapes. These are the tools you use to model a domain precisely.

How it works

// Union: a value that is one of several types.
type Id = string | number;
type Status = 'pending' | 'paid' | 'cancelled';   // union of string literals

// Intersection: a value that satisfies several shapes at once.
interface Timestamped { createdAt: Date; updatedAt: Date; }
interface Order { id: string; totalCents: number; }
type PersistedOrder = Order & Timestamped;        // has all four fields

// Discriminated union: the pro move for modelling events or results.
type PaymentResult =
  | { kind: 'success'; chargeId: string }
  | { kind: 'declined'; reason: string }
  | { kind: 'error'; message: string };

function handle(result: PaymentResult) {
  switch (result.kind) {
    case 'success':
      return result.chargeId;      // TypeScript knows chargeId exists here
    case 'declined':
      return result.reason;        // and reason here
    case 'error':
      return result.message;
    default:
      // Exhaustiveness: if a new kind is added, this line errors.
      const _never: never = result;
      return _never;
  }
}

The discriminated union (a union of objects that share a common literal field, here kind) is one of the most valuable patterns in TypeScript backend code. It models "a thing that is one of several shapes" — a payment result, a webhook event, a command — and the compiler narrows to the right shape inside each case. The never default gives you exhaustiveness checking for free.

How a Senior Backend Engineer thinks about this

A senior models the domain with unions so that illegal combinations cannot be represented. Instead of an object with success: boolean, chargeId?: string and reason?: string (where every combination is technically possible, including the nonsensical ones), they use a discriminated union where a success always has a charge id and a decline always has a reason, and nothing else is expressible. "Make illegal states unrepresentable" is the principle; discriminated unions are the main tool for it in TypeScript.

Common mistakes

  • Boolean-and-optional-field soup ({ ok: boolean; data?: T; error?: string }) instead of a discriminated union, allowing impossible combinations.
  • Using interface and type inconsistently across a codebase; pick a convention.

Interview questions

  1. What is a discriminated union and why is it useful? A union of object types sharing a literal "tag" field; the compiler narrows to the correct shape per branch, and it prevents illegal field combinations.
  2. Interface vs type alias — when does it matter? Rarely for plain object shapes; interfaces can be re-opened and are conventional for public contracts, type aliases can express unions and intersections. Consistency matters more than the choice.

Practical exercise

Model a WebhookEvent as a discriminated union with three kinds (order.created, order.paid, order.cancelled), each carrying different fields, and write a process function with exhaustiveness checking. Acceptance criteria: adding a fourth kind without handling it causes a compile error.

69.7.3 Generics: types that take parameters

Concept

A generic is a type with a blank to fill in. Array<T> is a generic: T is the blank, so Array<string> is an array of strings and Array<Order> is an array of orders. Generics let you write one reusable function or type that works for many element types while staying fully type-safe.

Why does it exist?

Without generics, you would either write a separate firstString, firstNumber, firstOrder for each type (repetitive), or use any and lose all safety. A generic first<T>(items: T[]): T | undefined works for every type and keeps the exact type: first(orders) returns Order | undefined, not any.

How it works

// A generic function. T is a placeholder filled in at the call site.
function first<T>(items: T[]): T | undefined {
  return items.length > 0 ? items[0] : undefined;
}

const o = first([{ id: 'ord_1' }]); // o is typed as { id: string } | undefined
const n = first([1, 2, 3]);          // n is number | undefined

// A generic interface: a reusable "page of results" shape.
interface Page<T> {
  items: T[];
  total: number;
  cursor: string | null;
}

const orderPage: Page<Order> = { items: [], total: 0, cursor: null };

// Constrained generic: T must have an id. "extends" sets the constraint.
function indexById<T extends { id: string }>(items: T[]): Map<string, T> {
  const map = new Map<string, T>();
  for (const item of items) map.set(item.id, item);
  return map;
}

The constraint T extends { id: string } means "T can be any type, as long as it has a string id". That lets the body safely read item.id while still working for any entity with an id.

Practical example — a typed generic repository

This previews a pattern used throughout the book: one generic base repository that every entity's repository extends.

interface Repository<T extends { id: string }> {
  findById(id: string): Promise<T | null>;
  save(entity: T): Promise<T>;
  delete(id: string): Promise<void>;
}

// A concrete repository just fills in T:
type OrderRepository = Repository<Order>;

How a Senior Backend Engineer thinks about this

A senior uses generics to remove duplication without sacrificing type safety — the generic Page<T>, the generic Result<T, E>, the generic repository. They do not over-engineer: a generic with four type parameters and nested constraints is usually a sign something is too clever. The rule is "reach for a generic when you are about to copy a function only to change its element type." The tools (Page<T>, Promise<T>, Record<K, V>, Partial<T>, Pick<T, K>) become second nature and let them describe real API shapes exactly.

Common mistakes

  • Using any where a generic would keep the type (function first(items: any[]): any).
  • Over-complicated generics that are harder to read than three concrete versions would be.
  • Forgetting a constraint (T extends ...) and then being unable to touch the value's properties.

Interview questions

  1. What problem do generics solve? Reuse across element types without losing type safety or resorting to any.
  2. What does T extends { id: string } mean? A constraint: T may be any type that has a string id property, letting the function safely use id.
  3. Give a real backend use of a generic type. A Page<T> pagination wrapper, a Result<T, E> type, or a base Repository<T>.

Practical exercise

Write a generic function groupBy<T, K extends string>(items: T[], keyFn: (item: T) => K): Record<K, T[]> that groups array elements by a computed key. Test it by grouping orders by status. Acceptance criteria: the return type correctly reflects the key type, and the original array is not mutated.

Part 70 — Asynchronous JavaScript

Backend code spends most of its life waiting. It waits for the database to answer a query, for a payment provider to respond, for a file to be read from disk, for another service across the network. Those waits are long — a database query is a few milliseconds, a cross-region HTTP call can be a hundred — and if your program stopped dead during every wait, it could serve one user at a time. Asynchronous programming is how JavaScript handles thousands of simultaneous requests on a single thread by never standing still during a wait.

This Part teaches asynchronous JavaScript from the beginning. We start with the event loop at a level a beginner can hold in their head (Part 3 goes much deeper). Then callbacks, the original way to handle "do this when the result arrives", and the "callback hell" that made them painful. Then promises, the object that represents a future value. Then async/await, the modern syntax that makes asynchronous code read like ordinary code. We finish with error handling in asynchronous code and the pitfalls that catch everyone at least once.

If this is the one Part of Volume 0 you half-skip, your backend career will be a long series of confusing bugs. Asynchronous code is where beginners write things that work on their laptop with one user and fall apart in production with a thousand. Spend the time here.

70.1 Why asynchronous code exists

70.1.1 The single thread and the event loop

Concept

Node.js runs your JavaScript on one thread — one worker, doing one thing at a time. That sounds like a limitation, and it would be, except that Node does not sit idle during slow operations. When your code asks for something slow (a database query, a network call, a file read), Node hands that work off to the operating system, moves on to other work, and comes back to your code when the result is ready. The mechanism that juggles this is the event loop.

Why does it exist?

A web server must handle many requests at once. The old model gave each request its own operating-system thread, which is simple but expensive: each thread uses memory and the operating system spends effort switching between thousands of them. Node took a different bet: one thread, but never block it. Because most of a backend's time is spent waiting (on I/O — input/output — not on computing), one thread that never waits idly can handle enormous concurrency cheaply. This is why a single Node process can serve tens of thousands of simultaneous connections.

Mental model

Imagine a single chef in a kitchen (the one thread). A naive chef puts a pot on to boil and stands there watching it for ten minutes, doing nothing else. A good chef puts the pot on, sets a timer, and starts chopping vegetables for the next order. When the timer rings (the event), they come back to the pot. The chef is never cloned — there is always exactly one — but they are never idle while something cooks. The event loop is the chef's habit of always checking "what is ready now?" and never standing and staring at a pot.

The crucial consequence: if the chef ever does a task that cannot be set aside — say, hand-grinding spices for ten minutes with full attention — then every other order waits, because there is only one chef. In Node, a long synchronous computation (a giant loop, parsing a huge string, a slow regular expression) is exactly that: it blocks the one thread, and every other request freezes until it finishes. This is the most important thing to understand about Node.

How it works

Here is the beginner's picture of the event loop. (Part 3 covers microtasks, macrotasks, phases and libuv in full.)

  Your synchronous code runs top to bottom on the one thread.
        |
        |  hits a slow operation (query, HTTP, timer, file read)
        v
  Node hands it to the OS / a thread pool and registers a callback
        |
        |  your code keeps running; the thread is free
        v
  [ Event loop ] keeps checking: "is any result ready?"
        |
        |  when a result arrives, its callback is queued
        v
  The callback runs on the one thread when it is free again

Three things to take away:

  1. Your own JavaScript is never interrupted mid-function. A function runs to completion before anything else runs. This makes a lot of reasoning simple — there are no surprise interruptions in the middle of your code.
  2. Slow I/O does not block the thread, because Node hands it off and comes back via a callback.
  3. Slow computation does block the thread, because computation is your JavaScript, and your JavaScript holds the one thread until it returns.

Practical example

console.log('1: start');

setTimeout(() => {
  console.log('3: timer fired after everyone else');
}, 0);

console.log('2: end');

// Output order:
// 1: start
// 2: end
// 3: timer fired after everyone else

Even though the timer is 0 milliseconds, 3 prints last. The setTimeout callback is handed to the event loop and can only run after the current synchronous code (1 and 2) finishes. This surprises every beginner and is the clearest demonstration that "asynchronous" means "later, when the thread is free", not "right now in parallel".

Production scenario

A NestJS endpoint handles 2,000 requests per second on a single Node process. Each request does three database queries (about 2 ms each) and one call to a pricing service (about 40 ms). The thread is busy with actual JavaScript for maybe 0.5 ms per request; the other ~46 ms is waiting on I/O, during which the thread serves other requests. That is how one thread serves 2,000 requests per second: it is almost never computing, almost always waiting, and the event loop fills the waits with other requests' work.

Failure scenario

At 14:20 an endpoint that validates uploaded CSV files starts timing out for all users, not just the ones uploading. The cause: a new feature parsed each uploaded file with a synchronous loop that, for a large file, ran for 800 milliseconds of pure computation. During those 800 ms the one thread was held, so every other request — logins, product pages, checkouts — queued behind it. The dashboard showed the whole service degraded whenever anyone uploaded a big file. The fix was to move the parsing off the main thread (a worker thread, Part 3) and to stream the file instead of loading it whole. The lesson: on Node, one slow synchronous operation harms everyone.

Edge cases & failure modes

  • A long synchronous loop or heavy computation blocks every request (CPU-bound work needs worker threads or a separate service; Part 3).
  • A synchronous file read (fs.readFileSync) in a request handler blocks the thread for the duration of the read; always use the asynchronous versions in a server.
  • A catastrophic regular expression (ReDoS) can block the thread for seconds on a crafted input — both a performance and a security problem (Part 23).

How a Senior Backend Engineer thinks about this

A senior carries one rule from this section into everything: do not block the event loop. They know Node's superpower is handling many concurrent waits cheaply and its weakness is CPU-bound work, so they keep request handlers light on computation, push heavy work to background workers (Part 20), and measure event-loop lag as a first-class metric (Part 3). When someone proposes doing image processing or large-file parsing inside a request handler, the senior's first question is "how long does that hold the thread, and whom does it block while it runs?"

Common mistakes

  • Thinking setTimeout(fn, 0) runs fn immediately; it runs after the current synchronous code.
  • Doing heavy computation in a request handler and blocking all other requests.
  • Using synchronous file or crypto functions (...Sync) in a server.
  • Assuming Node is multi-threaded for your code; your JavaScript runs on one thread.

Interview questions

  1. Node runs on one thread — how does it handle thousands of concurrent requests? It never blocks the thread on I/O; it hands slow operations to the OS and returns to them via callbacks through the event loop, filling the waits with other work.
  2. Why does setTimeout(fn, 0) not run fn immediately? The callback is queued and can only run after the current synchronous code finishes and the event loop reaches it.
  3. What is the danger of a CPU-bound loop in a request handler? It blocks the single thread, freezing every other request until it finishes.

Practical exercise

Write a script that prints A, schedules a setTimeout(..., 0) that prints C, and prints B, then predict and verify the output order. Then add a synchronous loop that counts to 1 billion between A and B and observe that C is delayed by the whole loop, demonstrating event-loop blocking. Acceptance criteria: explain in two sentences why C is delayed.

70.2 Callbacks

70.2.1 The callback pattern

Concept

A callback is a function you give to another function to be called later, when some work finishes. "Here is my phone number; call me back when the result is ready." Callbacks were the original way JavaScript handled asynchronous results, and they still appear in older Node APIs and some libraries.

Why does it exist?

Because the result is not ready yet. A function that reads a file cannot return the file contents immediately — the file takes time to read. So instead it says "give me a function, and I will call it with the contents once I have them." The callback is how the slow function delivers its result after the wait.

Mental model

You order a coffee and the barista takes your name. You do not stand frozen at the counter staring at the machine (that would be blocking). You sit down and do other things. When the coffee is ready, the barista calls your name (the callback) and you come get it. Your name is the callback; the barista calling it is the asynchronous completion.

How it works

Node's traditional callbacks follow the error-first convention: the callback's first argument is an error (or null if all went well), and the second is the result. This convention is everywhere in older Node code.

import { readFile } from 'node:fs';

// readFile is asynchronous: it returns immediately and calls the callback later.
readFile('order.json', 'utf8', (err, data) => {
  if (err) {
    console.error('failed to read file:', err.message);
    return;                          // must return so we do not use data
  }
  console.log('file contents:', data);
});

console.log('this prints BEFORE the file contents');

The console.log at the bottom runs first, because readFile returns immediately and the callback runs later when the file has been read. Checking err first, and returning on error, is mandatory — forgetting it leads to using an undefined result.

Practical example

Chaining two dependent asynchronous steps with callbacks: read a config file, then read the file it points to.

import { readFile } from 'node:fs';

readFile('config.json', 'utf8', (err, configRaw) => {
  if (err) return console.error('config read failed:', err.message);

  const config = JSON.parse(configRaw);
  readFile(config.dataPath, 'utf8', (err2, data) => {
    if (err2) return console.error('data read failed:', err2.message);
    console.log('data:', data);
  });
});

Notice the nesting. Each dependent step goes one level deeper. With two steps it is fine. With six, it becomes the problem described next.

Failure scenario (callback hell)

A real order-processing flow had seven dependent asynchronous steps: validate, check inventory, reserve stock, charge card, create shipment, send email, write audit log. Written with callbacks, it became a pyramid eight levels deep, with error handling duplicated at every level and a growing rightward drift that engineers nicknamed "the christmas tree". A bug in the refund path went unnoticed for weeks because the error handling at level six silently swallowed it — a return was missing, so after logging the error the code fell through and continued as if nothing was wrong, charging the card after inventory had failed. The deep nesting hid the control-flow bug. Promises and async/await were invented largely to make this class of bug visible and rare.

doA(function (err, a) {
  if (err) ...
  doB(a, function (err, b) {
    if (err) ...
    doC(b, function (err, c) {
      if (err) ...
        doD(c, function (err, d) {    // the pyramid keeps growing right
          ...
        });
    });
  });
});

Edge cases & failure modes

  • Forgetting return after handling an error, so the code continues with a bad or undefined result (the refund bug above).
  • Calling the callback twice (for example in both a success and an error path), causing downstream logic to run twice — a real source of double-charges.
  • Errors thrown inside a callback are not caught by a try/catch around the function that scheduled it, because the callback runs later, on a different turn of the event loop. This is a major reason promises are better.
  • Unhandled errors in a callback with no error handling crash the process.

How a Senior Backend Engineer thinks about this

A senior reads callback-based code carefully for the two classic bugs — missing return after an error, and double invocation — because both are invisible in deeply nested code and both cause money bugs (double charges, continuing after a failed step). In new code they never write raw callbacks for multi-step flows; they promisify the callback API (util.promisify, or use the fs/promises version) and use async/await. Callbacks remain fine for genuine event streams (an event emitter firing many times), which promises do not model well.

Common mistakes

  • Deeply nested callbacks ("callback hell") that hide control-flow bugs.
  • Missing return after an error check.
  • Mixing try/catch with callbacks and wondering why errors are not caught.
  • Calling a callback more than once.

Interview questions

  1. What is the error-first callback convention? The callback's first argument is an error (or null), the second is the result; you must check the error before using the result.
  2. Why does try/catch not catch errors thrown inside an asynchronous callback? The callback runs on a later turn of the event loop, after the try/catch has already finished; the error has no surrounding try at that point.
  3. What is callback hell and what replaced it? Deeply nested callbacks for dependent async steps; promises and async/await replaced it with flat, readable, properly-catchable code.

Practical exercise

Take a three-level nested callback flow (read file, parse, write a derived file) and identify where a missing return after an error check would cause the next step to run with bad data. Then note which line a double callback invocation would break. Acceptance criteria: you can point to the exact failure for each bug without running the code.

70.3 Promises

70.3.1 What a promise is

Concept

A promise is an object that represents a value that is not ready yet but will be (or will fail) in the future. It is a placeholder for an asynchronous result. Instead of handing a callback into a function, the function hands you back a promise, and you attach what to do on success (.then) and on failure (.catch).

A promise is always in one of three states: pending (still working), fulfilled (succeeded, has a value), or rejected (failed, has an error). Once it settles (fulfilled or rejected) it never changes again.

Why does it exist?

Promises exist to fix the problems with callbacks: the nesting pyramid, the duplicated error handling, and the fact that try/catch could not catch asynchronous errors. A promise is a first-class object you can pass around, return, store and combine. That object-ness is what lets you flatten the pyramid into a chain, handle all errors in one place, and run several asynchronous operations together.

Mental model

A promise is a tracking number for a parcel. The moment you order, you do not have the parcel, but you have a tracking number — a handle to the eventual delivery. You can check its status (pending, delivered, failed). You can say "when it is delivered, do this" (.then) and "if delivery fails, do that" (.catch). You can even say "when all five of my parcels arrive, start the party" (Promise.all). The tracking number exists now; the parcel comes later.

How it works

stateDiagram-v2
    [*] --> pending
    pending --> fulfilled: resolve(value)
    pending --> rejected: reject(error)
    fulfilled --> [*]
    rejected --> [*]
// A promise that resolves after a delay. This is the promise version of setTimeout.
function delay(ms: number): Promise<void> {
  return new Promise((resolve) => {
    setTimeout(resolve, ms);
  });
}

// Using .then / .catch
delay(1000)
  .then(() => console.log('one second passed'))
  .catch((err) => console.error('something failed', err));

A promise that already comes from a library (a database driver, an HTTP client) is the common case; you rarely build one with new Promise yourself. When you do, you call resolve(value) on success or reject(error) on failure.

Chaining and flattening

The key improvement over callbacks: .then returns a new promise, so you chain instead of nesting. Dependent steps go down, not right.

fetchOrder(orderId)                       // returns Promise<Order>
  .then((order) => fetchCustomer(order.customerId))  // returns Promise<Customer>
  .then((customer) => sendReceipt(customer.email))   // returns Promise<void>
  .then(() => console.log('done'))
  .catch((err) => console.error('any step failed:', err.message));

Two things to notice. First, the flow reads top to bottom even though each step depends on the previous — no pyramid. Second, one .catch at the end handles a failure in any of the steps. If fetchCustomer rejects, the chain skips the remaining .thens and jumps straight to .catch. This is the single biggest practical win over callbacks: error handling in one place.

A subtle but critical rule: you must return the inner promise from a .then (return fetchCustomer(...)), or the chain does not wait for it. Forgetting the return is a classic bug where the next step runs before the previous one finished.

Combining promises

// Promise.all: run several in parallel, wait for all, fail if any fails.
const [order, inventory, pricing] = await Promise.all([
  fetchOrder(id),
  fetchInventory(id),
  fetchPricing(id),
]);
// All three ran concurrently. Total time ~= the slowest one, not the sum.

// Promise.allSettled: wait for all, never short-circuit; get each result or error.
const results = await Promise.allSettled([sendEmail(a), sendEmail(b), sendEmail(c)]);
// results[i] is { status: 'fulfilled', value } or { status: 'rejected', reason }

// Promise.race: settle as soon as the FIRST one settles (used for timeouts).
const data = await Promise.race([
  fetchFromSlowService(),
  rejectAfter(2000, new Error('timeout')),
]);

// Promise.any: resolve as soon as the first SUCCESS; useful for redundant sources.

The difference between Promise.all and Promise.allSettled matters in production. Promise.all short-circuits: the moment one promise rejects, the combined promise rejects, and you lose the other results (they still run, but you do not see their outcomes). Use Promise.all when you need every one to succeed (fetch three things to build a page — if one fails, the page fails). Use Promise.allSettled when you want all outcomes regardless (send three notifications — report which succeeded and which failed, do not abandon the rest).

Practical example — parallel vs serial

// SERIAL: three queries one after another. Total ~= sum of all three.
async function serial(id: string) {
  const a = await fetchOrder(id);        // wait 5 ms
  const b = await fetchInventory(id);    // then wait 5 ms
  const c = await fetchPricing(id);      // then wait 5 ms
  return { a, b, c };                     // ~15 ms total
}

// PARALLEL: three queries at once because they are independent. Total ~= slowest.
async function parallel(id: string) {
  const [a, b, c] = await Promise.all([
    fetchOrder(id),
    fetchInventory(id),
    fetchPricing(id),
  ]);
  return { a, b, c };                      // ~5 ms total
}

This is one of the most common real performance wins. Three independent 40 ms calls take 120 ms serially and 40 ms in parallel. On an endpoint that does several independent lookups, switching from serial awaits to Promise.all can cut latency by 3x with a one-line change. Only parallelize independent work; if step B needs step A's result, they must be serial.

Production scenario

A product-detail endpoint originally did six await calls in sequence — product, inventory, reviews, recommendations, price, shipping estimate — for a p50 of 95 ms. Four of the six were independent of each other. Grouping those four into a Promise.all and keeping the two dependent ones serial dropped p50 to 38 ms. No new infrastructure, no caching, just stopping the thread from waiting serially on things that could wait together.

Failure scenario

A notification service sent three messages with Promise.all([sms, email, push]). One day the SMS provider had an outage. Because Promise.all short-circuits on the first rejection, the whole call rejected, the error handler logged "notifications failed", and the email and push were treated as failed too even though they had actually succeeded — and worse, a retry then re-sent the email and push, so users got duplicate emails. Switching to Promise.allSettled fixed it: each channel's outcome was handled independently, only the failed SMS was retried, and the duplicates stopped. The lesson: Promise.all is for "all must succeed"; for independent best-effort work, use allSettled.

Edge cases & failure modes

  • Forgetting to return the inner promise in a .then, so the chain does not wait and later steps run too early.
  • An unhandled rejection (a promise that rejects with no .catch and no surrounding try/catch) crashes the Node process in modern versions. Every promise chain needs error handling.
  • Promise.all loses sibling results on the first rejection; use allSettled when you need them all.
  • Creating promises in a loop and not awaiting them fires them all at once with no concurrency limit, which can open 10,000 database connections and exhaust the pool. For large batches, limit concurrency (a batching helper or a library like p-limit).
  • A promise never settles (a bug where resolve/reject is never called) hangs that chain forever; always have a timeout on external calls.

How a Senior Backend Engineer thinks about this

A senior sees await a; await b; await c on independent operations as a latency bug and reaches for Promise.all. They choose all vs allSettled deliberately based on whether partial success is acceptable. They never fire an unbounded number of promises in a loop against a shared resource (database, downstream service) without a concurrency limit, because that turns a batch job into a self-inflicted denial-of-service. And they put a timeout on every call that leaves the process, because a promise that waits forever on a hung dependency is how one slow service takes down yours (Part 38 covers timeouts, retries and circuit breakers in depth).

Common mistakes

  • Serial awaits for independent work (slow endpoints).
  • Forgetting return inside .then.
  • Unhandled rejections crashing the process.
  • Unbounded Promise.all over a huge array, exhausting connections.
  • Using all where allSettled is needed, abandoning or duplicating sibling work on one failure.

Interview questions

  1. What are the three states of a promise? Pending, fulfilled, rejected; once settled it never changes.
  2. What is the difference between Promise.all and Promise.allSettled? all rejects as soon as any input rejects and loses the other results; allSettled waits for all and reports each outcome. Use all when every one must succeed, allSettled for independent best-effort work.
  3. How do you convert serial awaits into parallel execution, and when must you not? Group independent operations into Promise.all; you must keep operations serial when one depends on another's result.
  4. What happens to an unhandled promise rejection in modern Node? It crashes the process; every chain needs a .catch or a surrounding try/catch.
  5. Why is firing thousands of promises in a loop against the database dangerous? It opens all those operations at once with no concurrency limit, exhausting the connection pool and overwhelming the database.

Practical exercise

Given functions fetchUser(id), fetchOrders(id) and fetchRecommendations(id) (all independent, each ~30 ms), write a getDashboard(id) that runs them in parallel with Promise.all and returns a combined object. Then write a notifyAll(users) that sends an email to each user with Promise.allSettled, limiting concurrency to 10 at a time, and returns counts of succeeded and failed. Acceptance criteria: the dashboard completes in ~30 ms not ~90 ms, and notifyAll never has more than 10 emails in flight at once.

70.4 Async and await

70.4.1 Writing asynchronous code that reads like synchronous code

Concept

async/await is syntax built on top of promises. An async function always returns a promise. Inside it, await pauses the function until a promise settles, then gives you the value — or throws if it rejected. The result is asynchronous code that reads top to bottom like ordinary synchronous code, with normal try/catch for errors.

Why does it exist?

Even with promises, .then chains get awkward for anything with conditionals, loops or several intermediate values. async/await lets you write the same logic as plain-looking sequential code. It is not a new mechanism — under the hood it is still promises and the event loop — it is a much more readable way to write them. Today it is the default for all asynchronous backend code; .then/.catch is reserved for a few specific spots.

Mental model

await is a bookmark. When your function hits await someSlowThing(), it places a bookmark, steps away so the one thread can serve other work, and comes back to exactly that line when the result is ready — picking up with the value in hand. The function appears to "wait", but the thread does not; only this particular function is paused, bookmarked, while everyone else carries on.

How it works

// The same order flow from the promises section, now with async/await.
async function processOrder(orderId: string): Promise<void> {
  const order = await fetchOrder(orderId);          // pause until order arrives
  const customer = await fetchCustomer(order.customerId); // then until customer
  await sendReceipt(customer.email);                // then until receipt sent
  console.log('done');
}

Compare this to the .then chain in 70.3 and the callback pyramid in 70.2 — same logic, progressively more readable. Three rules:

  1. await can only be used inside an async function (or at the top level of a module in modern Node).
  2. An async function always returns a promise, even if you return a plain value — return 5 becomes Promise<number>.
  3. await unwraps the promise: const x = await fetchOrder(id) gives you the Order, not a Promise<Order>.

Error handling with try/catch

The big win: asynchronous errors are caught by ordinary try/catch, which callbacks could not do.

async function processOrder(orderId: string): Promise<void> {
  try {
    const order = await fetchOrder(orderId);
    const customer = await fetchCustomer(order.customerId);
    await sendReceipt(customer.email);
  } catch (err) {
    // Catches a rejection from ANY of the awaited calls above.
    console.error('order processing failed:', (err as Error).message);
    throw err;                      // rethrow if the caller must know
  }
}

One try/catch covers every await inside it, just as one .catch covered the whole chain. In TypeScript the caught value is typed unknown (since anything can be thrown), so you narrow it with err instanceof Error before reading .message.

Parallelism with async/await

await is sequential by default — each one waits for the previous. For independent work, combine await with Promise.all, exactly as before.

async function getDashboard(userId: string) {
  // WRONG for independent work: three sequential waits.
  // const user = await fetchUser(userId);
  // const orders = await fetchOrders(userId);
  // const recs = await fetchRecommendations(userId);

  // RIGHT: start all three, then await them together.
  const [user, orders, recs] = await Promise.all([
    fetchUser(userId),
    fetchOrders(userId),
    fetchRecommendations(userId),
  ]);
  return { user, orders, recs };
}

Writing await three times in a row is the most common beginner performance mistake. await does not mean "do these in parallel" — it means "wait here". Independent work needs Promise.all.

Practical example — NestJS service method

Every NestJS service method you write will look like this: an async method that awaits a repository and handles errors.

import { Injectable, NotFoundException } from '@nestjs/common';
import { InjectRepository } from '@nestjs/typeorm';
import { Repository } from 'typeorm';
import { Order } from './order.entity';

@Injectable()
export class OrdersService {
  constructor(@InjectRepository(Order) private readonly repo: Repository<Order>) {}

  async findOne(id: string): Promise<Order> {
    const order = await this.repo.findOne({ where: { id } });
    if (!order) throw new NotFoundException(`Order ${id} not found`);
    return order;
  }

  async summary(userId: string) {
    // Independent queries run together.
    const [open, completed] = await Promise.all([
      this.repo.count({ where: { userId, status: 'pending' } }),
      this.repo.count({ where: { userId, status: 'delivered' } }),
    ]);
    return { open, completed };
  }
}

Edge cases & failure modes

  • Serial await for independent work (the main performance trap).
  • await inside Array.forEach does not work — forEach ignores the returned promise, so the loop does not wait. Use a for...of loop (serial) or Promise.all(map(...)) (parallel).
  • Forgetting await on a promise-returning call means the function continues before the work finishes, and any error becomes an unhandled rejection. TypeScript with the right lint rule flags "floating promises".
  • Awaiting in a loop over a large array runs serially and can be very slow; parallelize with a concurrency limit if the work is independent.
  • A missing return await inside try/catch: if you write return somePromise() instead of return await somePromise(), a rejection escapes the try/catch because the function has already returned. Use return await when you want the catch to handle it.

How a Senior Backend Engineer thinks about this

A senior writes async/await as the default and uses Promise.all the instant two awaited operations are independent. They never use await inside forEach. They enable the "no floating promises" lint rule so a forgotten await is caught at build time rather than becoming a 2 a.m. unhandled rejection. They put try/catch where they can actually do something useful with the error (translate it, add context, decide to retry) and let it propagate otherwise, because catching an error only to re-log and rethrow it at every level just produces noise (Part 36).

Common mistakes

  • Serial awaits for independent work.
  • await inside forEach (silently does nothing useful).
  • Forgetting await, creating a floating promise and an unhandled rejection.
  • Wrapping everything in try/catch and swallowing errors instead of handling or propagating them.

Interview questions

  1. What does an async function return? Always a promise, even if the body returns a plain value.
  2. Why does await inside forEach not work? forEach ignores the promise returned by its callback, so it does not wait; use for...of or Promise.all(map(...)).
  3. How do you run two independent awaited calls concurrently? const [a, b] = await Promise.all([callA(), callB()]).
  4. What is a floating promise and why is it dangerous? A promise-returning call with no await and no .catch; its errors become unhandled rejections and its completion is not awaited, causing race conditions and crashes.

Practical exercise

Convert the callback-based config-then-data flow from Part 70.1 into async/await with a single try/catch. Then write a loadAll(paths: string[]) that reads many files; provide two versions — one serial with for...of, one parallel with Promise.all — and measure the difference. Acceptance criteria: the parallel version is dramatically faster for many files, and both handle a missing file with a clear error.

70.5 Error handling and pitfalls in asynchronous code

70.5.1 Errors, timeouts and cancellation

Concept

Asynchronous code fails in ways synchronous code does not: the thing you are waiting for can be slow, can hang forever, can fail, or can succeed after you have given up. Robust asynchronous code plans for all of these. The three tools are: proper error propagation (try/catch around awaits), timeouts (never wait forever on the network), and cancellation (AbortController) to stop work you no longer need.

Why does it exist?

Without a timeout, one hung downstream service makes every request to your endpoint hang too, until your own connection pool and thread capacity are exhausted and your whole service goes down — a cascading failure. Without cancellation, when a user navigates away or a request times out, you keep doing expensive work for a result nobody will read. These are not edge cases; they are how real outages spread.

How it works

Timeout on any promise using Promise.race or, in modern Node, AbortSignal.timeout:

// Generic timeout wrapper.
function withTimeout<T>(promise: Promise<T>, ms: number): Promise<T> {
  const timeout = new Promise<never>((_, reject) =>
    setTimeout(() => reject(new Error(`timed out after ${ms}ms`)), ms),
  );
  return Promise.race([promise, timeout]);
}

const order = await withTimeout(fetchOrder(id), 2000); // fail if it takes > 2s

Cancellation with AbortController, the standard way to cancel fetch and many Node APIs:

const controller = new AbortController();
const timer = setTimeout(() => controller.abort(), 2000); // cancel after 2s

try {
  const res = await fetch('https://pricing.internal/quote', {
    signal: controller.signal,      // fetch stops if aborted
  });
  const data = await res.json();
} catch (err) {
  if ((err as Error).name === 'AbortError') console.error('request cancelled');
} finally {
  clearTimeout(timer);              // always clean up the timer
}

The difference between the two: a timeout wrapper makes your code stop waiting, but the underlying work may keep running and finish later (wasting resources). AbortController actually cancels the underlying work (closes the socket, stops the fetch). Prefer real cancellation where the API supports it.

The result-type alternative to throwing

For expected failures (a payment declined, a validation error), some teams return a discriminated union (a Result type, Part 69) instead of throwing, reserving exceptions for truly exceptional situations. Both approaches are valid; the key is consistency.

type Result<T> = { ok: true; value: T } | { ok: false; error: string };

async function charge(amountCents: number): Promise<Result<string>> {
  try {
    const chargeId = await provider.charge(amountCents);
    return { ok: true, value: chargeId };
  } catch (err) {
    return { ok: false, error: (err as Error).message };
  }
}

Practical example — retry with backoff and timeout

Putting it together: call a flaky service with a per-attempt timeout and exponential backoff between attempts. This is the shape of nearly every resilient external call (Part 38 goes deeper).

async function sleep(ms: number) {
  return new Promise((r) => setTimeout(r, ms));
}

async function callWithRetry<T>(
  fn: () => Promise<T>,
  attempts = 3,
  perAttemptMs = 2000,
): Promise<T> {
  let lastError: unknown;
  for (let i = 0; i < attempts; i++) {
    try {
      return await withTimeout(fn(), perAttemptMs);
    } catch (err) {
      lastError = err;
      if (i < attempts - 1) {
        // exponential backoff with jitter: 200ms, 400ms, 800ms (plus randomness)
        await sleep(200 * 2 ** i + Math.random() * 100);
      }
    }
  }
  throw lastError;
}

Production scenario

A checkout endpoint calls a pricing service. One afternoon the pricing service deployed a bad build and started hanging — accepting connections but never responding. The checkout code had no timeout, so every checkout request hung too. Within four minutes, all of checkout's threads and database connections were tied up waiting, and checkout went fully down even though its own code and database were healthy. The post-incident fix was a 1.5-second timeout on the pricing call with a sensible fallback (use the last cached price and flag the order for review). After the fix, a pricing outage degrades one feature for 1.5 seconds per request instead of taking down checkout entirely.

Failure scenario

A search endpoint fired a database query on every keystroke. Users typing fast generated bursts of requests; the late ones returned after the early ones, so results flickered and sometimes showed stale matches for a query the user had already changed. The fix was an AbortController per request: when a new keystroke arrived, the previous in-flight query was aborted, so only the latest query's results ever rendered. Cancellation is not only about saving resources; it is sometimes about correctness.

Edge cases & failure modes

  • No timeout on an external call; one hung dependency cascades into your whole service going down.
  • Timeout without cancellation, so the underlying work keeps running and you waste resources even after giving up.
  • Swallowing errors (an empty catch), hiding failures until they cause a bigger, more confusing problem later.
  • Catching and rethrowing the same error at every level, producing noise with no added context.
  • Not cleaning up timers or listeners in a finally, leaking them.
  • Race conditions from out-of-order responses (the search flicker) when a later-but-stale response overwrites a newer one.

How a Senior Backend Engineer thinks about this

A senior puts a timeout on every call that leaves the process, full stop — the network is never trusted to respond. They prefer real cancellation (AbortController) over bare timeouts so abandoned work actually stops. They distinguish expected failures (declined payment, not found) from unexpected ones (database down) and handle each appropriately — expected failures become clean responses, unexpected ones are logged with context and surfaced as 5xx. They never write an empty catch; an error that is truly safe to ignore gets a comment saying why. And they think about out-of-order responses whenever a client can issue overlapping requests.

Common mistakes

  • No timeout on network calls; the classic cause of cascading outages.
  • Empty catch blocks that swallow errors silently.
  • Treating all errors the same instead of separating expected from unexpected.
  • Not cancelling superseded requests, causing flicker or wasted work.
  • Forgetting clearTimeout/cleanup in finally.

Interview questions

  1. Why must every external call have a timeout? A hung dependency with no timeout makes your requests hang too, exhausting threads and connections until your service goes down — a cascading failure.
  2. What is the difference between a timeout wrapper and AbortController? A timeout wrapper stops your code from waiting but the underlying work may keep running; AbortController actually cancels the underlying operation.
  3. When would you return a Result type instead of throwing? For expected, routine failures (declined payment, validation error) where throwing is heavy-handed; reserve exceptions for exceptional situations. Consistency across the codebase matters most.
  4. What is wrong with an empty catch block? It swallows the error silently, hiding the failure until it causes a larger, harder-to-diagnose problem later.
  5. How do out-of-order async responses cause bugs, and how do you fix them? A slower earlier request can resolve after a newer one and overwrite fresh data; cancel superseded requests with AbortController or ignore stale responses by sequence number.

Acceptance criteria: a hung pricing function never blocks the caller longer than ~3 seconds total, and only the latest call's result is used.

Part 71 — How the Web Works

Before you build a backend, you need a clear picture of what a backend actually does. A backend is a program that sits on a computer somewhere, waits for requests to arrive over the internet, and sends back responses. That is the whole job, at the highest level. Everything else — databases, caches, authentication — is detail in service of that one loop: receive a request, produce a response.

This Part explains the web from the ground up for a beginner: what a client is and what a server is, what the browser does, what an HTTP request and response look like, status codes and headers, URLs, JSON, and what people mean when they say "REST API". Part 4 covers the networking stack (TCP, DNS, TLS) in full depth and Part 8 covers API design as a craft; this Part is the on-ramp, the mental model you need before those make sense. We keep it concrete: every example is a real request you could send with a browser or with curl.

71.1 Client and server

71.1.1 The request-response model

Concept

The web runs on a simple pattern: a client asks, a server answers. The client sends a request; the server sends back a response. That single exchange — one request, one response — is the atom of the web. A web page loading is dozens of these exchanges; using an app is thousands.

The client is whatever makes the request: a web browser, a mobile app, another server, or a tool like Postman or curl. The server is the program that listens for requests and produces responses — that program is your backend.

Why does it exist?

Your data and logic cannot live only on the user's device. If an e-commerce site kept every product and every order on each shopper's phone, no two shoppers would see the same catalog, nobody could place an order anyone else could fulfil, and a lost phone would lose the business. So the shared truth lives on a server, and clients talk to it over the network. The request-response model is the agreed way for millions of clients to safely share one source of truth.

Mental model

Imagine a restaurant with a kitchen behind a serving hatch. You (the client) write your order on a slip and pass it through the hatch (the request). The kitchen (the server) prepares the dish and passes it back (the response). You cannot walk into the kitchen; you can only pass slips and receive plates. Many customers use the same hatch and the same kitchen. The hatch is the network; the slip format is HTTP; the kitchen's rules for which slips it accepts are your API.

How it works

sequenceDiagram
    participant B as Browser
    participant S as Server
    B->>S: GET /products/42 (request)
    S->>S: look up product 42 in the database
    S-->>B: 200 OK + product JSON (response)
    B->>B: render the product on the page
  1. The client builds a request: a method (what it wants to do), a URL (what it wants to act on), headers (extra information), and sometimes a body (data it is sending).
  2. The request travels over the internet to the server (Part 4 explains how — DNS, TCP, TLS).
  3. The server reads the request, does its work (query a database, call another service), and builds a response.
  4. The response travels back: a status code (how it went), headers, and usually a body (the data).
  5. The client uses the response — the browser renders it, the mobile app updates the screen, another server continues its logic.

The connection is usually closed or reused after the exchange, and the server forgets about you. This is what "stateless" means (71.3): each request stands alone and carries everything the server needs to handle it.

Practical example

When you open https://shop.example.com/products/42 in a browser, the browser sends roughly this request:

GET /products/42 HTTP/1.1
Host: shop.example.com
Accept: text/html
User-Agent: Mozilla/5.0 ...

The server responds with roughly:

HTTP/1.1 200 OK
Content-Type: text/html; charset=utf-8
Content-Length: 5120

<!doctype html><html>... the product page ...</html>

That page then triggers more requests — for the stylesheet, the images, and often a call to an API like GET /api/products/42 that returns JSON for the dynamic parts. A single page load can be fifty request-response exchanges.

Production scenario

A product API server handles 3,000 requests per second. Each request is independent: it arrives, the server reads it, queries PostgreSQL, builds a response and sends it, all in a few milliseconds, then forgets about it. Because each request is self-contained, the business can run twenty identical copies of the server behind a load balancer (Part 26), and any copy can handle any request — there is no "your" server that remembers you. This is only possible because of the stateless request-response model.

Edge cases & failure modes

  • The request never arrives (network drops). The client sees a timeout and may retry.
  • The response never arrives even though the server did the work. The client cannot tell "did it fail?" from "did the reply get lost?" — which is exactly why writes need idempotency (Part 18).
  • The server is slow, so the client waits. A client should have a timeout (Part 70).
  • A large body (a big upload or a huge response) takes time and memory; servers stream large bodies rather than loading them whole (Part 3).

How a Senior Backend Engineer thinks about this

A senior keeps the request-response atom in mind constantly, especially its failure mode: the client can never be sure whether a request that got no response actually happened. That single fact drives idempotency keys, retries, and the design of every write endpoint. They also lean on statelessness as the thing that makes horizontal scaling possible — keep the server forgetful between requests, push any shared state into the database or cache, and you can run as many copies as you need.

Common mistakes

  • Assuming a request always reaches the server and a response always comes back; the network loses both.
  • Keeping per-client state in the server's memory, which breaks the moment you run more than one copy.
  • Not setting client timeouts, so a slow server hangs the client.

Interview questions

  1. What is the request-response model? A client sends a request, a server sends back one response; each exchange is independent and self-contained.
  2. Why is statelessness important for scaling? If the server keeps no per-client memory between requests, any copy can handle any request, so you can run many copies behind a load balancer.
  3. Why can't a client be sure a write succeeded if it gets no response? The failure could be before the work (safe to retry) or after the work but the reply was lost (retry would duplicate); this is why writes need idempotency.

Practical exercise

Using curl (or a browser's network tab), make a GET request to any public API and identify in the output: the method, the URL, three request headers, the status code, and three response headers. Acceptance criteria: you can label each part and say in one sentence what it is for.

71.2 HTTP: the language of the web

71.2.1 Requests, methods and URLs

Concept

HTTP (HyperText Transfer Protocol) is the set of rules for how clients and servers phrase requests and responses. It defines the shape of a request (method, URL, headers, body) and a response (status code, headers, body). Almost every backend you build speaks HTTP. Understanding its pieces is understanding the web.

Why does it exist?

Clients and servers are written by different people in different languages on different machines. They need a shared, agreed format so a browser written by one company can talk to a server written by another. HTTP is that shared format — a universal envelope that everyone understands.

Mental model

HTTP is like the format of a physical letter. There is an action on the outside (the method: deliver, return, update), an address (the URL), information on the envelope (the headers: who it is from, what language, how urgent), and the contents inside (the body). The post office (the network) does not care what is inside; it just follows the envelope. A server reads the envelope and the contents and writes a reply in the same format.

How it works — the methods

The HTTP method (also called the verb) says what the client wants to do. The common ones:

Method Means Changes data? Idempotent? Typical use
GET Read something No Yes Fetch a product, a list, a profile
POST Create something, or do an action Yes No Create an order, log in, trigger a job
PUT Replace something entirely Yes Yes Replace a whole resource
PATCH Change part of something Yes Usually Update one field
DELETE Remove something Yes Yes Delete a resource

Two properties in that table matter a lot. "Changes data" (the technical word is "safe" for methods that do not) tells you whether the request is a read or a write; reads can be cached and retried freely. "Idempotent" means doing it twice has the same effect as doing it once. GET, PUT and DELETE are idempotent — deleting an already-deleted thing still ends with it deleted. POST is not — posting the same order twice creates two orders. This is why retrying a lost GET is safe but retrying a lost POST needs care (Part 18).

How it works — the URL

A URL (Uniform Resource Locator) is the address of what the client wants to act on. Its parts:

https://api.shop.example.com:443/v1/products/42?color=red&size=l#reviews
\___/   \____________________/\_/\_____________/\_____________/\______/
scheme        host           port   path          query        fragment
  • Scheme: https (encrypted) or http (not). Always https in production.
  • Host: which server to reach (api.shop.example.com). DNS turns this into an IP address (Part 4).
  • Port: which door on the server (443 for https, 80 for http, often omitted because they are the defaults).
  • Path: which resource (/v1/products/42). This is what your backend routes on.
  • Query string: optional parameters after ?, as key=value pairs joined by &. Used for filtering, pagination, search.
  • Fragment: after #, used only by the browser (to jump to a section); it is never sent to the server.

The path is the heart of API design. /products/42 names "product number 42". /products names the collection. Good APIs use nouns for paths and methods for actions, so GET /products/42 reads product 42 and DELETE /products/42 removes it.

The request body

POST, PUT and PATCH usually carry a body — the data being sent. For APIs the body is almost always JSON (71.4). A GET has no body; its inputs go in the path and query string.

POST /v1/orders HTTP/1.1
Host: api.shop.example.com
Content-Type: application/json
Content-Length: 84

{"items":[{"productId":"42","quantity":2}],"couponCode":"SAVE10"}

Practical example

Here is a small API's endpoints expressed as method-plus-path, the way you will design them:

GET    /v1/products            -> list products (with ?category=&page=)
GET    /v1/products/42         -> get product 42
POST   /v1/products            -> create a product (admin)
PATCH  /v1/products/42         -> update some fields of product 42
DELETE /v1/products/42         -> delete product 42
POST   /v1/orders             -> place an order
GET    /v1/orders/ord_1001    -> get one order

Edge cases & failure modes

  • Using GET to change data (for example GET /deleteUser?id=5) is a classic mistake: search engines and browsers prefetch and cache GETs, so a crawler could delete your data. Reads must be safe; writes must use POST/PUT/PATCH/DELETE.
  • Very long URLs (huge query strings) can be truncated by proxies; there is a practical limit around 2,000 to 8,000 characters. Large inputs belong in a POST body.
  • Query-string injection: query values are user input and must be validated like any other (Part 23).
  • Unencoded characters in a URL (spaces, &, non-ASCII) break parsing; they must be percent-encoded (%20 for a space).

How a Senior Backend Engineer thinks about this

A senior maps each operation to the method whose safety and idempotency match it: reads are GET, creates are POST, full replacements are PUT, partial updates are PATCH, removals are DELETE. They never hide a write behind a GET, because safe methods get retried, prefetched and cached by machinery outside their control. They design paths as nouns and keep them stable, because a URL printed in a mobile app or an integration is a contract that is expensive to change (Part 32 on compatibility).

Common mistakes

  • Changing data with GET, inviting accidental deletions by crawlers and prefetchers.
  • Putting actions in the path (/getProduct, /createOrder) instead of using the method on a noun.
  • Forgetting to percent-encode special characters in URLs.
  • Cramming large data into the query string instead of the body.

Interview questions

  1. What does it mean for an HTTP method to be idempotent, and which methods are? Doing it twice has the same effect as once; GET, PUT, DELETE are idempotent, POST is not. It matters for safe retries.
  2. Why should a read never use POST and a write never use GET? Reads should be safe and cacheable; writes must not be, because GETs are prefetched and cached by browsers, crawlers and proxies, which would trigger the write unexpectedly.
  3. What are the parts of a URL and which part never reaches the server? Scheme, host, port, path, query, fragment; the fragment (after #) stays in the browser.
  4. Where do a GET request's inputs go, versus a POST? GET inputs go in the path and query string; POST inputs go in the body.

Practical exercise

Design the endpoints (method + path) for a simple "notes" API that supports listing notes, getting one note, creating a note, editing a note's text, and deleting a note. Mark which are idempotent. Acceptance criteria: reads use GET, writes use the correct write method, paths are nouns, and no write is hidden behind a GET.

71.3 Responses: status codes and headers

71.3.1 Status codes

Concept

Every HTTP response starts with a three-digit status code that says, at a glance, how the request went. 200 means "OK". 404 means "not found". 500 means "the server broke". The first digit groups them into five families, and knowing those families lets you understand any status code you have never seen.

Why does it exist?

The client needs a fast, standard way to know the outcome without parsing the whole response. A mobile app that gets a 401 knows to prompt for login; one that gets a 429 knows to slow down; one that gets a 503 knows to retry later. Status codes are the shared vocabulary of outcomes, so clients can react correctly without reading English error messages.

Mental model

Status codes are like the response you get when you mail a letter. 2xx is "delivered and handled". 3xx is "the recipient moved; here is the new address". 4xx is "there is something wrong with your letter — wrong address, missing postage, you are not allowed to send this". 5xx is "the post office itself broke". The first digit tells you whose fault it is and what to do next.

How it works — the five families

1xx  Informational   rare; "continue"                     (you can mostly ignore)
2xx  Success         the request worked
3xx  Redirection     go somewhere else for the resource
4xx  Client error    the client did something wrong
5xx  Server error    the server failed

The ones you will use constantly:

Code Name Meaning When your backend sends it
200 OK Success with a body A successful GET or update
201 Created A new resource was created A successful POST that creates something
204 No Content Success, no body A successful DELETE
301 Moved Permanently Resource has a new URL forever Permanent redirects
302 Found Temporary redirect Temporary redirects
304 Not Modified Your cached copy is still good Conditional GET with ETags (Part 4)
400 Bad Request The request is malformed or fails validation Invalid JSON, missing required field
401 Unauthorized You are not authenticated No or invalid login token
403 Forbidden You are authenticated but not allowed A normal user hitting an admin endpoint
404 Not Found The resource does not exist Product id that is not in the database
409 Conflict The request conflicts with current state Duplicate unique value, version conflict
422 Unprocessable Entity Well-formed but semantically invalid Business-rule validation failure
429 Too Many Requests You are being rate-limited Client exceeded its request quota
500 Internal Server Error The server threw an unexpected error An unhandled exception
502 Bad Gateway An upstream server gave a bad response A proxy's backend failed
503 Service Unavailable The server is temporarily down or overloaded Maintenance, overload, failing health check
504 Gateway Timeout An upstream server timed out A downstream dependency hung

The 401-versus-403 distinction trips up beginners. 401 means "I do not know who you are" — log in. 403 means "I know who you are, and you may not do this." The 400-versus-422 distinction: 400 is "I could not even understand your request" (broken JSON); 422 is "I understood it, but it breaks a rule" (ordering a negative quantity).

Practical example

POST /v1/orders           -> 201 Created   (order placed, body has the new order)
GET  /v1/orders/missing   -> 404 Not Found (no such order)
POST /v1/orders (no auth) -> 401 Unauthorized
DELETE /v1/orders/1 (not yours) -> 403 Forbidden
POST /v1/orders (qty: -1) -> 422 Unprocessable Entity (validation)
(server bug)              -> 500 Internal Server Error

Production scenario

A monitoring dashboard watches the ratio of 5xx responses. Normally it sits near zero. One afternoon it spikes to 8 percent, all 503s from one service. Because status codes are standard, the alert fired automatically and the on-call engineer immediately knew the server was failing (5xx = server's fault), not that clients were sending bad requests (which would be 4xx). The clear separation of "client's fault" (4xx) from "server's fault" (5xx) is what makes this kind of automatic alerting possible, and it is why returning the correct code matters operationally, not just aesthetically.

Failure scenario

An API returned 200 OK with a body like {"error": "not found"} for everything, including failures. The mobile app could not tell success from failure without parsing the body, caches stored error responses as if they were real data, and the monitoring dashboard showed a perfect 5xx rate of zero while users were seeing constant errors. A whole outage went undetected for an hour because the status codes lied. The fix — return 404, 422, 500 correctly — made the errors visible to every layer that speaks HTTP. The lesson: the status code is not decoration; infrastructure depends on it being honest.

Edge cases & failure modes

  • Returning 200 for errors (the lie above) breaks caching, monitoring and client logic.
  • Returning 500 for a client's bad input pages the on-call for what is actually a 400; separate client faults from server faults.
  • Returning 404 versus 403 for a resource the user may not see: sometimes 404 is deliberately used to avoid revealing that a resource exists (Part 23).
  • Retrying 4xx is usually pointless (the request is wrong and will stay wrong); retrying 5xx and 429 can help (the server may recover).

How a Senior Backend Engineer thinks about this

A senior is precise with status codes because machines, not just humans, read them: load balancers route on them, caches decide what to store by them, clients decide whether to retry by them, and dashboards alert on them. They keep the discipline that 5xx means "our bug or outage" and 4xx means "the caller's mistake", so the 5xx rate is a clean signal of system health. They also return a consistent error body shape alongside the code (Part 8), so clients get both a machine-readable status and a human-readable reason.

Common mistakes

  • Returning 200 with an error in the body.
  • Using 500 for validation failures, which should be 400 or 422.
  • Mixing up 401 (not authenticated) and 403 (not allowed).
  • Retrying 4xx responses, which will keep failing.

Interview questions

  1. What is the difference between the 4xx and 5xx families? 4xx is the client's fault (bad request); 5xx is the server's fault (it failed). This split drives monitoring, alerting and retry decisions.
  2. 401 vs 403? 401 means not authenticated (who are you?); 403 means authenticated but not permitted.
  3. 400 vs 422? 400 means the request could not be understood (malformed); 422 means it was understood but violates a rule.
  4. Which status codes are worth retrying? 5xx and 429 (the server may recover; back off first); 4xx generally not, because the request itself is wrong.

Practical exercise

For a "create order" endpoint, list the status code you would return for each of: success, missing auth token, a normal user trying to create an order for another user, an unknown product id, a negative quantity, and an unexpected database error. Acceptance criteria: each maps to the correct code and you can justify the 400-vs-422 and 401-vs-403 choices.

71.3.2 Headers

Concept

Headers are key-value pairs attached to a request or response that carry information about the message rather than the message itself. "What format is the body?" "Who is sending this?" "Is the client allowed to cache this?" "Here is my authentication token." Headers answer all of these.

Why does it exist?

The body carries the data; everything else the client and server need to know about that data has to live somewhere. Headers are that somewhere — metadata that both sides understand without it polluting the actual content. Authentication, content type, caching, compression, language and dozens of other concerns are negotiated through headers.

How it works — the headers you will meet most

Header On Purpose
Content-Type both What format the body is (application/json, text/html, image/png)
Content-Length both Size of the body in bytes
Authorization request Credentials, usually Bearer <token> (Part 21)
Accept request What formats the client can handle in the response
Accept-Encoding request Compression the client supports (gzip, br)
Content-Encoding response How the body is compressed
Cache-Control response Whether and how long to cache (Part 4, Part 16)
ETag response A version fingerprint for conditional requests
Set-Cookie response Tells the browser to store a cookie
Cookie request Sends stored cookies back
Location response Where to go, on a 201 (new resource) or 3xx (redirect)
X-Request-Id both A trace id to follow one request across services (Part 35)

Content-Type is the one you must always get right. When your API returns JSON, it must send Content-Type: application/json, or clients may misinterpret the bytes. When a client sends a JSON body, it must send the same header, or your server may not parse it.

Practical example

A request with headers and the matching response:

POST /v1/orders HTTP/1.1
Host: api.shop.example.com
Authorization: Bearer eyJhbGci...        <- who the client is
Content-Type: application/json            <- the body is JSON
Accept: application/json                   <- send me JSON back
Accept-Encoding: gzip                      <- I can decompress gzip
X-Request-Id: 7f3c-...                      <- trace id

{"items":[{"productId":"42","quantity":2}]}
HTTP/1.1 201 Created
Content-Type: application/json
Content-Encoding: gzip                      <- the body is gzipped
Location: /v1/orders/ord_1001               <- the new order's URL
Cache-Control: no-store                     <- do not cache this
X-Request-Id: 7f3c-...                       <- same trace id echoed back

{"id":"ord_1001","status":"pending","totalCents":2000}

Edge cases & failure modes

  • Wrong or missing Content-Type so JSON is treated as plain text and parsing fails.
  • Trusting client-supplied headers (like a X-User-Id the client sets) for security decisions; clients can send any header, so authentication must come from a verified token, not a self-declared header (Part 23).
  • Huge or many headers can be rejected by proxies (there are size limits around 8 KB total).
  • Case and duplicates: header names are case-insensitive; some headers can appear more than once.
  • Leaking information in headers (server version, stack details) helps attackers; strip revealing headers in production.

How a Senior Backend Engineer thinks about this

A senior treats headers as a contract and a security surface at once. They always set Content-Type correctly, always propagate a request-id header for tracing across services, and never trust a client-set header for anything that matters — identity and permissions come from a verified token, period. They use Cache-Control deliberately (a private, user-specific response must be no-store; a public, shareable one can be cached), because a wrong cache header either leaks one user's data to another or wastes a caching opportunity (Part 16).

Common mistakes

  • Forgetting Content-Type: application/json, breaking clients and parsers.
  • Trusting a client-provided header (X-User-Id, X-Role) for authorization.
  • Caching a user-specific response because of a loose Cache-Control, leaking data across users.
  • Leaking server internals through verbose headers.

Interview questions

  1. What is the role of the Content-Type header? It tells the receiver what format the body is in, so it can parse it correctly; JSON APIs must set application/json.
  2. Why must you never trust a client-set header for authorization? Clients can send any header value, so a self-declared X-User-Id or X-Role is forgeable; identity must come from a server-verified token.
  3. Where does the authentication token usually go, and in what format? In the Authorization request header, typically as Bearer <token>.
  4. Why propagate an X-Request-Id header? To trace a single request across multiple services and logs, which is essential for debugging distributed systems (Part 35).

Practical exercise

Inspect the headers of a real API response in your browser's network tab. Identify the Content-Type, any caching header, and whether the response sets a cookie. Then explain why a response containing your personal account data should have Cache-Control: no-store. Acceptance criteria: you can read the headers and justify the caching choice for private data.

71.4 JSON: the data format of APIs

71.4.1 What JSON is and how to use it safely

Concept

JSON (JavaScript Object Notation) is a text format for structured data. It looks like JavaScript objects and arrays — curly braces for objects, square brackets for arrays, with strings, numbers, booleans and null. It is the format almost every modern API uses for request and response bodies, because it is human-readable, compact enough, and supported by every programming language.

Why does it exist?

A server written in TypeScript needs to send data to a mobile app written in Swift or Kotlin, or to a browser, or to another server written in Go. They need a shared text format that all of them can produce and parse. JSON won that role because it is simple, maps cleanly onto the basic data types every language has, and is easy for humans to read when debugging.

How it works

{
  "id": "ord_1001",
  "status": "pending",
  "totalCents": 2000,
  "paid": false,
  "shippedAt": null,
  "items": [
    { "productId": "42", "quantity": 2 },
    { "productId": "99", "quantity": 1 }
  ],
  "customer": { "id": "usr_7", "email": "alice@example.com" }
}

The allowed value types are: string (double quotes only — single quotes are invalid JSON), number, boolean (true/false), null, object ({}), and array ([]). That is the whole list. Notably missing: dates (sent as strings, usually ISO 8601 like "2026-11-04T09:30:00Z"), comments (not allowed), and undefined (not a JSON value).

In JavaScript and TypeScript you convert between JSON text and objects with two built-in functions:

// Object -> JSON text (for sending in a response or request body)
const order = { id: 'ord_1001', totalCents: 2000 };
const text = JSON.stringify(order);   // '{"id":"ord_1001","totalCents":2000}'

// JSON text -> object (for reading a request body or a file)
const parsed = JSON.parse(text);      // { id: 'ord_1001', totalCents: 2000 }

Practical example — parsing untrusted input safely

Here is the single most important JSON habit for a backend engineer: data parsed from the outside world is unknown and must be validated before you trust it. JSON.parse tells you the text was valid JSON; it does not tell you the data has the shape you expect.

function parseOrderRequest(bodyText: string): { productId: string; quantity: number } {
  let raw: unknown;
  try {
    raw = JSON.parse(bodyText);           // throws on malformed JSON -> 400
  } catch {
    throw new Error('body is not valid JSON');
  }
  // Validate the shape; do not trust it just because it parsed.
  if (
    typeof raw !== 'object' || raw === null ||
    typeof (raw as any).productId !== 'string' ||
    typeof (raw as any).quantity !== 'number' ||
    !Number.isInteger((raw as any).quantity) ||
    (raw as any).quantity <= 0
  ) {
    throw new Error('invalid order: productId (string) and positive integer quantity required');
  }
  return { productId: (raw as any).productId, quantity: (raw as any).quantity };
}

In a real NestJS backend you do not write this by hand — you use DTOs with class-validator (Part 74), which does exactly this validation declaratively. But understanding what the framework does for you is the point: parse, then validate, then trust.

Edge cases & failure modes

  • Malformed JSON from a client throws on JSON.parse; catch it and return 400, do not let it crash the request.
  • Valid JSON, wrong shape (missing fields, wrong types) parses fine but is invalid for your purpose; you must validate separately.
  • Numbers losing precision: JSON numbers are floating-point, so a huge integer id (a 64-bit database id) can lose precision. Send such ids as strings.
  • JSON.stringify drops undefined and functions and turns Date into an ISO string; parsing it back gives you a string, not a Date, which surprises people.
  • Deeply nested or huge JSON can be slow to parse and can be used as a denial-of-service (a 50 MB body, or an object nested 100,000 levels deep); limit body size at the gateway (Part 23).
  • Circular references (an object that contains itself) make JSON.stringify throw.

How a Senior Backend Engineer thinks about this

A senior treats every incoming JSON body as hostile until validated: parse it (catching malformed input as a 400), then validate its shape and values against a schema before a single field reaches business logic. They cap body size to stop oversized-payload attacks. They send large integer ids as strings to avoid precision loss. They know JSON.stringify loses undefined, functions and Date types, so they map domain objects to explicit response shapes (Part 69) rather than stringifying raw internal objects, which both fixes the type issues and prevents leaking internal fields.

Common mistakes

  • Trusting parsed JSON without validating its shape ("it parsed, so it must be fine").
  • Letting JSON.parse throw crash the request instead of returning 400.
  • Sending 64-bit ids as JSON numbers and losing precision.
  • Expecting a Date back after JSON.parse (you get a string).
  • No body-size limit, allowing huge-payload denial-of-service.

Interview questions

  1. What value types does JSON support? String (double-quoted), number, boolean, null, object, array. No dates (sent as strings), no comments, no undefined.
  2. Why must you validate JSON after parsing it? JSON.parse only confirms the text is valid JSON, not that the data has the expected fields and types; untrusted input must be validated before use.
  3. Why might a large integer id be wrong after a round-trip through JSON? JSON numbers are floating-point, so integers beyond ~9 quadrillion lose precision; send them as strings.
  4. What happens to a Date and to undefined when you JSON.stringify and JSON.parse? A Date becomes an ISO string and does not come back as a Date; undefined properties are dropped entirely.

Practical exercise

Write safeParse(text) that returns a discriminated union { ok: true, value } | { ok: false, error }, returning an error for malformed JSON instead of throwing. Then extend it to validate that the parsed value is an object with a string email and a positive integer quantity. Acceptance criteria: malformed JSON, a non-object, and a valid-JSON-but-wrong-shape input each return a clear { ok: false } with a useful message.

71.5 REST APIs

71.5.1 What a REST API is

Concept

A REST API is a style of building web APIs where you expose your data as resources (nouns like products, orders, users), each with a URL, and you act on them with the standard HTTP methods (GET to read, POST to create, PATCH to update, DELETE to remove). "REST" stands for Representational State Transfer, but for a beginner the useful definition is simpler: an API organized around nouns and the HTTP methods, speaking JSON, using status codes honestly, and keeping each request self-contained.

Why does it exist?

Before REST became the common style, every API invented its own conventions, so learning one taught you nothing about the next. REST is a set of conventions widely enough agreed that a developer who has used one REST API can guess how another works: GET /things lists, GET /things/5 fetches one, POST /things creates, and the status codes mean what they always mean. That predictability is the value. Part 8 covers REST design as a craft and Part 61 covers the alternatives (GraphQL, gRPC) and when they win; here we establish the baseline.

Mental model

A REST API is like a well-organized library with a strict filing system. Every book (resource) has a shelf location (URL). The actions are standardized: borrow (GET), add a new book (POST), update a record (PATCH), remove a book (DELETE). Because every library uses the same system, once you know it you can walk into any branch and find your way. REST is that shared filing system for data over HTTP.

How it works — the resource pattern

The core idea is: pick your nouns, give each a URL for the collection and for an individual item, and use the methods consistently.

Collection URL:  /v1/products
Item URL:        /v1/products/42

GET    /v1/products       -> list products        (200, array of products)
POST   /v1/products       -> create a product     (201, the new product + Location header)
GET    /v1/products/42    -> get product 42        (200 product, or 404)
PUT    /v1/products/42    -> replace product 42    (200, or 404)
PATCH  /v1/products/42    -> update some fields     (200, or 404)
DELETE /v1/products/42    -> delete product 42      (204, or 404)

Relationships become nested paths:

GET    /v1/orders/ord_1/items        -> the items in order ord_1
POST   /v1/orders/ord_1/items        -> add an item to order ord_1
GET    /v1/users/usr_7/orders        -> that user's orders

Filtering, sorting and pagination go in the query string, never in the path:

GET /v1/products?category=dental&sort=price&page=2&limit=20
GET /v1/orders?status=paid&from=2026-01-01&to=2026-01-31

Pagination

A list endpoint must never return "all" rows — a GET /orders on a table with ten million rows would try to send ten million objects and fall over. Lists are paginated. The two common styles:

Offset pagination:  ?page=2&limit=20   (simple; slow and unstable deep in large tables)
Cursor pagination:  ?cursor=eyJ...&limit=20  (stable and fast; the professional default)

Part 8 covers why cursor pagination is preferred for large tables; for now, remember that every list endpoint is paginated and returns a bounded page plus a way to get the next one.

Practical example — a consistent response shape

A small but important discipline: make your responses predictable. A single resource returns the object; a list returns a page object with the items and pagination info; an error returns a consistent error shape.

// GET /v1/products/42
{ "id": "42", "name": "Dental Mirror", "priceCents": 1299 }

// GET /v1/products?limit=2
{
  "items": [
    { "id": "42", "name": "Dental Mirror", "priceCents": 1299 },
    { "id": "43", "name": "Probe", "priceCents": 899 }
  ],
  "nextCursor": "eyJpZCI6IjQzIn0",
  "total": 1284
}

// Any error
{
  "error": { "code": "not_found", "message": "Product 999 not found" }
}

Production scenario

A company's mobile app, website, and a partner integration all talk to the same REST API. Because the API follows REST conventions, the mobile team, the web team and the partner each understood it from the endpoint list alone, with minimal hand-holding. When the company added a new "wishlists" feature, they added GET/POST /v1/wishlists and GET /v1/users/{id}/wishlists following the same pattern, and every consumer immediately knew how to use it. The consistency is what let three independent teams move fast against one API.

Failure scenario

An early API grew without conventions: POST /getProducts, GET /product_delete?id=5, some endpoints returning {data: ...} and others returning the object directly, errors sometimes 200 with an error body and sometimes 500. Every new integration took weeks because nothing was predictable, a crawler that prefetched GET /product_delete?id=5 links deleted products, and the client code was full of special cases. Refactoring to consistent REST conventions — nouns, correct methods, honest status codes, one response shape — cut integration time from weeks to a day and ended the accidental deletions. The lesson: conventions are not pedantry; they are what makes an API usable and safe.

Edge cases & failure modes

  • Verbs in the path (/createOrder) instead of methods on nouns; works, but throws away the conventions that make REST valuable.
  • Unbounded lists with no pagination, which fall over on large tables.
  • Inconsistent response shapes across endpoints, forcing clients into special cases.
  • Actions that are not CRUD (create/read/update/delete) — like "refund an order" or "send a password reset" — do not fit neatly; model them as a sub-resource (POST /orders/1/refunds) or accept a pragmatic action endpoint. Dogmatic REST is not the goal; a usable, consistent API is.
  • Breaking changes: once published, a URL and its response shape are a contract; changing them breaks every consumer (Part 32 on versioning and compatibility).

How a Senior Backend Engineer thinks about this

A senior uses REST as a strong default because its predictability lowers the cost for everyone who consumes the API, but they are not dogmatic — when an operation is genuinely an action rather than a CRUD operation, they model it pragmatically rather than contorting it. They paginate every list from day one, keep response shapes consistent, use status codes honestly, and treat every published endpoint as a long-lived contract. They also know when REST is the wrong tool: a mobile app that needs to fetch deeply nested data in one round trip may be better served by GraphQL, and internal service-to-service calls may be better as gRPC (Part 61).

Common mistakes

  • Verbs in paths instead of methods on nouns.
  • List endpoints with no pagination.
  • Inconsistent response and error shapes.
  • Changing a published URL or response shape and breaking consumers.
  • Forcing every operation into strict CRUD even when it is awkward.

Interview questions

  1. What makes an API "RESTful" in practical terms? Resources as nouns with URLs, standard HTTP methods for actions, JSON bodies, honest status codes, consistent shapes, and self-contained (stateless) requests.
  2. How do you handle filtering and pagination in REST? In the query string (?status=paid&limit=20&cursor=...), never in the path; every list is paginated.
  3. How would you model "refund an order" in a REST API? As a sub-resource action, for example POST /orders/{id}/refunds, since a refund is a thing you create against an order.
  4. Why is a published URL a contract, and what does that imply? Clients (apps, integrations) depend on it; changing it breaks them, so changes must be backward-compatible or versioned (Part 32).

Practical exercise

Design a REST API for a food-delivery service covering restaurants, menus, orders and order status. Include collection and item URLs, the correct methods, how to filter restaurants by cuisine and location, how to paginate, and how to model "mark an order as delivered". Acceptance criteria: nouns in paths, correct methods and status codes, pagination on every list, and a sensible model for the status-change action.

71.6 What the browser does

71.6.1 From URL to rendered page, and why the backend engineer cares

Concept

When a user types a URL and presses enter, the browser does a surprising amount of work: it resolves the domain to an address, opens a secure connection, sends an HTTP request, receives HTML, and then fetches everything that HTML references (styles, scripts, images, and API data), running JavaScript that may send still more requests. A backend engineer does not need to render pages, but they need to understand this flow, because it explains where their API fits and why certain things (CORS, caching, cookies) behave the way they do.

Why does it exist?

A web page is not one file; it is a document that pulls in many resources from potentially many servers. The browser orchestrates all of that. Understanding it tells you why a single page view produces dozens of requests to your backend, why a browser enforces rules (CORS) that Postman does not, and why your API's caching and cookie headers matter.

Mental model

The browser is a general contractor building a house from a blueprint. It gets the blueprint (the HTML), reads it, and realizes it needs materials from various suppliers: the paint supplier (CSS), the electrician (JavaScript), the furniture store (images), and the data from your backend (JSON via API calls). It places all those orders, often in parallel, assembles everything into the finished house (the rendered page), and keeps calling suppliers as the occupants use the house (more API calls as the user clicks).

How it works

sequenceDiagram
    participant U as User
    participant Br as Browser
    participant DNS as DNS
    participant Web as Web server
    participant API as Your API

    U->>Br: type shop.example.com, press enter
    Br->>DNS: what IP is shop.example.com?
    DNS-->>Br: 203.0.113.10
    Br->>Web: GET / (over HTTPS)
    Web-->>Br: 200 OK, HTML document
    Br->>Web: GET /styles.css, /app.js, /logo.png (parallel)
    Web-->>Br: the assets
    Br->>Br: run app.js
    Br->>API: GET /v1/products (fetch, with cookie/token)
    API-->>Br: 200 OK, products JSON
    Br->>Br: render products into the page
  1. DNS lookup: turn the domain name into an IP address (Part 4).
  2. Connect and TLS: open a TCP connection and set up encryption (Part 4).
  3. Request the document: GET /, receive HTML.
  4. Fetch sub-resources: the browser parses the HTML and requests the CSS, JavaScript, fonts and images it references, in parallel.
  5. Run JavaScript: modern apps then call your API (via fetch) to get the dynamic data as JSON and render it.
  6. Keep going: as the user interacts, the JavaScript sends more API requests.

For a backend engineer, steps 5 and 6 are where your work lives: the browser's JavaScript calls your API, your API returns JSON, and the browser renders it.

CORS: the rule that confuses every beginner

Browsers enforce a security rule called the same-origin policy: JavaScript running on shop.example.com cannot, by default, read responses from api.other.com. This stops a malicious site from using your logged-in browser to read your bank's API. CORS (Cross-Origin Resource Sharing) is how a server opts in to allowing specific other origins to call it: the server sends headers like Access-Control-Allow-Origin: https://shop.example.com, and the browser then permits the call.

The key insight for a beginner: CORS is enforced by the browser, for browser JavaScript only. A request from Postman, curl, or another server is not subject to CORS — those are not browsers. So "it works in Postman but fails in the browser with a CORS error" is extremely common and means exactly one thing: your server is not sending the CORS headers the browser requires. The fix is on the server (allow the frontend's origin), not in the frontend. NestJS enables CORS with one line (Part 74).

Cookies and tokens

The browser stores cookies the server sets (via Set-Cookie) and automatically attaches them to future requests to that domain (via Cookie). This is how a server remembers a logged-in session across the stateless request-response model. Modern APIs often use a token in the Authorization header instead (Part 21). Either way, the thing the backend engineer must know: the browser handles cookies automatically, which is convenient but also why cookie security settings (HttpOnly, Secure, SameSite) matter (Part 23).

Practical example — why a page is slow

A product page loads slowly. The network tab shows the browser made 60 requests: the HTML, 8 scripts, 12 images, 3 fonts, and 36 separate API calls (one per product in a list, the "N+1 over the network" problem). The backend engineer's fix is to add a single GET /v1/products?ids=... batch endpoint so the browser makes one API call instead of 36. Understanding what the browser does — that it makes a request per resource unless told otherwise — is what lets the backend engineer see and fix the problem.

Edge cases & failure modes

  • CORS errors when a frontend on one origin calls an API on another and the server has not allowed that origin.
  • Mixed content: an HTTPS page calling an HTTP API is blocked by the browser; everything must be HTTPS.
  • Too many requests (N+1 over the network) making pages slow; batch endpoints fix it.
  • Caching surprises: the browser caches responses per Cache-Control; a wrong header serves stale data or re-fetches needlessly.
  • Cookies not sent cross-origin unless the request uses credentials: 'include' and the server allows it, a common authentication-in-the-browser gotcha.

How a Senior Backend Engineer thinks about this

A senior understands the browser well enough to design APIs that serve it well: batch endpoints to avoid N+1 network calls, correct Cache-Control so the browser caches what it safely can, correct CORS configuration so the frontend can call the API, and secure cookie settings. They recognize the "works in Postman, fails in the browser" symptom instantly as CORS and fix it on the server. They know the browser is both a consumer of their API and an enforcer of security rules (same-origin, mixed-content) that server-to-server callers do not have, so an API consumed by browsers has extra requirements.

Common mistakes

  • Debugging a CORS error in the frontend when the fix is server-side CORS headers.
  • Serving user-specific API responses with a cacheable Cache-Control, letting the browser cache private data.
  • Designing APIs that force the browser into dozens of calls per page.
  • Mixing HTTP and HTTPS and being blocked by the browser.

Interview questions

  1. What is CORS and where is it enforced? A browser security mechanism where a server opts in to allowing specific other origins to read its responses; it is enforced by the browser for browser JavaScript, not for Postman, curl or server-to-server calls.
  2. Why does an API call work in Postman but fail with a CORS error in the browser? Postman is not a browser and ignores CORS; the browser requires the server to send allow-origin headers, which it is not. Fix it on the server.
  3. How does a stateless server remember a logged-in user across requests? Via cookies the browser stores and resends, or a token the client sends in the Authorization header; the server verifies it each request.
  4. What is the N+1 problem over the network and how do you fix it from the backend? A page making one API call per item instead of one call for all; add a batch endpoint that returns many items at once.

Practical exercise

Open any web app's network tab and count the requests one page load makes. Identify the HTML document, at least one CSS and JavaScript request, and at least one API (JSON) call. Then find one place where the page makes several similar API calls that a batch endpoint could collapse into one. Acceptance criteria: you can describe the full load as request-response exchanges and propose one batching improvement.

Part 72 — Linux and the Command Line

Your code runs on Linux. Not on your laptop's friendly desktop, but on a Linux server in a data center, inside a container, reached over a text-only connection. When your backend misbehaves at 2 a.m., you will not click buttons to fix it; you will type commands into a terminal. The command line is where backend engineers actually live, and fluency in it is the difference between an engineer who can only write code and one who can run, inspect and repair a production system.

This Part teaches the Linux command line from the beginning, aimed squarely at what a backend developer needs: the shell and the filesystem, navigation, permissions, processes, pipes and redirection, environment variables, package managers, and the SSH basics for reaching a remote server. We do not cover system administration in depth; we cover the commands you will reach for every day and the mental models that make them stick. Part 3 covers processes, threads and signals at the operating-system level; this Part is the practical, hands-on layer.

A note on terms. "The shell" is the program that reads your commands and runs them — on most systems that is bash or zsh. "The terminal" is the window the shell runs in. "The command line" is the general idea of typing commands. We use them loosely, as everyone does.

72.1 The shell and the filesystem

72.1.1 What the shell is

Concept

The shell is a program that waits for you to type a command, runs it, shows the output, and waits again. It is a text-based way to tell the computer to do things: list files, run programs, start your server, read logs. Every command follows the same shape — the name of a program, then options and arguments — and learning the shell is mostly learning that shape and a few dozen programs.

Why does it exist?

A graphical interface shows you a fixed set of buttons someone decided to build. A shell lets you run any program, combine programs, repeat commands, automate them in scripts, and do all of it over a text-only remote connection to a server that has no screen. Servers have no desktop; the shell is the only interface they offer. It is also faster for an expert: typing grep error app.log finds every error line instantly, with no mouse, no scrolling.

Mental model

The shell is a conversation with the computer in a tiny, precise language. You say a sentence (a command), it does the thing and replies. The "words" are programs; the "grammar" is options and arguments and the pipes that join commands together. Like any language, the first hundred words feel awkward and then become automatic. Unlike a human language, it is unforgiving: a space in the wrong place or a wrong character changes the meaning completely, so precision matters.

How it works

A command has three parts:

command   -options   arguments
ls        -l         /var/log
  • The command is the program to run (ls, the "list" program).
  • Options (also called flags) modify behavior, usually starting with - (-l means "long format"). Short options can combine: -la is -l -a. Long options use -- (--all).
  • Arguments are what the command acts on (/var/log, a directory to list).

The shell prints a prompt (often ending in $) and waits. You type a command, press Enter, it runs, output appears, and you get a new prompt. The prompt usually shows your username, the machine, and the current directory, so you always know where you are and who you are.

alice@web-prod-1:/var/www/app$ ls -l
# ^user  ^machine    ^current directory  ^the command you typed

Getting help

Three ways to learn any command, which you will use constantly:

man ls            # the full manual page (press q to quit, / to search)
ls --help         # a shorter usage summary
tldr ls           # community examples, if the 'tldr' tool is installed

When you do not know a command, man is the answer. Nobody memorizes every option; they look them up.

Practical example

A first session a backend developer might run on logging into a server:

whoami            # which user am I? -> alice
hostname          # which machine am I on? -> web-prod-1
pwd               # where am I? -> /home/alice
date              # what time does the server think it is? (time zones matter)
uptime            # how long has the server been up, and how loaded is it?

Each is one word, each answers one question. This is the texture of command-line work: small precise questions, immediate answers.

How a Senior Backend Engineer thinks about this

A senior is fluent enough in the shell that it disappears — they think about the problem, not the typing. They always know three things before acting on a server: who they are (whoami), where they are (pwd), and which machine they are on (hostname), because running the right command on the wrong server or as the wrong user is how accidents happen. They reach for man and --help without shame, because the mark of expertise is knowing what to look up, not memorizing everything. They treat the production shell with respect: a command that would be harmless on a laptop can be an incident on a production server.

Common mistakes

  • Running a command on the wrong server because you did not check hostname.
  • Running as root (the all-powerful user) when a normal user would do, so a typo becomes a disaster.
  • Not reading man/--help and guessing at options.
  • Copy-pasting commands from the internet without understanding them (especially destructive ones).

Interview questions

  1. What is the difference between the shell, the terminal and the command line? The shell is the program interpreting commands (bash/zsh); the terminal is the window it runs in; the command line is the general concept. (Beginner-level; the point is clarity of terms.)
  2. How do you find out what a command does and its options? man command, command --help, or tldr command.
  3. Why always check who and where you are before acting on a server? Running the right command on the wrong host or as the wrong user turns a routine action into an incident.

Practical exercise

Open a terminal and, using only the commands above, answer: your username, your machine's hostname, your current directory, the current server time, and how long the machine has been up. Then open the manual page for ls, find what the -h option does, and quit the manual. Acceptance criteria: you can state what ls -lh would show differently from ls -l.

72.1.2 The filesystem and navigating it

Concept

Linux organizes everything into a single tree of directories (folders) starting from the root, written /. Every file and directory has a path describing where it sits in that tree. Navigating the filesystem — knowing where you are, moving around, and listing what is there — is the most basic command-line skill and the foundation of everything else.

Why does it exist?

Your code, its configuration, its logs, and the system's own files all live somewhere in the filesystem. To run your server you must be in or point to the right directory; to read logs you must find the log directory; to fix a config you must locate the config file. The filesystem is the map, and paths are the addresses.

Mental model

The filesystem is a tree, or like a set of nested folders. The root / is the trunk. Branches lead to directories like /home (users' files), /var (variable data like logs), /etc (configuration), /usr (installed programs). Your current position in this tree is the "working directory", like standing in one room of a large building. A path is directions to a room: either from the entrance (an absolute path starting with /) or from where you are standing (a relative path).

How it works

/                          the root of everything
├── home/
│   └── alice/             your home directory, shortcut: ~
│       └── app/
│           ├── src/
│           └── package.json
├── etc/                   system configuration files
├── var/
│   └── log/               log files live here
├── usr/                   installed programs and libraries
└── tmp/                   temporary files (cleared on reboot)

The navigation commands:

pwd                 # print working directory: where am I?
ls                  # list files in the current directory
ls -la              # list all (including hidden) in long format
cd /var/log         # change directory to an absolute path
cd app              # change into the 'app' subdirectory (relative)
cd ..               # go up one level to the parent
cd ~                # go to your home directory
cd -                # go back to the previous directory

Paths come in two kinds:

  • Absolute paths start from root: /home/alice/app/src. They mean the same thing no matter where you are.
  • Relative paths start from the current directory: src/index.ts, ../config. . means "here", .. means "the parent", ~ means "my home directory".

Hidden files start with a dot (.env, .gitignore) and do not show in a plain ls; use ls -a to see them. Backend configuration often lives in hidden files, so this matters.

Reading files

cat app.log           # print the whole file (fine for small files)
less app.log          # page through a large file (q to quit, / to search)
head -n 20 app.log    # first 20 lines
tail -n 20 app.log    # last 20 lines
tail -f app.log       # follow: show new lines as they are written (live logs!)

tail -f is one you will use constantly — it streams a log file live, so you watch your server's output as it happens. For a huge log, less lets you page and search without loading it all; never cat a multi-gigabyte log file, because it dumps the whole thing to your screen.

Creating, moving, copying, deleting

mkdir logs            # make a directory
mkdir -p a/b/c        # make nested directories, creating parents as needed
touch notes.txt       # create an empty file (or update its timestamp)
cp a.txt b.txt        # copy
cp -r src backup      # copy a directory and its contents (-r = recursive)
mv old.txt new.txt    # move or rename
rm notes.txt          # delete a file
rm -r backup          # delete a directory and everything in it

Edge cases & failure modes

  • rm -rf is irreversible and has no trash. rm -rf / or rm -rf $VAR/ where $VAR is empty has destroyed whole systems. There is no undo. Double-check every rm -rf, especially with variables or wildcards.
  • Spaces in filenames break commands unless quoted: rm my file.txt tries to delete two files; use rm "my file.txt".
  • Wildcards expand before the command runs: rm *.log deletes all .log files; rm * .log (stray space) deletes everything in the directory. A space changes the meaning entirely.
  • Hidden files are missed by ls and by cp * (which skips dotfiles), so a backup can silently omit .env.
  • Relative paths depend on where you are, so a script using relative paths breaks if run from a different directory.

How a Senior Backend Engineer thinks about this

A senior treats destructive commands (rm -rf, mv over an existing file) with deliberate caution, especially when variables or wildcards are involved, because there is no recycle bin on a server. They prefer absolute paths in scripts so behavior does not depend on the current directory. They know where things live by convention — logs in /var/log, config in /etc, their app in /home or /opt or /var/www — so they can find their way on any Linux box. They use tail -f to watch live logs and less to search large ones, never cat on a huge file.

Common mistakes

  • rm -rf with a wildcard or an empty variable, deleting far more than intended.
  • Forgetting to quote filenames with spaces.
  • Using relative paths in scripts that then break when run from elsewhere.
  • cat-ing a huge log file and flooding the terminal.
  • Backing up with cp * and silently missing hidden files like .env.

Interview questions

  1. What is the difference between an absolute and a relative path? Absolute starts from / and is location-independent; relative starts from the current directory (., .., no leading slash).
  2. How do you watch a log file update live? tail -f file; for searching a large file, less.
  3. Why is rm -rf dangerous and how do you use it safely? It deletes recursively with no undo and no trash; double-check the exact path, avoid empty variables and stray spaces in wildcards, and prefer explicit paths.
  4. Why might a backup made with cp * be incomplete? Wildcard expansion skips hidden dotfiles like .env; use cp -r on the directory or include dotfiles explicitly.

Practical exercise

Create a directory ~/practice, inside it create src/ and logs/, create an empty .env file and a README.md, list all files including hidden ones, copy src/ to a backup/, then rename README.md to NOTES.md. Finally, confirm the .env file exists with ls -a. Acceptance criteria: you use both absolute and relative paths at least once, and you can explain why a plain ls did not show .env.

72.2 Permissions

72.2.1 Users, groups and file permissions

Concept

Linux controls who can read, change and run each file through permissions. Every file has an owner, a group, and three sets of permissions — for the owner, for the group, and for everyone else — each granting read, write and/or execute. This is why you sometimes get "Permission denied" and why servers are secure: not everyone can touch everything.

Why does it exist?

A server runs many programs for many purposes. You do not want your web application able to read every user's private files, or a compromised process able to rewrite system configuration. Permissions enforce the principle that each user and program can touch only what it needs. They are the first and most basic layer of security on a Linux system.

Mental model

Think of each file as a room with three kinds of visitor: the owner (you), members of a group (your team), and the general public (everyone else). For each kind, the room can allow looking (read), rearranging (write), or entering to use it (execute). Permissions are the sign on the door saying which visitors may do which of those three things.

How it works

Run ls -l and the first column shows the permissions:

-rwxr-xr--  1 alice  devs  4096 Nov  4 09:30 deploy.sh
 \_/\_/\_/
  |  |  └── others: r-- (read only)
  |  └───── group (devs): r-x (read + execute)
  └──────── owner (alice): rwx (read + write + execute)
first char: - file, d directory, l symbolic link

Each triple is r (read), w (write), x (execute), or - if not granted. Read lets you see the contents; write lets you change them; execute lets you run the file as a program (for a directory, execute means "enter it").

Permissions also have a numeric form you will see everywhere: read is 4, write is 2, execute is 1, added together per triple. So rwx is 7, r-x is 5, r-- is 4. The common sets:

755  rwxr-xr-x   owner full, others read+execute  (scripts, programs, directories)
644  rw-r--r--   owner read+write, others read     (normal files, config)
600  rw-------    owner read+write, nobody else     (secrets like private keys, .env)
700  rwx------    owner full, nobody else           (private directories)

Changing permissions and ownership:

chmod +x deploy.sh      # add execute permission (so you can run ./deploy.sh)
chmod 644 config.json   # set exact permissions numerically
chmod 600 .env          # lock a secrets file to owner-only
chown alice:devs app.js # change owner to alice and group to devs

Root, sudo and least privilege

The root user can do anything, ignoring all permissions. You rarely log in as root; instead you run individual commands with sudo ("do this one thing as root"):

sudo systemctl restart myapp   # restart a service (needs root)
sudo apt install nginx          # install software (needs root)

The rule professionals live by is least privilege: run as a normal user, use sudo only for the specific commands that need it, and run your application as a dedicated non-root user. A backend process running as root means a bug in it can damage the whole server; the same bug in a locked-down appuser can damage only what that user owns.

Practical example — securing a secrets file

Your application reads database credentials from a .env file. That file must not be readable by other users on the server:

ls -l .env            # -rw-r--r--  -- BAD: others can read your DB password
chmod 600 .env        # fix: owner-only
ls -l .env            # -rw-------  -- now only the owner can read it

This one command is the difference between "our database password was in a file any process could read" and "it was locked down". Secrets files are always 600.

Edge cases & failure modes

  • "Permission denied" running a script: it lacks execute permission; chmod +x script.sh.
  • A world-readable secrets file (644) leaks credentials to any user or process on the box; use 600.
  • Running the app as root so a compromise gives an attacker the whole machine; run as a dedicated user.
  • chmod 777 (everyone can do everything) is almost always wrong and a security red flag; it is a lazy "fix" that opens the file to all.
  • Ownership mismatches after copying files as root, so the app user cannot read its own files; fix with chown.

How a Senior Backend Engineer thinks about this

A senior applies least privilege reflexively: the application runs as a non-root user, secrets files are 600, and sudo is used only where genuinely required. They see chmod 777 as a smell that someone did not understand the actual permission needed and papered over it. When a process gets "permission denied", they diagnose the exact missing permission rather than escalating to root, because escalating to root turns a small access problem into a large security problem. On any server, "who owns this and who can read it" is a question they ask about every sensitive file.

Common mistakes

  • chmod 777 to make an error go away, opening files to everyone.
  • Leaving secrets files world-readable (644 instead of 600).
  • Running the application as root.
  • Fixing "permission denied" by prefixing everything with sudo instead of fixing ownership.

Interview questions

  1. What do the three permission triples represent? Owner, group, others; each with read (4), write (2), execute (1).
  2. What permissions should a secrets file like a private key or .env have, and why? 600 (owner read/write only), so no other user or process on the machine can read the credentials.
  3. What is least privilege and how does it apply to running a backend? Grant only the access needed; run the app as a dedicated non-root user so a compromise is contained, and use sudo only for specific privileged commands.
  4. Why is chmod 777 a red flag? It grants everyone full access, usually masks a misunderstanding of the real permission needed, and is a security risk.

Practical exercise

Create a script hello.sh that echoes a message, try to run it (it fails without execute permission), add execute permission, and run it successfully. Then create a fake secrets file, set it to 600, and verify with ls -l that only you can read it. Acceptance criteria: you can explain each permission bit in the ls -l output for both files.

72.3 Processes

72.3.1 Viewing and managing running programs

Concept

A process is a running program. Your backend server is a process; the database is a process; the shell itself is a process. Each has an id (a PID), an owner, and resource usage. Managing processes — seeing what is running, how much memory and CPU it uses, and stopping it — is core to operating a server. Part 3 covers processes and threads at the operating-system level; here we cover the day-to-day commands.

Why does it exist?

When your server misbehaves — using all the memory, stuck, or needing a restart — you work with it as a process. "Is it even running? What is its PID? How much memory is it using? Why is the CPU at 100 percent?" are questions you answer with process commands. Without them you are blind to what the machine is actually doing.

Mental model

A process is a worker the operating system hired to run one program. The OS keeps a roster of all its workers with id badges (PIDs), what each is doing, and how many resources (CPU time, memory) each is consuming. The process commands let you read that roster, find a specific worker, and, if one is misbehaving, tell it to stop — politely at first, forcefully if it ignores you.

How it works

ps aux                  # list all processes (user, PID, CPU%, MEM%, command)
ps aux | grep node      # find processes whose command mentions 'node'
top                     # live, updating view of processes by resource use (q to quit)
htop                    # a nicer top, if installed

A line from ps aux:

USER   PID  %CPU %MEM    VSZ   RSS  STAT  START  TIME COMMAND
alice 4521  3.2  8.1  985000 332000  Sl   09:30  2:14 node dist/main.js
#     ^PID              ^virtual ^actual memory         ^the command

The PID (4521) is the id you use to signal the process. %MEM and RSS tell you memory use (RSS is the actual physical memory). %CPU tells you CPU use. For a Node process eating memory, this is where you see it.

Signals are how you communicate with a process. The main ones:

kill 4521            # send SIGTERM: "please shut down gracefully"
kill -9 4521         # send SIGKILL: "stop immediately, no cleanup" (last resort)
kill -HUP 4521       # send SIGHUP: often "reload your config"

The difference between kill (SIGTERM) and kill -9 (SIGKILL) is important. SIGTERM asks the process to shut down cleanly — finish in-flight requests, close database connections, flush logs. A well-written server catches SIGTERM and does exactly that (graceful shutdown, Part 27). SIGKILL cannot be caught; it stops the process instantly, mid-request, leaving connections dangling. Always try SIGTERM first; use SIGKILL only when a process ignores SIGTERM.

Foreground, background and jobs

node server.js          # runs in the foreground, ties up your terminal
node server.js &        # runs in the background, gives you the prompt back
jobs                    # list background jobs started in this shell
fg                      # bring the most recent background job to the foreground
nohup node server.js &  # keep running even after you log out
Ctrl+C                  # send SIGINT: stop the foreground process
Ctrl+Z                  # suspend the foreground process (resume with fg)

For real servers you do not run processes with &; you use a process manager (systemd, or pm2 for Node, or a container orchestrator like Kubernetes, Part 27) that restarts them on crash and starts them on boot. But knowing the manual commands helps you understand what those managers do.

Practical example — diagnosing a stuck server

Your Node server is not responding. You investigate:

ps aux | grep node                     # is it running? what PID?
# alice 4521 99.0 8.1 ... node dist/main.js   <- 99% CPU, stuck in a loop
top                                     # confirm it is pegging a CPU
kill 4521                               # ask it to shut down gracefully
# if it does not stop within ~10 seconds:
kill -9 4521                            # force it
# then the process manager restarts it, or you restart it

The 99% CPU is the tell: the Node event loop is blocked by a synchronous computation (Part 70), so the process is alive but unresponsive. The process commands let you see it, confirm it, and recover it.

Edge cases & failure modes

  • A zombie or stuck process that ignores SIGTERM needs SIGKILL, but SIGKILL skips cleanup (dangling connections, unflushed data).
  • kill -9 on a database can corrupt data by skipping its shutdown; always prefer graceful shutdown for stateful processes.
  • Orphaned background jobs from & keep running after you log out only with nohup or a process manager; otherwise they may be killed when your session ends.
  • OOM killer: when the server runs out of memory, Linux kills a process to survive, often your app; you find "Killed" in logs and an OOM message in dmesg (Part 3, Part 27).
  • High load average (from uptime/top) means more work queued than CPUs can handle; a sustained load above the core count signals saturation.

How a Senior Backend Engineer thinks about this

A senior reaches for ps, top and kill as naturally as a mechanic reaches for a wrench. They always try SIGTERM before SIGKILL so processes shut down cleanly, and they design their own servers to handle SIGTERM gracefully (drain requests, close connections) because orchestrators send SIGTERM on every deploy and scale-down. They read top to tell apart a CPU problem (one core pegged, event loop blocked) from a memory problem (RSS climbing toward the limit) from a load problem (many processes queued). On production they rely on a process manager rather than manual &, but they understand the primitives underneath.

Common mistakes

  • Reaching for kill -9 first, skipping graceful shutdown and dropping in-flight work.
  • kill -9 on a database or other stateful process, risking corruption.
  • Running production servers with & instead of a process manager, so they do not restart on crash or boot.
  • Not implementing SIGTERM handling, so deploys kill requests mid-flight.

Interview questions

  1. What is the difference between SIGTERM and SIGKILL? SIGTERM (kill) asks for a graceful shutdown and can be caught; SIGKILL (kill -9) stops the process instantly and cannot be caught. Always try SIGTERM first.
  2. How do you find which process is using all the CPU or memory? top/htop for a live view, ps aux sorted or grepped for a specific program; read %CPU and RSS.
  3. Why should a backend handle SIGTERM? Orchestrators and process managers send SIGTERM on deploy and scale-down; handling it lets the server finish in-flight requests and close connections cleanly instead of dropping them.
  4. What is the OOM killer? When memory runs out, Linux kills a process to survive, often the app; you diagnose it from "Killed" in logs and OOM messages in the kernel log.

Practical exercise

Start a long-running command (for example a script that sleeps in a loop) in the foreground, suspend it with Ctrl+Z, resume it in the background, list jobs, then find its PID with ps and stop it with kill (SIGTERM). Acceptance criteria: you stop it with SIGTERM, not SIGKILL, and can explain when you would have needed SIGKILL instead.

72.4 Pipes, redirection and text tools

72.4.1 Composing commands

Concept

The real power of the command line is combining small commands into pipelines. A pipe (|) sends the output of one command as the input of the next. Redirection (>, >>, <) sends output to or input from a file. With a handful of text tools (grep, sort, uniq, wc, cut, awk) joined by pipes, you can answer questions about logs and data that would otherwise need a program.

Why does it exist?

Each Unix tool does one thing well: grep filters lines, sort orders them, uniq removes duplicates, wc counts. Rather than build one giant program, Unix lets you chain these small tools together so the combination does something none of them does alone. "How many unique IP addresses hit my error endpoint today?" is one pipeline of four tools, written in seconds. This composability is the core philosophy of the command line.

Mental model

Think of an assembly line where each station does one operation and passes the result to the next. Raw material (a log file) enters, grep filters out everything irrelevant, cut keeps one column, sort orders it, uniq -c counts duplicates, and the finished product (a count per value) comes out the end. The pipe | is the conveyor belt between stations. You build the line by naming the stations in order.

How it works

Every program has three standard streams: stdin (input), stdout (normal output), and stderr (error output). Pipes and redirection connect these.

command1 | command2        # stdout of command1 becomes stdin of command2
command > file.txt         # write stdout to a file (overwrites)
command >> file.txt        # append stdout to a file
command 2> errors.txt      # write stderr to a file
command > out.txt 2>&1      # write both stdout and stderr to one file
command < input.txt        # read stdin from a file

The essential text tools:

grep "error" app.log            # lines containing "error"
grep -i "error" app.log         # case-insensitive
grep -v "health" app.log        # lines NOT containing "health" (invert)
grep -c "error" app.log         # count matching lines
sort                            # sort lines
sort -n                         # sort numerically
uniq                            # collapse adjacent duplicate lines
uniq -c                         # count occurrences (needs sorted input)
wc -l                           # count lines
cut -d',' -f2                   # the 2nd comma-separated field of each line
head -n 10 / tail -n 10         # first / last 10 lines

Practical example — analyzing a log file

These are real pipelines a backend engineer runs during an incident. Read each left to right as an assembly line.

# How many errors in the log today?
grep -c "ERROR" app.log

# Which error messages are most common? (top 10)
grep "ERROR" app.log | cut -d']' -f2 | sort | uniq -c | sort -rn | head -n 10

# How many requests per status code? (assuming status is field 9)
cut -d' ' -f9 access.log | sort | uniq -c | sort -rn

# Watch for errors live as they happen:
tail -f app.log | grep --line-buffered "ERROR"

# How many unique IPs hit the login endpoint? (field 1 is the IP)
grep "/login" access.log | cut -d' ' -f1 | sort | uniq | wc -l

The second pipeline is the pattern to internalize: grep to filter, cut to extract a field, sort then uniq -c to count occurrences, sort -rn to rank, head to take the top. That one pattern answers "what are the most common X" for almost any log. You will use it hundreds of times.

Searching the filesystem

find . -name "*.ts"             # all TypeScript files under the current dir
find . -name "*.log" -mtime +7  # .log files modified more than 7 days ago
find /var/log -size +100M       # files larger than 100 MB
grep -r "TODO" src/             # recursively search file contents for "TODO"
grep -rn "apiKey" .             # recursive, with line numbers (find leaked secrets!)

Edge cases & failure modes

  • uniq only collapses adjacent lines, so you must sort first or it misses non-adjacent duplicates. This is the most common uniq mistake.
  • > overwrites the target file immediately; command > important.log destroys important.log even if the command fails. Use >> to append when you mean to add.
  • Errors go to stderr, so command | grep ... does not filter error messages unless you redirect 2>&1.
  • Huge files: a pipeline over a multi-gigabyte file is fine (it streams), but sort on a huge file uses a lot of memory and temp space.
  • Fields shift: cut -f assumes a consistent delimiter; log lines with variable spacing break simple cut, where awk is more robust.

How a Senior Backend Engineer thinks about this

A senior treats the shell as a data-analysis tool, not just a way to launch programs. During an incident, instead of downloading logs and opening them in an editor, they answer the question in place with a pipeline — the most common error, the status-code breakdown, the top offending IPs — in seconds. They always sort before uniq -c, always use >> when they mean append, and reach for awk when cut is too fragile. This fluency is a genuine force multiplier: the engineer who can interrogate a log with a one-line pipeline diagnoses incidents far faster than one who cannot.

Common mistakes

  • uniq without sort first, missing non-adjacent duplicates.
  • > when you meant >>, overwriting a file you wanted to append to.
  • Forgetting that errors go to stderr and are not caught by a plain pipe to grep.
  • Opening a huge log in an editor instead of filtering it with a pipeline.

Interview questions

  1. What does a pipe (|) do? Connects one command's stdout to the next command's stdin, letting you compose small tools into a pipeline.
  2. Why must you sort before uniq -c? uniq only collapses adjacent duplicate lines; sorting groups all duplicates together so the count is correct.
  3. Write a pipeline to find the ten most common error messages in a log. grep ERROR app.log | sort | uniq -c | sort -rn | head -n 10 (extracting the message field with cut/awk as needed).
  4. What is the difference between > and >>? > overwrites the file; >> appends to it.
  5. How do you capture both normal and error output to one file? command > out.txt 2>&1.

Practical exercise

Given a web access log, write pipelines to answer: how many total requests, how many returned a 5xx status, which three URLs were requested most often, and how many unique IP addresses appeared. Acceptance criteria: each is a single pipeline, you sort before any uniq -c, and you can explain what each stage of the pipeline does.

72.5 Environment variables

72.5.1 Configuring programs from the outside

Concept

An environment variable is a named value that the shell and every program it launches can read. They are the standard way to pass configuration into a program without changing its code — database URLs, API keys, which environment it is running in (development, production), the port to listen on. Your backend reads them at startup.

Why does it exist?

The same code runs on your laptop, in staging and in production, but it must connect to a different database and use different secrets in each. You cannot hardcode those values — that would mean a different build per environment, and secrets committed to source control. Environment variables solve this: the code reads process.env.DATABASE_URL, and each environment supplies a different value from the outside. This separation of configuration from code is a core principle of well-built applications (the "twelve-factor app", Part 28).

Mental model

Environment variables are like the settings on the outside of a machine, set by whoever installs it, that the machine reads when it turns on. The machine's internals (your code) do not change between a home and a factory; only the external dial settings differ. The program asks "what database should I use?" and reads the answer off the dial, rather than having the answer welded inside.

How it works

echo $HOME                      # read a variable (note the $)
echo $PATH                      # the list of directories searched for commands
printenv                        # list all environment variables
export DATABASE_URL="postgres://localhost/app"   # set one for this shell and its children
export NODE_ENV=production        # common one: tells the app which environment

# Set a variable for just one command (not persisted):
PORT=4000 node dist/main.js

export makes a variable available to programs the shell launches. Without export, the variable exists only in the shell itself, not in programs it starts. Variables set with export last only for the current shell session; when you close the terminal, they are gone. To persist them, you put them in a shell startup file (~/.bashrc, ~/.zshrc) or, for an application, use a .env file loaded at startup.

The PATH variable deserves special mention: it is a colon-separated list of directories the shell searches to find a command. When you type node, the shell looks through each directory in PATH for a program called node. "command not found" usually means the program is not in any PATH directory.

.env files

Backend projects keep their configuration in a .env file during development. A library (dotenv, built into NestJS via @nestjs/config, Part 74) reads it into process.env at startup.

# .env  -- NEVER commit this file; it holds secrets
DATABASE_URL=postgres://user:password@localhost:5432/shop
REDIS_URL=redis://localhost:6379
JWT_SECRET=a-long-random-secret
NODE_ENV=development
PORT=3000

The .env file must be in .gitignore so it is never committed — it contains secrets. A committed .env.example with placeholder values documents which variables are needed without leaking the real ones. In production, secrets usually come from a secret manager (AWS Secrets Manager, Part 28) rather than a file on disk.

Reading them in Node

// In your code, environment variables are on process.env (all strings or undefined).
const port = Number(process.env.PORT ?? 3000);     // convert; env values are strings
const dbUrl = process.env.DATABASE_URL;
if (!dbUrl) {
  throw new Error('DATABASE_URL is required');       // fail fast at startup
}

Two habits here: every process.env value is a string or undefined (so convert numbers with Number(...)), and you should fail fast at startup if a required variable is missing, rather than crashing later mid-request when something tries to use it.

Edge cases & failure modes

  • Committing a .env file leaks every secret into source control history, where it stays forever even if deleted later; rotate the secrets immediately if this happens.
  • Env values are strings, so process.env.PORT > 3000 compares strings, not numbers; convert first.
  • Missing required variable causes a confusing runtime crash deep in the app; validate at startup instead.
  • export scope: a variable set in one shell is not seen by another shell or by a process manager; configuration for a service must be set where the service is launched.
  • Precedence confusion: a variable set inline, in .env, in the shell, and in the deploy system can conflict; know which wins (usually the one set closest to launch).

How a Senior Backend Engineer thinks about this

A senior keeps all configuration in environment variables and never hardcodes a URL, port or secret, so the same artifact runs in every environment. They validate required variables at startup and fail fast with a clear message, because a missing config caught at boot is a trivial fix while the same config missing at runtime is a production incident. They keep .env out of source control religiously and treat an accidentally committed secret as a security incident requiring rotation, not just a deletion. In production they prefer a secret manager over files on disk.

Common mistakes

  • Committing .env and leaking secrets into git history.
  • Hardcoding environment-specific values (URLs, ports, keys) in code.
  • Forgetting env values are strings and comparing or using them as numbers.
  • Not validating required config at startup, leading to confusing late crashes.

Interview questions

  1. Why configure a backend with environment variables instead of hardcoding? So the same build runs in every environment with different config and secrets, keeping secrets out of source control (twelve-factor principle).
  2. What type are process.env values, and what follows from that? Always strings (or undefined); you must convert numbers and booleans, and handle missing values.
  3. What is PATH and what does "command not found" usually mean? The list of directories the shell searches for commands; the command is not in any of those directories.
  4. What do you do if a .env file is accidentally committed? Treat it as a breach: rotate every secret it contained, because git history preserves it even after deletion.

Practical exercise

Create a .env file with PORT and a fake API_KEY, add it to a .gitignore, write a small Node script that reads both, converts PORT to a number, and throws a clear error if API_KEY is missing. Run it once with the variable present and once with it removed. Acceptance criteria: the missing-variable case fails fast at startup with a readable message, and .env is ignored by git.

72.6 Package managers

72.6.1 Installing software and dependencies

Concept

A package manager installs, updates and removes software, handling the dependencies each piece needs. There are two levels: the system package manager (apt on Debian/Ubuntu, yum/dnf on Red Hat) installs software on the whole machine; the language package manager (npm/pnpm/yarn for Node.js) installs the libraries your project depends on. A backend developer uses both.

Why does it exist?

Software is built from other software. Your Node backend uses dozens of libraries, each of which uses more. Installing them by hand — finding each, downloading it, finding what it needs, repeating — would be impossible to manage. A package manager automates it: you declare what you want, and it figures out and installs the whole dependency tree, in compatible versions, reproducibly.

Mental model

A package manager is like an app store with automatic dependency handling. You ask for one app (a library), and it quietly installs the ten other things that app needs to run, in versions that work together, and keeps a receipt (a lock file) so the exact same set can be installed again on another machine. Without it, you would be hunting down and installing each dependency by hand and hoping the versions matched.

How it works — system packages

sudo apt update                 # refresh the list of available packages
sudo apt install nginx          # install a package
sudo apt upgrade                # upgrade installed packages
sudo apt remove nginx           # remove a package
apt list --installed            # what is installed

(On Red Hat-family systems the same ideas use dnf install, dnf update, etc.)

How it works — Node packages

Node projects use npm (or pnpm/yarn). The project's dependencies are declared in package.json, and the exact installed versions are locked in package-lock.json (or pnpm-lock.yaml).

npm install                     # install everything in package.json (uses the lock file)
npm install express             # add a new dependency
npm install --save-dev jest     # add a development-only dependency (tests, build tools)
npm uninstall express           # remove a dependency
npm run build                   # run the "build" script defined in package.json
npm run start                   # run the "start" script
npm ci                          # clean install exactly from the lock file (used in CI)

Two directories and two files matter:

  • package.json declares dependencies with version ranges ("express": "^4.18.0").
  • package-lock.json records the exact versions actually installed, so everyone gets the same ones.
  • node_modules/ is where the installed packages live; it is huge and never committed (it is in .gitignore).
  • npm ci installs exactly what the lock file says, which is what you use in automated builds for reproducibility; npm install may update the lock file.

Semantic versioning

Versions follow MAJOR.MINOR.PATCH (for example 4.18.2). A MAJOR bump may break compatibility; MINOR adds features compatibly; PATCH fixes bugs compatibly. The ^ in ^4.18.0 means "any 4.x.y at or above this", allowing compatible updates but not a breaking major bump. Understanding this tells you how risky an upgrade is (Part 32 covers compatibility in depth).

Edge cases & failure modes

  • Committing node_modules bloats the repository enormously; it must be in .gitignore and rebuilt from the lock file.
  • Not committing the lock file means different machines install different versions, causing "works on my machine" bugs; always commit the lock file.
  • npm install in CI can quietly update the lock file; use npm ci for reproducible builds.
  • Supply-chain risk: a dependency (or one of its dependencies) can be malicious or compromised; this is a real attack vector (Part 23). Audit with npm audit and be cautious adding dependencies.
  • Global vs local installs: npm install -g installs system-wide; prefer local project dependencies so each project pins its own versions.
  • Version conflicts when two dependencies need incompatible versions of a third; package managers resolve most but not all.

How a Senior Backend Engineer thinks about this

A senior always commits the lock file and uses npm ci in automated builds, because reproducibility — the exact same dependency set on every machine and every deploy — eliminates a whole class of "works on my machine" failures. They are deliberately conservative about adding dependencies: every dependency is code they now run and must trust, update and secure, so a small utility they could write in ten lines is not worth a new dependency and its own dependency tree. They run npm audit and keep an eye on supply-chain risk, and they understand semantic versioning well enough to judge whether an upgrade is routine or risky.

Common mistakes

  • Committing node_modules to the repository.
  • Not committing the lock file, causing version drift between machines.
  • Using npm install instead of npm ci in CI, getting non-reproducible builds.
  • Adding heavy dependencies for trivial needs, growing the attack surface and maintenance load.

Interview questions

  1. What is the purpose of the lock file (package-lock.json)? It records the exact installed versions of every dependency so the same set is reproducible across machines and deploys.
  2. What is the difference between npm install and npm ci? install installs per package.json and may update the lock file; ci installs exactly from the lock file and is used in CI for reproducibility.
  3. What does ^4.18.0 allow? Any compatible 4.x.y version at or above 4.18.0, but not a breaking 5.0.0; based on semantic versioning.
  4. What is supply-chain risk and how do you mitigate it? A dependency or transitive dependency can be malicious or compromised; mitigate by minimizing dependencies, pinning versions via the lock file, running npm audit, and vetting what you add.

Practical exercise

Initialize a new Node project with npm init -y, install express as a dependency and jest as a dev dependency, and inspect package.json to see where each landed. Then delete node_modules and restore it with npm ci. Acceptance criteria: you can explain why node_modules is gitignored, what the lock file guarantees, and the difference between a dependency and a dev dependency.

72.7 SSH: reaching a remote server

72.7.1 Connecting securely to a machine you cannot touch

Concept

SSH (Secure Shell) is how you log into a remote server's command line over an encrypted connection. The server is in a data center; your laptop is wherever you are; SSH gives you a shell on that server as if you were sitting at it, with everything encrypted in transit. Almost every interaction with a production Linux server starts with SSH.

Why does it exist?

Servers have no keyboard or screen you can reach. You need a secure way to run commands on them from across the internet. Doing this in plain text would expose your commands and credentials to anyone listening on the network. SSH provides an encrypted, authenticated channel so you can operate a remote machine safely. It is the backbone of server administration and the transport underneath git push to many git servers.

Mental model

SSH is a secure phone line into the server's control room. Once connected, you speak commands and hear the server's replies, with the whole conversation scrambled so eavesdroppers hear nothing useful. The server checks it is really you (authentication) before letting you in, and your SSH client checks it is really the server (so you are not tricked into connecting to an imposter).

How it works

ssh alice@web-prod-1.example.com        # log in as alice to that host
ssh -i ~/.ssh/deploy_key alice@1.2.3.4  # use a specific private key
ssh -p 2222 alice@host                   # connect on a non-default port

# Once connected, you are at a shell on the remote machine. Type 'exit' to leave.

# Copy files to/from a server:
scp local.txt alice@host:/home/alice/    # copy a file up to the server
scp alice@host:/var/log/app.log ./       # copy a file down from the server
rsync -avz ./dist/ alice@host:/var/www/app/  # efficient sync of a directory

Key-based authentication is how SSH is done securely. Instead of a password, you generate a key pair: a private key that stays on your laptop (never shared) and a public key you put on the server. The server lets you in if you can prove you hold the matching private key. This is far more secure than passwords (which can be guessed or phished) and is the standard.

ssh-keygen -t ed25519 -C "alice@laptop"   # generate a key pair (ed25519 is modern, strong)
# This creates ~/.ssh/id_ed25519 (private, SECRET) and ~/.ssh/id_ed25519.pub (public, shareable)
ssh-copy-id alice@host                      # install your public key on the server

The private key is the most sensitive file you own — anyone with it can log in as you. It is stored 600 (owner-only, 72.2) and often protected with a passphrase. Never share it, never commit it, never email it.

Practical example — a deploy over SSH

A simple manual deploy (real deploys use CI/CD, Part 29, but this shows the primitives):

# Build locally, then copy the build up and restart the service on the server:
npm run build
rsync -avz ./dist/ alice@web-prod-1:/var/www/app/dist/
ssh alice@web-prod-1 "sudo systemctl restart myapp"
# One line that runs a command on the remote machine without an interactive session.

Edge cases & failure modes

  • Leaking the private key (committing it, wrong permissions, sharing it) lets anyone impersonate you; treat it as the crown jewels, 600, never shared.
  • "Host key verification failed" means the server's identity changed since you last connected — either it was legitimately rebuilt, or you are being tricked (a man-in-the-middle). Investigate before blindly removing the old key.
  • Password authentication enabled on a server invites brute-force attacks; production servers disable it and allow keys only.
  • Permissions too open on ~/.ssh (the key or the directory being group/world-readable) makes SSH refuse to use the key; it must be 600/700.
  • Leaving sessions open or using long-lived keys without rotation widens the window if a laptop is compromised.

How a Senior Backend Engineer thinks about this

A senior uses key-based SSH exclusively, protects the private key with a passphrase, and keeps ~/.ssh locked down. They disable password authentication on servers they manage, because passwords are brute-forceable and keys are not. They treat the private key as the single most sensitive thing on their laptop and would rotate it immediately if the laptop were lost. They prefer deploying through automation (CI/CD) over manual SSH, reserving interactive SSH for investigation and emergencies, because manual steps are unrepeatable and error-prone, and every manual production action is a chance for a mistake. When they do SSH into production, they carry the same discipline from 72.1: check who and where they are first.

Common mistakes

  • Committing or sharing a private key.
  • Leaving password authentication enabled on production servers.
  • Ignoring a "host key changed" warning that could signal an attack.
  • Doing everything by hand over SSH instead of automating repeatable deploys.
  • Wrong permissions on ~/.ssh causing confusing authentication failures.

Interview questions

  1. How does key-based SSH authentication work and why is it better than passwords? You hold a private key, the server has your public key, and you prove possession of the private key without sending it; it resists guessing, phishing and brute force in ways passwords do not.
  2. Which SSH key file is secret, and how is it protected? The private key (id_ed25519); it stays on your machine only, with 600 permissions, ideally passphrase-protected.
  3. What does "host key verification failed" mean and why not ignore it? The server's identity differs from what you recorded; it could be a legitimate rebuild or a man-in-the-middle attack, so investigate before trusting it.
  4. Why prefer automated deploys over manual SSH for production changes? Automation is repeatable, reviewable and less error-prone; manual production steps are unrepeatable and a common source of mistakes.

Practical exercise

Generate an ed25519 SSH key pair, verify the private key has 600 permissions, and identify which of the two files you would put on a server and which you must keep secret. Then write the single ssh command that would run uptime on a remote host without opening an interactive session. Acceptance criteria: you correctly identify the public vs private key and can explain why the private key's permissions matter.

Part 73 — Git Basics and the Development Workflow

Every real software project uses version control, and in practice that means Git. Git records the history of your code: every change, who made it, when, and why. It lets many people work on the same codebase without overwriting each other, lets you undo mistakes, and lets you see how any line of code came to be. You cannot work on a team — or even safely on your own — without it.

This Part is the beginner's on-ramp to Git. Part 30 covers Git deeply (internals, rebasing strategies, bisect, reflog recovery, advanced workflows); this Part teaches the foundation you need before that makes sense: what Git is and why, the core commands (init, clone, add, commit, status, log), branches and merging, remotes and pull requests, and how to resolve a conflict without panic. By the end you will be able to clone a repository, make a change on a branch, commit it, push it, open a pull request, and handle a merge conflict — the everyday loop of professional development.

We teach the command line Git here, because it is universal and because understanding the commands makes the graphical tools make sense. Once you know the commands, use whatever interface you like.

73.1 What Git is and why it exists

73.1.1 Version control and the commit

Concept

Git is a version control system: a tool that records snapshots of your project over time. Each snapshot is called a commit. A commit captures the exact state of all your files at a moment, along with a message explaining the change, who made it, and when. The full history of commits is your project's memory — you can look at any past state, compare any two, and undo back to any point.

Why does it exist?

Without version control, you save over your files and the previous version is gone. You keep folders named project-final, project-final-v2, project-really-final. Two people editing the same file overwrite each other. You cannot tell when a bug was introduced or by whom. Git solves all of this: every version is kept forever, changes from different people merge together, and every line's history is recoverable. It is the difference between working with a safety net and working without one.

Mental model

Imagine a photographer taking a snapshot of your entire project every time you finish a meaningful change, and filing each snapshot with a note about what changed. You can flip back through the album to any past snapshot, see exactly what the project looked like then, and compare any two snapshots to see what moved. You can even start an alternate album (a branch) to try something risky, and either merge it back or throw it away without affecting the main album. Git is that photographer and that album system, automated and precise.

How it works

Git tracks your project through three "places" a change moves through:

Working directory  ->  Staging area (index)  ->  Repository (commits)
   (your files)         (changes you          (permanent history)
                         marked to save)
      |                       |                        |
   you edit               git add                  git commit
  1. Working directory: the actual files you edit. Git watches them and notices changes.
  2. Staging area: a holding area where you place the specific changes you want in your next commit. git add moves changes here. This lets you commit some changes but not others.
  3. Repository: the permanent history. git commit takes everything staged and records it as a new commit forever.

Each commit has a unique id (a long hash like a43fe077...), a parent (the commit before it), an author, a timestamp, and a message. The chain of commits, each pointing to its parent, is the history.

The core commands

git init                 # start tracking a new project in the current directory
git clone <url>          # copy an existing remote repository to your machine
git status               # what has changed, what is staged (run this constantly)
git add file.ts          # stage one file's changes for the next commit
git add .                # stage all changes in the current directory
git commit -m "message"  # record staged changes as a commit with a message
git log                  # show the history of commits
git log --oneline        # compact one-line-per-commit history
git diff                 # show unstaged changes (what you edited but didn't stage)
git diff --staged        # show staged changes (what will go in the next commit)

git status is the command you run most. It tells you where you are: what has changed, what is staged, which branch you are on. Run it before and after almost everything until the state is obvious to you.

Writing a good commit message

A commit message explains why a change was made, not just what. "Fix bug" is useless in six months; "Fix order total to include tax before applying discount" tells the next person (often you) what happened and why. The common convention is a short summary line (under ~50 characters), a blank line, then more detail if needed.

git commit -m "Add idempotency key to order creation

Clients retry failed POST /orders requests, which was creating
duplicate orders. The idempotency key lets the server detect and
reject duplicates. Fixes TSB-4422."

Practical example — your first commits

mkdir my-api && cd my-api
git init                              # start a repository
echo "node_modules/" > .gitignore     # tell git to ignore node_modules
git add .gitignore
git commit -m "Add gitignore"
# ... create src/index.ts ...
git add src/index.ts
git status                            # confirm it is staged
git commit -m "Add entry point"
git log --oneline                     # see your two commits

The .gitignore file

Some files should never be committed: node_modules/ (huge, rebuildable), .env (secrets), build output (dist/), editor settings. A .gitignore file lists patterns Git should ignore. Setting it up early is important — committing node_modules or .env is a classic beginner mistake (the first bloats the repo, the second leaks secrets).

Edge cases & failure modes

  • Committing secrets (.env, API keys) puts them in history forever, even if deleted in a later commit; this is a security incident requiring secret rotation (Part 23). Prevent it with .gitignore.
  • Committing node_modules bloats the repository massively; always gitignore it.
  • Huge commits mixing many unrelated changes are hard to review and hard to revert cleanly; make focused commits.
  • Useless messages ("stuff", "wip", "fix") make history worthless for understanding why code is the way it is.
  • Forgetting to git add before commit, so your change is not actually included; git status catches this.

How a Senior Backend Engineer thinks about this

A senior treats commit history as documentation that future engineers (including themselves) will read to understand why the code is the way it is. They make small, focused commits each doing one thing, with messages that explain the reasoning, so that history can be read, searched and selectively reverted. They set up .gitignore before the first commit to keep secrets and junk out of history permanently, because what enters git history is effectively permanent. They run git status and git diff before every commit to know exactly what they are recording, never blindly git add . without looking.

Common mistakes

  • Committing secrets or node_modules (prevent with .gitignore).
  • Giant unfocused commits mixing unrelated changes.
  • Vague commit messages that explain nothing.
  • git add . without checking what it is staging, accidentally committing unintended files.

Interview questions

  1. What are the three areas a change moves through in Git? Working directory (your files), staging area (changes marked for the next commit via git add), and the repository (committed history via git commit).
  2. Why does a committed secret require rotating the secret, not just deleting it? Git history is permanent; the secret remains in past commits even after deletion, so anyone with the repo can recover it.
  3. What makes a good commit message? A concise summary of what changed and, importantly, why; focused on a single logical change.
  4. Why make small, focused commits? They are easier to review, understand and revert cleanly, and they make the history a useful record.

Practical exercise

Create a new Git repository, add a .gitignore that excludes node_modules/ and .env, make two separate focused commits (one for a config file, one for a source file) with clear messages, and view the history with git log --oneline. Then run git status and git diff to confirm the working directory is clean. Acceptance criteria: history shows two focused commits with meaningful messages, and neither node_modules nor .env is tracked.

73.2 Branches

73.2.1 Working in parallel without stepping on each other

Concept

A branch is an independent line of development. The default branch (usually main) holds the stable, shared code. When you start work, you create a branch off main, make your commits there, and later merge them back. Branches let many people (and many features) progress in parallel without interfering, and let you keep risky or unfinished work away from the stable code.

Why does it exist?

If everyone committed directly to main, every unfinished or broken change would immediately affect everyone else, and two people editing the same area would constantly overwrite each other. Branches isolate work-in-progress. Your feature lives on your branch, broken or unfinished, until it is ready; only when it is reviewed and working does it merge into main. This is how teams of dozens work on one codebase without chaos.

Mental model

Think of main as the trunk of a tree and branches as limbs growing off it. You climb out onto your own limb to build something, in your own space, without disturbing anyone on the trunk or on other limbs. When your work is solid, you graft your limb back onto the trunk (merge), and everyone on the trunk now has your work. If the limb turns out to be a bad idea, you simply cut it off, and the trunk is untouched.

How it works

git branch                           # list branches; * marks the current one
git branch feat/add-coupons          # create a branch (does not switch to it)
git switch feat/add-coupons          # switch to that branch
git switch -c feat/add-coupons       # create AND switch in one step (common)
git switch main                      # go back to main
git branch -d feat/add-coupons       # delete a merged branch

(You will also see the older git checkout -b feat/... and git checkout main; switch is the newer, clearer command for changing branches.)

A branch is really just a movable pointer to a commit. When you commit on a branch, the pointer advances. main points to the latest stable commit; your feature branch points to your latest work. This is why branching in Git is instant and cheap — it is just creating a pointer, not copying files.

flowchart LR
    A["commit 1"] --> B["commit 2 (main)"]
    B --> C["commit 3 (feat/add-coupons)"]
    C --> D["commit 4 (feat/add-coupons)"]
    B --> E["commit 5 (feat/fix-tax)"]

Here, two feature branches grew from the same point on main. Each developer works independently. When each is ready and reviewed, it merges back into main.

Branch naming

Teams use conventions so a branch name tells you what it is. A common one, which matches this book's example repo:

feat/TSB-4422-notification-filter    a feature, with the ticket number
fix/login-timeout                    a bug fix
chore/upgrade-nestjs                 maintenance

Including the ticket number (like TSB-4422) links the branch to the task tracker (Jira, in this project), so anyone can trace code back to the reason it exists.

Practical example — the everyday loop

git switch main                       # start from the stable branch
git pull                              # get the latest from the remote (73.3)
git switch -c feat/add-coupons        # create your feature branch
# ... edit code, make commits ...
git add .
git commit -m "Add coupon validation to checkout"
# ... more work, more commits ...
git push -u origin feat/add-coupons   # push your branch to the remote (73.3)
# then open a pull request (73.3)

This is the loop you will run every working day: branch off up-to-date main, commit your work, push, open a pull request. Never work directly on main.

Edge cases & failure modes

  • Working directly on main defeats the purpose of branches and makes every unfinished change affect everyone; always branch.
  • A long-lived branch that diverges from main for weeks accumulates painful conflicts when it finally merges; keep branches short-lived and merge often.
  • Uncommitted changes when switching branches: Git may refuse to switch or carry changes along confusingly; commit or git stash first.
  • Forgetting which branch you are on and committing to the wrong one; git status always shows the current branch.
  • Deleting an unmerged branch with git branch -D (capital D forces it) loses that work; the lowercase -d refuses to delete unmerged branches as a safeguard.

How a Senior Backend Engineer thinks about this

A senior keeps branches short-lived and focused — one branch per feature or fix, merged within days, not weeks — because the longer a branch lives apart from main, the more it diverges and the more painful the eventual merge. They always branch off an up-to-date main and never commit directly to the shared branch. They use clear, ticket-linked branch names so work is traceable. They treat git stash as the tool for "I need to switch branches but am mid-change", and they rely on git status to always know where they are, because committing to the wrong branch is a common and avoidable slip.

Common mistakes

  • Committing directly to main.
  • Long-lived branches that become a merge nightmare.
  • Switching branches with uncommitted changes and getting confused.
  • Losing work by force-deleting an unmerged branch.

Interview questions

  1. What is a branch, mechanically? A movable pointer to a commit; branching is cheap because it creates a pointer rather than copying files.
  2. Why work on a branch instead of directly on main? To isolate unfinished or risky work from the stable shared code and let people work in parallel without conflict.
  3. Why keep branches short-lived? The longer a branch diverges from main, the more conflicts accumulate; frequent small merges are far less painful than one big one.
  4. What does git stash do and when would you use it? It temporarily shelves uncommitted changes so you can switch branches cleanly, then reapply them later.

Practical exercise

From an up-to-date main, create a branch feat/practice, make two commits on it, switch back to main and confirm those commits are not there, then switch back to your branch. Try switching branches with an uncommitted change and observe Git's behavior, then use git stash to handle it. Acceptance criteria: you can explain why the commits appear only on your branch and demonstrate stashing to switch cleanly.

73.3 Remotes and pull requests

73.3.1 Sharing work through a remote repository

Concept

A remote is a copy of the repository hosted somewhere everyone can reach — on GitHub, GitLab or similar. Your local repository and everyone else's are copies; the remote is the shared central copy they synchronize through. You push your commits up to the remote and pull others' commits down. A pull request (PR) — called a merge request on GitLab — is a proposal to merge your branch into main, where teammates review it before it is accepted.

Why does it exist?

Git is distributed: every developer has the full history on their machine. But to collaborate, everyone needs a shared point to sync through, and teams need a checkpoint where changes are reviewed before entering the stable branch. The remote provides the shared copy; the pull request provides the review gate. Together they are how code goes from one engineer's laptop to the shared main safely, with at least one other person having looked at it.

Mental model

Imagine a shared document in the cloud that everyone has a local copy of. You make changes locally, then upload them (push) so others can download them (pull). But before your changes are accepted into the official version, you submit them for review — a colleague reads them, comments, requests tweaks, and approves. Only approved changes become part of the official document. The cloud document is the remote; the review-and-approve step is the pull request.

How it works

git clone <url>                       # get a copy of a remote repo (sets up 'origin')
git remote -v                         # show configured remotes (usually 'origin')
git push -u origin feat/add-coupons   # push your branch up the first time (-u links them)
git push                              # push subsequent commits
git pull                              # fetch others' commits and merge them into your branch
git fetch                             # download remote changes WITHOUT merging (safer to inspect first)

origin is the conventional name for the main remote (the one you cloned from). git push -u origin <branch> the first time links your local branch to a remote branch so later you can just type git push and git pull.

The pull request workflow:

flowchart LR
    A["Branch off main"] --> B["Commit work locally"]
    B --> C["git push to remote"]
    C --> D["Open pull request"]
    D --> E["Teammates review and comment"]
    E --> F{"Approved?"}
    F -->|"changes requested"| G["Make more commits, push"]
    G --> E
    F -->|"yes"| H["Merge into main"]
    H --> I["Delete the branch"]
  1. You push your branch to the remote.
  2. You open a pull request: "please merge feat/add-coupons into main", with a description of what and why.
  3. Automated checks run (tests, linting — Part 29 on CI/CD).
  4. Teammates review the code, leave comments, maybe request changes.
  5. You address feedback with more commits and push again (the PR updates automatically).
  6. Once approved and checks pass, the PR is merged into main and the branch is deleted.

The pull request description

A good PR description tells the reviewer what changed, why, and how to verify it. It links the ticket. It calls out anything risky. A reviewer who understands the intent reviews faster and better than one staring at a raw diff.

Title: Add idempotency key to order creation (TSB-4422)

What: POST /orders now accepts an Idempotency-Key header and rejects
duplicate submissions within 24 hours.

Why: Clients retry failed requests, which was creating duplicate orders
(see incident INC-883).

How to test: POST the same order twice with the same key; the second
returns the first order, not a new one.

Risk: Low. New behavior is behind the header; requests without the
header are unchanged.

Practical example — from branch to merged

git switch main && git pull                  # start fresh and up to date
git switch -c fix/login-timeout              # branch
# ... fix the bug, commit ...
git commit -am "Increase login token timeout to 30 minutes"
git push -u origin fix/login-timeout         # push
# open the PR in the web UI, fill in the description, request a reviewer
# reviewer comments; you address them:
git commit -am "Address review: make timeout configurable via env"
git push                                      # PR updates automatically
# reviewer approves, checks pass, merge via the web UI, delete the branch
git switch main && git pull                   # bring the merged change into your local main

Edge cases & failure modes

  • Pushing to the wrong branch or force-pushing over others' work (git push --force) can destroy commits; avoid force-push on shared branches (Part 30 covers the safe --force-with-lease).
  • A stale local main: forgetting to git pull before branching means you build on old code and hit conflicts; always start from up-to-date main.
  • A huge PR (thousands of lines) is nearly impossible to review well; reviewers rubber-stamp it and bugs slip through. Keep PRs small.
  • Merging your own PR without review skips the quality gate that catches mistakes; follow the team's review requirement.
  • Secrets in a PR: pushing a commit with a secret exposes it to everyone with repo access, even if later removed; prevent with .gitignore and pre-commit checks.

How a Senior Backend Engineer thinks about this

A senior keeps pull requests small and focused, because a PR a reviewer can actually read in ten minutes gets a real review, while a 2,000-line PR gets a rubber stamp. They write PR descriptions that explain intent and how to verify, treating the reviewer's time as valuable. They always branch from up-to-date main and pull frequently to keep divergence small. They never force-push shared branches. They see code review not as a gate to get past but as the main mechanism by which a team shares knowledge and catches defects early, and they both give and receive review thoughtfully (Part 25 covers code review as a practice).

Common mistakes

  • Branching off a stale main, causing avoidable conflicts.
  • Giant PRs that cannot be reviewed meaningfully.
  • Force-pushing shared branches and destroying others' commits.
  • Thin or missing PR descriptions that waste the reviewer's time.
  • Merging without review when the team requires it.

Interview questions

  1. What is the difference between git fetch and git pull? fetch downloads remote changes without merging (so you can inspect first); pull fetches and immediately merges into your branch.
  2. What is a pull request and what purpose does it serve? A proposal to merge a branch into main, providing a review and automated-check gate before changes enter the stable branch.
  3. Why keep pull requests small? Small PRs get genuine review and are easier to understand and revert; large ones get rubber-stamped and hide bugs.
  4. Why is force-pushing a shared branch dangerous? It rewrites history others may have based work on, potentially destroying their commits; use it only on your own branches, and prefer --force-with-lease.

Practical exercise

Clone a repository (or use one you created), create a branch, make a commit, push it with git push -u origin <branch>, and open a pull request with a description covering what, why, how to test, and risk. Acceptance criteria: the PR has a meaningful description and links to the branch; you can explain what origin and the -u flag did.

73.4 Merging and resolving conflicts

73.4.1 Bringing branches together

Concept

Merging combines the commits from one branch into another — typically merging your feature branch into main. Most merges are automatic: Git figures out how to combine the changes. Sometimes two branches changed the same lines of the same file in different ways, and Git cannot decide which to keep. That is a merge conflict, and you resolve it by telling Git which change wins (or how to combine them).

Why does it exist?

When work happens in parallel on branches, those branches must eventually come back together. Merging is that reunion. Conflicts arise because Git is careful: rather than guess wrong and silently lose someone's change, it stops and asks you when two changes genuinely overlap. A conflict is not an error or a failure — it is Git correctly refusing to make a decision only a human can make.

Mental model

Imagine two editors marking up the same paragraph of a document separately. Most of the time they edit different paragraphs, and combining their work is trivial — Git does it for you. But if both rewrote the same sentence differently, no automated rule can know which rewrite is right. Git brackets both versions and hands them to you: "you decide." Resolving a conflict is reading both versions and writing the correct final one.

How it works

A typical merge:

git switch main
git pull                              # make sure main is current
git merge feat/add-coupons            # merge the feature branch into main
# If there are no conflicts, done. If there are, Git tells you which files conflict.

When a conflict happens, Git marks the conflicting sections inside the file with markers:

<<<<<<< HEAD
const timeoutMs = 30000;        // the version currently on your branch (main)
=======
const timeoutMs = 60000;        // the version from the branch being merged
>>>>>>> feat/add-coupons

To resolve, you edit the file to the correct final version and remove all three markers (<<<<<<<, =======, >>>>>>>):

const timeoutMs = 60000;        // you decided the incoming value is correct

Then:

git add src/config.ts                 # mark the conflict as resolved
git commit                            # complete the merge (Git pre-fills a message)

The commands for handling a conflict:

git status                            # lists the files with conflicts
# ... edit each conflicting file, remove markers, keep the correct content ...
git add <resolved-file>               # stage each resolved file
git commit                            # finish the merge
git merge --abort                     # OR: give up and go back to before the merge

Rebase: the other way (brief)

Besides merge, Git has rebase, which replays your branch's commits on top of the latest main, producing a straighter history. It is powerful and common, but it rewrites commits, so it has its own rules and risks. Part 30 covers rebase, when to use it versus merge, and the "golden rule of rebase" (never rebase commits others have based work on). As a beginner, understand merge first; reach for rebase once you are comfortable.

Practical example — resolving a real conflict

Two people both edited the shipping-cost function. You merge and hit a conflict:

git switch main && git pull
git merge feat/free-shipping
# CONFLICT (content): Merge conflict in src/shipping.ts
git status                            # shows src/shipping.ts as "both modified"

Opening src/shipping.ts:

<<<<<<< HEAD
if (subtotalCents >= 5000) return 0;         // free over $50 (from main)
=======
if (subtotalCents >= 4000) return 0;         // free over $40 (from the branch)
>>>>>>> feat/free-shipping

You check the ticket, learn the business decided on $40, edit the file to keep that line, remove the markers, then:

git add src/shipping.ts
git commit                            # completes the merge

Crucially, you also re-run the tests (Part 24) after resolving, because a conflict resolution can be syntactically valid but logically wrong — you might keep both lines, or the wrong one, and only tests catch that.

Edge cases & failure modes

  • Leaving a conflict marker (<<<<<<<) in the file and committing it breaks the code; search for markers before committing, and tests/linting catch them.
  • Resolving wrong — keeping the wrong side or an inconsistent mix — compiles but behaves incorrectly; always re-run tests after resolving.
  • Panicking and making it worse: git merge --abort cleanly undoes an in-progress merge so you can start over calmly.
  • A huge conflict from a long-diverged branch is painful; prevent it by keeping branches short and pulling main often.
  • Binary file conflicts (images, compiled files) cannot be merged line-by-line; you pick one version wholesale, which is a reason not to commit binaries casually.

How a Senior Backend Engineer thinks about this

A senior sees a conflict as routine, not alarming — it is Git doing its job. They resolve it by understanding both changes and the intent behind them (often checking the ticket or asking the other author), not by blindly picking a side. They always re-run the tests after resolving, because a conflict resolution is a code change like any other and can be subtly wrong. They prevent most conflicts by keeping branches short-lived and frequently pulling the latest main into their branch, so divergence stays small. When a merge goes sideways, they know git merge --abort gives them a clean slate, so they never feel trapped.

Common mistakes

  • Committing conflict markers left in the file.
  • Resolving conflicts without understanding the other change, keeping the wrong version.
  • Not re-running tests after resolving, shipping a logically broken resolution.
  • Letting branches diverge for weeks, turning a routine merge into a nightmare.

Interview questions

  1. What causes a merge conflict? Two branches changed the same lines of the same file differently, so Git cannot automatically decide which to keep and asks you.
  2. How do you resolve a conflict? Edit the file to the correct final content, remove the conflict markers, git add the file, and git commit; then re-run tests.
  3. Why re-run tests after resolving a conflict? A resolution is a code change that can be syntactically valid but logically wrong; tests catch an incorrect merge.
  4. How do you prevent painful conflicts? Keep branches short-lived and merge/pull main frequently so branches do not diverge far.
  5. What does git merge --abort do? Cancels an in-progress merge and returns to the state before it started, so you can retry calmly.

Practical exercise

Create a repository, make a branch, and on both main and the branch edit the same line of the same file differently. Merge the branch into main, resolve the resulting conflict by choosing the correct final line and removing the markers, and complete the merge. Then deliberately leave a marker in a second conflict and observe how tests or a linter catch it. Acceptance criteria: you resolve the first conflict cleanly, complete the merge, and can explain why leaving a marker is dangerous.

73.5 The development workflow, end to end

73.5.1 Putting it together

Concept

The everyday professional Git workflow is a short, repeatable loop that ties together everything in this Part: start from up-to-date main, branch, commit focused changes with good messages, push, open a pull request, respond to review, merge, and clean up. Knowing the loop as a single rhythm is what makes Git second nature rather than a series of commands you look up.

How it works

1. git switch main && git pull          start from the latest stable code
2. git switch -c feat/TSB-1234-thing    branch (named after the ticket)
3. edit, git add, git commit            make small focused commits with clear messages
4. git push -u origin feat/...          push your branch
5. open a pull request                   describe what, why, how to test, risk
6. automated checks run                   tests and lint (CI, Part 29)
7. address review feedback               more commits, git push; PR updates
8. merge into main                        once approved and green
9. git switch main && git pull           pull the merged change locally
10. git branch -d feat/...               delete the finished branch

This loop runs once per feature or fix, often several times a day. Everything else in Git (rebasing, cherry-picking, bisecting, reflog recovery) is a refinement or a rescue tool layered on top of this core loop, and Part 30 covers those.

A quick command reference

# Starting work
git clone <url>                  git switch main                  git pull
git switch -c feat/my-feature

# Saving work
git status                       git diff                         git add .
git commit -m "message"

# Sharing work
git push -u origin feat/my-feature    git push    git pull    git fetch

# Branches
git branch                       git switch <name>                git branch -d <name>

# History and inspection
git log --oneline                git show <commit>                git diff main..feat/x

# Undoing (basics; Part 30 goes deeper)
git restore <file>               # discard unstaged changes to a file
git restore --staged <file>      # unstage a file (keep the edits)
git revert <commit>              # make a new commit that undoes an old one (safe on shared history)

  • Rewriting shared history; use git revert on anything others have.
  • Skipping git pull before branching, building on stale code.

74.1 Project setup

74.1.1 What NestJS is and creating the project

Concept

NestJS is a framework for building backend applications in Node.js and TypeScript. A framework gives you structure and ready-made pieces (routing, validation, dependency injection, database integration) so you do not reinvent them. NestJS organizes an application into modules, controllers (which handle HTTP requests) and services (which hold business logic), with a system that wires them together for you called dependency injection.

Why does it exist?

You could build an HTTP server with raw Node, but you would hand-write routing, request parsing, validation, error handling, and the plumbing to connect everything — and every project would do it differently. NestJS provides a consistent, well-trodden structure so a team can build and a new engineer can navigate any NestJS codebase. It is opinionated in a way that pays off: the conventions mean less bikeshedding and more shared understanding. Part 6 covers its architecture and dependency injection in depth; here we use it.

Mental model

Think of NestJS as a pre-built office building with the plumbing, wiring and room layout already in place. You do not lay pipes or run cables; you move into rooms designed for specific purposes — the controller is the reception desk that receives visitors (requests), the service is the back office that does the actual work, the repository is the records department that talks to the filing system (the database). The building (the framework) handles how they connect; you furnish each room with your logic.

How it works — creating the project

NestJS has a command-line tool that scaffolds a project. Using Node 22 and NestJS 10:

npm i -g @nestjs/cli          # install the Nest CLI globally
nest new products-api          # scaffold a new project (choose npm when prompted)
cd products-api
npm run start:dev              # run in watch mode: restarts on file changes
# the API is now running on http://localhost:3000

The generated project structure (the parts that matter):

products-api/
├── src/
│   ├── main.ts                 # the entry point: creates and starts the app
│   ├── app.module.ts           # the root module: wires everything together
│   ├── app.controller.ts       # a sample controller (we will replace it)
│   └── app.service.ts          # a sample service
├── test/                       # end-to-end tests
├── package.json                # dependencies and scripts
├── tsconfig.json               # TypeScript configuration
└── .env                        # our config (we add this; it is gitignored)

The entry point, main.ts, is where the application starts. The generated version is minimal; we will enhance it shortly with validation and configuration.

// src/main.ts (generated)
import { NestFactory } from '@nestjs/core';
import { AppModule } from './app.module';

async function bootstrap() {
  const app = await NestFactory.create(AppModule);
  await app.listen(3000);
}
bootstrap();

NestFactory.create(AppModule) builds the whole application from the root module, wiring together every controller and service. app.listen(3000) starts the HTTP server on port 3000. The async/await here is exactly what you learned in Part 70 — starting a server is asynchronous.

The three building blocks

Controller   receives HTTP requests, returns responses. Thin: no business logic.
Service      holds business logic. Called by controllers. Knows nothing about HTTP.
Module       groups related controllers and services and declares their wiring.

This separation is the single most important convention in NestJS and in good backend design generally (Part 5, Part 6). The controller's job is to translate between HTTP and your logic — parse the request, call a service, shape the response. The service's job is the actual work, with no knowledge of HTTP. Keeping them separate means your logic is testable without a web server and your HTTP handling is thin and uniform.

Practical example — the generated hello endpoint

The scaffold comes with a working endpoint you can call right now:

// src/app.controller.ts (generated)
import { Controller, Get } from '@nestjs/common';
import { AppService } from './app.service';

@Controller()                             // this class handles requests
export class AppController {
  constructor(private readonly appService: AppService) {}  // service injected

  @Get()                                  // handles GET /
  getHello(): string {
    return this.appService.getHello();    // delegates to the service
  }
}
curl http://localhost:3000
# Hello World!

Notice the pattern already: the @Get() decorator maps a method to an HTTP route, the controller delegates to an injected service, and the service (not the controller) does the work. Every endpoint you build follows this shape.

Decorators

Those @Controller(), @Get() annotations are decorators — special markers starting with @ that attach metadata to classes and methods. NestJS reads them to know "this class handles requests" and "this method handles GET /". You do not need to understand how decorators work internally yet; treat them as labels that tell NestJS what each piece is for. We will use @Controller, @Get, @Post, @Body, @Param, @Injectable and a few others.

How a Senior Backend Engineer thinks about this

A senior values the controller/service separation from the first file, keeping controllers thin (translate HTTP, delegate, shape the response) and putting all real logic in services that know nothing about HTTP. This is not ceremony; it is what makes the logic testable in isolation and keeps the HTTP layer uniform and swappable. They let the framework's conventions do their job rather than fighting them, because a codebase that follows NestJS conventions is one any NestJS engineer can read. They run in watch mode (start:dev) during development for the fast feedback loop.

Common mistakes

  • Putting business logic in the controller, making it untestable without a web server and tangling HTTP concerns with domain logic.
  • Fighting the framework's conventions and inventing a bespoke structure nobody else can follow.
  • Not separating configuration from code (we fix this with @nestjs/config next).

Interview questions

  1. What are the roles of a controller and a service in NestJS? The controller handles HTTP (routing, parsing requests, shaping responses) and stays thin; the service holds business logic and knows nothing about HTTP.
  2. Why keep controllers thin? So business logic is testable without a web server and the HTTP layer stays uniform; it separates concerns cleanly.
  3. What is a module in NestJS? A unit that groups related controllers and services and declares how they are wired together.

Practical exercise

74.2 The controller, service and DTO

74.2.1 Building the products endpoints

Concept

Now we build the real feature: a products resource with endpoints to list products, get one by id, and create one. We follow the REST conventions from Part 71 and the controller/service split from 74.1. The new piece is the DTO (Data Transfer Object) with validation — the object that describes and checks the shape of incoming request data.

Why does it exist?

Every request body from a client is untrusted (Part 71): it might be missing fields, have wrong types, or contain malicious values. Before any of that data reaches your business logic or your database, it must be validated. A DTO with validation decorators declares exactly what a valid request looks like, and NestJS automatically rejects anything that does not match with a 400 — so your service only ever receives well-formed data. This is the "parse, don't trust" principle from Part 69, built into the framework.

Mental model

The DTO and its validator are the security checkpoint at the entrance. Before a visitor (a request body) is allowed into the building (your logic), the checkpoint verifies their papers: are the required fields present? Are the types right? Are the values in allowed ranges? Anyone who fails is turned away at the door with a clear reason (400 Bad Request), and only verified visitors proceed. Your inner logic never has to wonder whether its input is valid, because nothing invalid gets past the door.

How it works — generate the module

The Nest CLI scaffolds a module, controller and service together:

nest generate resource products
# choose: REST API, and "yes" to generate CRUD entry points
# this creates src/products/ with a module, controller, service, DTOs and entity

The DTO with validation

npm install class-validator class-transformer
// src/products/dto/create-product.dto.ts
import { IsInt, IsString, Length, Min, IsOptional, Max } from 'class-validator';

export class CreateProductDto {
  @IsString()
  @Length(1, 200)                       // name must be 1 to 200 characters
  name!: string;

  @IsInt()
  @Min(0)                               // price in cents, never negative (Part 69)
  @Max(100_000_00)                      // sanity cap: $100,000
  priceCents!: number;

  @IsString()
  @Length(2, 2)                          // ISO currency code like "US" -> here 2 chars for region
  @IsOptional()
  currency?: string;
}

Each decorator is a rule. @IsString() requires a string; @Length(1, 200) bounds its length; @IsInt() and @Min(0) require a non-negative integer. @IsOptional() marks a field as allowed to be absent. If a request violates any rule, NestJS returns a 400 with a message naming the failing field — you write zero validation code in your controller.

Turning validation on globally

Validation only runs if you enable the validation pipe. Do it once in main.ts so it applies to every endpoint:

// src/main.ts
import { NestFactory } from '@nestjs/core';
import { ValidationPipe } from '@nestjs/common';
import { AppModule } from './app.module';

async function bootstrap() {
  const app = await NestFactory.create(AppModule);
  app.useGlobalPipes(
    new ValidationPipe({
      whitelist: true,              // strip properties not in the DTO
      forbidNonWhitelisted: true,   // reject requests with unknown properties
      transform: true,              // convert payloads to DTO class instances
    }),
  );
  await app.listen(Number(process.env.PORT ?? 3000));
}
bootstrap();

whitelist: true strips any field the client sends that is not in the DTO — so a client cannot sneak extra fields (like isAdmin: true) into your logic. forbidNonWhitelisted goes further and rejects such requests outright. These two settings are a meaningful security measure (Part 23, mass-assignment protection), and they are one line each.

The controller

// src/products/products.controller.ts
import { Controller, Get, Post, Body, Param, ParseUUIDPipe } from '@nestjs/common';
import { ProductsService } from './products.service';
import { CreateProductDto } from './dto/create-product.dto';

@Controller('products')                    // all routes start with /products
export class ProductsController {
  constructor(private readonly products: ProductsService) {}

  @Get()                                   // GET /products
  list(): Promise<Product[]> {
    return this.products.findAll();
  }

  @Get(':id')                              // GET /products/:id
  getOne(@Param('id', ParseUUIDPipe) id: string): Promise<Product> {
    return this.products.findOne(id);       // ParseUUIDPipe rejects non-UUID ids with 400
  }

  @Post()                                  // POST /products
  create(@Body() dto: CreateProductDto): Promise<Product> {
    return this.products.create(dto);       // dto is already validated by the pipe
  }
}

Notice how thin the controller is. Each method extracts input (@Body, @Param), calls the service, and returns the result. No business logic, no validation code (the DTO and pipes handle it), no database access. The @Param('id', ParseUUIDPipe) even validates that the id is a valid UUID before the method runs, returning 400 otherwise. This is a thin controller done right.

HTTP status codes, for free and on purpose

NestJS returns sensible status codes automatically: 200 for a successful GET, 201 for a successful POST. When your service throws a NestJS exception, it maps to the right code: NotFoundException becomes 404, ConflictException becomes 409, BadRequestException becomes 400 (Part 71 on status codes). You throw a meaningful exception; the framework returns the correct HTTP response.

Practical example — calling it

# create a product (POST with a JSON body)
curl -X POST http://localhost:3000/products \
  -H "Content-Type: application/json" \
  -d '{"name":"Dental Mirror","priceCents":1299}'
# 201 Created, returns the new product with its generated id

# validation in action: a negative price is rejected
curl -X POST http://localhost:3000/products \
  -H "Content-Type: application/json" \
  -d '{"name":"Bad","priceCents":-5}'
# 400 Bad Request: "priceCents must not be less than 0"

# an unknown field is rejected (whitelist)
curl -X POST http://localhost:3000/products \
  -H "Content-Type: application/json" \
  -d '{"name":"X","priceCents":100,"isAdmin":true}'
# 400 Bad Request: "property isAdmin should not exist"

# list products
curl http://localhost:3000/products

You wrote no validation logic, yet bad input, negative prices and injected fields are all rejected with clear messages and the correct 400 status. That is the framework and the DTO working together.

Edge cases & failure modes

  • Forgetting to enable the ValidationPipe means DTO decorators do nothing and invalid data flows straight through — a silent, dangerous gap. Enable it globally in main.ts.
  • Not setting whitelist lets clients send extra fields that may reach your logic or ORM (mass assignment, Part 23).
  • Business logic creeping into the controller makes it untestable and tangles concerns; keep it in the service.
  • Returning raw entities can leak internal fields; map to a response shape for anything sensitive (Part 69).
  • Missing Content-Type: application/json on the request means the body is not parsed as JSON (Part 71).

How a Senior Backend Engineer thinks about this

A senior treats the DTO as the contract and the validation boundary: everything crossing into the application is validated there, so no unvalidated data ever reaches business logic or the database. They enable whitelist and forbidNonWhitelisted as a default security posture. They keep controllers thin and let the framework map exceptions to status codes, which keeps error handling uniform across the whole API. They map entities to explicit response shapes when any field should not be exposed. The result is an API where input validation, status codes and field exposure are handled consistently by design, not sprinkled ad hoc through handlers.

Common mistakes

  • Not enabling the validation pipe, so DTO rules silently do nothing.
  • Validating by hand inside controllers instead of using DTOs.
  • Omitting whitelist, allowing extra/injected fields.
  • Fat controllers with business logic.
  • Returning raw database entities and leaking internal fields.

Interview questions

  1. What is a DTO and why validate it? A Data Transfer Object describing the expected shape of request data; validating it rejects malformed or malicious input at the boundary before it reaches business logic.
  2. What do whitelist and forbidNonWhitelisted do and why do they matter? whitelist strips unknown properties; forbidNonWhitelisted rejects requests containing them — together they prevent clients from injecting unexpected fields (mass assignment).
  3. How does a service signal a 404 to the client in NestJS? By throwing NotFoundException, which the framework maps to a 404 response.
  4. Why keep the controller thin? So logic is testable without HTTP and error handling stays uniform; the controller only translates between HTTP and the service.

74.3 Basic SQL and connecting to PostgreSQL

74.3.1 A little SQL first

Concept

PostgreSQL is a relational database: it stores data in tables of rows and columns, and you talk to it with SQL (Structured Query Language). Before we have NestJS talk to it, you should see the raw SQL, because the ORM we use later just generates SQL for you, and you cannot debug what you do not understand. Part 11 teaches SQL properly; this is the minimum to follow the rest of this Part.

Why does it exist?

Your products need to persist — survive a server restart, be shared across every copy of the server, be queried and filtered efficiently. An in-memory array does none of that. A relational database gives you durable, queryable, concurrent storage with guarantees (a row is either fully written or not at all) that are the foundation of correct backends. SQL is the universal language for working with it.

How it works — the four basic statements

Connect with psql (74.1) and run these. Every backend engineer knows these four cold:

-- CREATE a table: define the shape of the data.
CREATE TABLE products (
  id          uuid PRIMARY KEY DEFAULT gen_random_uuid(),  -- unique id, auto-generated
  name        text NOT NULL,                                -- required
  price_cents integer NOT NULL CHECK (price_cents >= 0),    -- required, non-negative
  currency    char(3) NOT NULL DEFAULT 'USD',
  created_at  timestamptz NOT NULL DEFAULT now()            -- when the row was created
);

-- INSERT: add a row.
INSERT INTO products (name, price_cents) VALUES ('Dental Mirror', 1299)
  RETURNING id, name, price_cents, created_at;   -- RETURNING gives back the new row

-- SELECT: read rows.
SELECT id, name, price_cents FROM products;                    -- all products
SELECT id, name, price_cents FROM products WHERE id = $1;      -- one by id ($1 is a parameter)
SELECT * FROM products WHERE price_cents < 2000 ORDER BY name; -- filtered and sorted

-- UPDATE and DELETE: change or remove rows.
UPDATE products SET price_cents = 1399 WHERE id = $1;
DELETE FROM products WHERE id = $1;

Key ideas visible here. A primary key (id) uniquely identifies each row. Constraints (NOT NULL, CHECK (price_cents >= 0)) make invalid rows impossible to insert — the database enforces "price is never negative" so even a buggy application cannot violate it, which is a stronger guarantee than application validation alone. Parameters ($1) are how you safely pass values into a query; never build SQL by gluing strings together with user input, which causes SQL injection (Part 23).

SQL injection: the one security rule to internalize now

-- NEVER do this (string concatenation with user input):
--   "SELECT * FROM products WHERE name = '" + userInput + "'"
-- A userInput of  '; DROP TABLE products; --  destroys your table.

-- ALWAYS do this (parameterized query): the value can never be treated as code.
SELECT * FROM products WHERE name = $1;   -- the driver sends $1 separately from the SQL

The ORM and the database driver parameterize for you, which is one of the main reasons to use them. But you must understand the rule, because the day you write a raw query, this is on you.

Practical example — do it by hand once

In psql, create the table, insert two products, select them back, update one price, and delete one. Seeing the raw rows and the RETURNING output demystifies what the ORM will do. When the ORM later behaves unexpectedly, you will reach for psql and the raw SQL to see the truth.

How a Senior Backend Engineer thinks about this

A senior always understands the SQL their ORM generates, because the ORM is a convenience over SQL, not a replacement for understanding it, and performance problems live at the SQL level (Part 12 on indexes and query plans). They push invariants into the database as constraints (NOT NULL, CHECK, unique indexes, foreign keys) rather than relying only on application checks, because the database is the last line of defense and enforces the rule for every writer, including future code and manual fixes. They treat parameterization as non-negotiable and would flag any string-concatenated query in review instantly.

Common mistakes

  • Building SQL by concatenating user input (SQL injection).
  • Relying only on application validation and leaving the database able to hold invalid rows (no CHECK, no NOT NULL).
  • Using the ORM without ever understanding the SQL it generates, then being helpless when it is slow or wrong.

Interview questions

  1. What is SQL injection and how do you prevent it? Treating user input as part of the SQL text, letting an attacker run their own SQL; prevent it with parameterized queries ($1), never string concatenation.
  2. Why put constraints like NOT NULL and CHECK in the database instead of only in the application? The database enforces them for every writer and is the last line of defense; application checks can be bypassed or forgotten.
  3. What are the four basic SQL statements? INSERT (create), SELECT (read), UPDATE (change), DELETE (remove).

Practical exercise

In psql, create the products table with the constraints shown, insert two products (one via RETURNING), select them ordered by price, update one price, and try to insert a product with a negative price to see the CHECK constraint reject it. Acceptance criteria: the negative-price insert fails at the database level, proving the constraint protects you regardless of application code.

74.3.2 Connecting NestJS to PostgreSQL with a repository

Concept

Now we connect the API to the database so products persist. We use TypeORM, an ORM (Object-Relational Mapper) that lets you work with database rows as TypeScript objects. You define an entity (a class mapped to a table), and TypeORM gives you a repository with methods like find, findOne and save that generate the SQL for you. The service uses the repository instead of an in-memory array.

Why does it exist?

Writing raw SQL for every operation and manually mapping rows to objects is repetitive and error-prone. An ORM handles the common cases — insert this object, find by id, update these fields — generating correct, parameterized SQL and mapping rows to typed objects automatically. It lets you stay in TypeScript for straightforward data access while dropping to raw SQL for the complex queries where you need control (Part 15 covers TypeORM and Sequelize in depth, including when to use the query builder or raw SQL).

Mental model

The repository is a translator between your TypeScript world (objects) and the database world (rows and SQL). You hand it a product object and say "save this"; it writes the INSERT. You say "find the product with this id"; it writes the SELECT and hands you back a product object. You think in objects; it thinks in SQL; the entity is the dictionary that maps between the two.

How it works — install and configure

npm install @nestjs/typeorm typeorm pg

A critical warning on synchronize: true: it makes TypeORM automatically change your database schema to match your entities, which is convenient in development but dangerous in production, where it can drop columns and lose data. In production you use migrations (versioned, reviewed schema change scripts, Part 31) and set synchronize: false. Learn it now so you never ship synchronize: true.

The entity

// src/products/product.entity.ts
import { Entity, PrimaryGeneratedColumn, Column, CreateDateColumn } from 'typeorm';

@Entity('products')                            // maps to the "products" table
export class Product {
  @PrimaryGeneratedColumn('uuid')              // id uuid PRIMARY KEY DEFAULT gen_random_uuid()
  id!: string;

  @Column({ type: 'text' })
  name!: string;

  @Column({ type: 'integer', name: 'price_cents' })  // maps to the price_cents column
  priceCents!: number;

  @Column({ type: 'char', length: 3, default: 'USD' })
  currency!: string;

  @CreateDateColumn({ name: 'created_at', type: 'timestamptz' })
  createdAt!: Date;
}

The entity is the TypeScript mirror of the table. Each @Column maps a class property to a database column. Note name: 'price_cents' maps the camelCase TypeScript property to the snake_case database column — a common convention (Part 69 on mapping).

The repository in the service

// src/products/products.service.ts
import { Injectable, NotFoundException } from '@nestjs/common';
import { InjectRepository } from '@nestjs/typeorm';
import { Repository } from 'typeorm';
import { Product } from './product.entity';
import { CreateProductDto } from './dto/create-product.dto';

@Injectable()
export class ProductsService {
  constructor(
    @InjectRepository(Product) private readonly repo: Repository<Product>,
  ) {}

  async findAll(): Promise<Product[]> {
    // In a real API this is paginated (Part 71); kept simple here.
    return this.repo.find({ order: { createdAt: 'DESC' }, take: 100 });
  }

  async findOne(id: string): Promise<Product> {
    const product = await this.repo.findOne({ where: { id } });
    if (!product) throw new NotFoundException(`Product ${id} not found`);
    return product;
  }

  async create(dto: CreateProductDto): Promise<Product> {
    const product = this.repo.create({
      name: dto.name,
      priceCents: dto.priceCents,
      currency: dto.currency ?? 'USD',
    });
    return this.repo.save(product);   // generates the INSERT ... RETURNING
  }
}
// src/products/products.module.ts -- register the entity's repository
import { Module } from '@nestjs/common';
import { TypeOrmModule } from '@nestjs/typeorm';
import { Product } from './product.entity';
import { ProductsController } from './products.controller';
import { ProductsService } from './products.service';

@Module({
  imports: [TypeOrmModule.forFeature([Product])],  // makes the Product repository injectable
  controllers: [ProductsController],
  providers: [ProductsService],
})
export class ProductsModule {}

That is the whole vertical slice. The async code (Part 70), the typed objects (Part 69), the HTTP layer (Part 71), and now persistence are all connected. this.repo.save(product) generates a parameterized INSERT and returns the saved row with its generated id and timestamp; this.repo.findOne({ where: { id } }) generates a parameterized SELECT. The SQL is safe (parameterized) and typed (returns Product objects).

Edge cases & failure modes

  • synchronize: true in production can drop columns and destroy data on a schema change; use migrations (Part 31) and synchronize: false.
  • No database connection (wrong config, database down) makes the app fail to start or every request error; validate config and handle connection errors (Part 13).
  • Connection pool exhaustion under load if too many queries run at once (Part 13); the pool has a limit and requests queue beyond it.
  • N+1 queries when loading related data naively (Part 15) — a classic ORM performance trap.
  • Returning the raw entity exposes every column; map to a response shape if any field is internal (Part 69).
  • Large findAll with no pagination can try to load millions of rows; always paginate list endpoints (Part 71).

How a Senior Backend Engineer thinks about this

A senior uses the ORM for the common cases and keeps a clear line to raw SQL for complex or performance-critical queries, never treating the ORM as a black box. They never ship synchronize: true; schema changes go through reviewed migrations so production data is safe. They paginate every list, watch for N+1 query patterns, and are mindful of the connection pool under load. They push invariants into the database as constraints even when the ORM also validates, because the database is the last line of defense. And they keep the layering clean — controller to service to repository — so each layer is testable and the data access is isolated in one place.

Common mistakes

  • Shipping synchronize: true to production and losing data on a schema change.
  • Treating the ORM as magic and never understanding the SQL it runs.
  • Unpaginated list endpoints that try to load huge tables.
  • N+1 queries from naive related-data loading.
  • Returning raw entities and leaking internal columns.

Interview questions

  1. What is an ORM and what does a repository give you? An Object-Relational Mapper maps database rows to typed objects; the repository provides methods (find, findOne, save) that generate parameterized SQL so you work in objects for common cases.
  2. Why is synchronize: true dangerous in production? It auto-alters the schema to match entities and can drop columns and lose data; production schema changes must go through reviewed migrations.
  3. How does using an ORM help prevent SQL injection? It generates parameterized queries, sending values separately from the SQL text, so input cannot be executed as code.
  4. Why should list endpoints be paginated even with an ORM? An unpaginated query can try to load an entire large table into memory, exhausting resources; pagination bounds the result.
  5. What is the N+1 query problem? Loading a list and then issuing a separate query per item for related data, turning one logical read into many queries; it is a common ORM performance trap.

Part 74 — Key Takeaways

  • A backend is a loop: receive a request, validate it, run logic (kept separate from HTTP), persist to a store with real guarantees, return a response with the right status code.
  • NestJS organizes this into thin controllers (HTTP), services (logic), and repositories (data); keeping them separate makes everything testable and uniform.
  • Validate every incoming request with a DTO and a global ValidationPipe; whitelist and forbidNonWhitelisted block injected fields for free.
  • Understand the SQL even when an ORM writes it; parameterize always (never concatenate user input), and push invariants into the database as constraints.
  • Connect NestJS to PostgreSQL with a TypeORM entity and repository; you work in typed objects while the ORM generates safe, parameterized SQL.
  • Never ship synchronize: true; production schema changes go through reviewed migrations (Part 31).
  • Persistence is what makes it a backend: data lives in the database, surviving restarts and shared across every server instance.
  • Production systems are this same shape, hardened and scaled; add complexity (caching, queues, services) only when real pressure demands it.
  • The discipline practiced here — thin controllers, validated input, clean layering, safe SQL and schema, secrets out of git — is the same discipline that keeps large systems maintainable.
