## 20.4 Choosing data types in PostgreSQL

A column's type is the cheapest constraint you will ever add and the most expensive one to change later. Changing `integer` to `bigint` on a 500-million-row table rewrites the table and every index that includes the column, under an exclusive lock, for hours. Choosing right the first time is a senior skill. This section covers each decision the reference schema had to make.

### 20.4.1 Primary key type: uuid vs bigint identity

#### Concept

A surrogate key is an identifier with no business meaning, generated by the system. The two mainstream choices in PostgreSQL are a 64-bit sequential integer (`bigint GENERATED ALWAYS AS IDENTITY`) and a 128-bit UUID (`uuid`). They differ in size, generation location, index behavior and what they leak.

#### Why does it exist?

Sequential integers are compact and fast to index, but they must be generated by the database, so the application cannot know the id before the insert, they reveal how many rows exist (`/orders/10432` tells competitors your volume), and they are guessable (`/orders/10433`). UUIDs can be generated by any service without coordination, are unguessable, and are safe to expose. The cost is 16 bytes instead of 8 and, for random UUIDs, a badly behaved index.

#### Mental model

Imagine a library that shelves books in the order they arrive. A new book always goes at the end of the last shelf: fast, no reshuffling. That is a sequential key in a B-tree. Now imagine the shelving rule is "shelve by a random number stamped on the spine". Every new book goes to a random place in the building; the shelf there is full, so half its books move to a new shelf. Every insert touches a random page, and the whole building must stay in memory to be fast. That is a random UUID (v4) in a B-tree.

#### How it works

A B-tree index stores keys in sorted order across 8 KB pages. When you insert:

1. With sequential keys, every new key is larger than all existing keys. It goes to the rightmost leaf page. That page is hot in cache. Page splits happen only at the right edge and PostgreSQL optimizes this case (it fills the split pages asymmetrically so the right page has room).
2. With random keys, the new key belongs on a random leaf page. If that page is not in `shared_buffers`, it is read from disk. If it is full, it splits 50/50, and both halves are now half-empty. Over time the index runs at roughly 50 to 70 percent fill instead of 90 percent, so it is bigger, and the working set is the entire index rather than its right edge.
3. WAL volume increases because every insert dirties a random page plus its full-page image after each checkpoint.

Concrete numbers from a typical benchmark on a 100-million-row table: a `bigint` primary key index is about 2.1 GB; a random `uuid` index is about 3 GB before bloat and closer to 4.5 GB after sustained inserts; insert throughput with random UUIDs drops 20 to 40 percent once the index exceeds RAM. A sorted UUID removes almost all of that penalty.

UUIDv7 (RFC 9562, 2024) solves the problem: the first 48 bits are a millisecond Unix timestamp, the rest is random. Keys generated in the same instant are still unique and unguessable, but they sort by creation time, so inserts land on the right edge of the index. PostgreSQL 18 includes `uuidv7()` natively; on earlier versions you generate it in the application (`uuid` npm package v10+ has `v7()`) or with a small SQL function.

```sql
-- UUIDv7 generator for PostgreSQL 13 to 17 (PG18 has uuidv7() built in)
CREATE OR REPLACE FUNCTION uuid_generate_v7() RETURNS uuid AS $$
SELECT encode(
  set_bit(set_bit(
    overlay(uuid_send(gen_random_uuid())
            placing substring(int8send((extract(epoch from clock_timestamp()) * 1000)::bigint) from 3)
            from 1 for 6),
    52, 1), 53, 1),
  'hex')::uuid;
$$ LANGUAGE sql VOLATILE;
```

#### Practical example

In the reference schema, `orders.id` is a UUID because the order id appears in URLs, emails, webhooks from the payment provider, and support tickets. `orders.order_number` is a separate `bigint` identity because customer support and finance want a short, human-readable number. `order_items.id` is `bigint` because nobody outside the database ever sees it and there will be five to ten times more of them than orders.

#### PostgreSQL example

```sql
-- Both patterns, side by side
CREATE TABLE orders_v1 (id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY, placed_at timestamptz NOT NULL DEFAULT now());
CREATE TABLE orders_v2 (id uuid PRIMARY KEY DEFAULT gen_random_uuid(),           placed_at timestamptz NOT NULL DEFAULT now());
CREATE TABLE orders_v3 (id uuid PRIMARY KEY DEFAULT uuid_generate_v7(),           placed_at timestamptz NOT NULL DEFAULT now());

-- Measure index size after 10 million inserts
INSERT INTO orders_v1 (placed_at) SELECT now() FROM generate_series(1, 10000000);
INSERT INTO orders_v2 (placed_at) SELECT now() FROM generate_series(1, 10000000);
INSERT INTO orders_v3 (placed_at) SELECT now() FROM generate_series(1, 10000000);

SELECT relname, pg_size_pretty(pg_relation_size(oid))
FROM pg_class WHERE relname LIKE 'orders_v%_pkey';
-- orders_v1_pkey  214 MB   (bigint, sequential)
-- orders_v2_pkey  428 MB   (uuid v4, random; bloated after splits)
-- orders_v3_pkey  301 MB   (uuid v7, near-sequential)
```

#### TypeORM example

```ts
import { Entity, PrimaryGeneratedColumn, PrimaryColumn, Column } from 'typeorm';
import { v7 as uuidv7 } from 'uuid';

@Entity({ name: 'orders' })
export class Order {
  // Let PostgreSQL generate: DEFAULT gen_random_uuid()
  @PrimaryGeneratedColumn('uuid')
  id!: string;

  // Human-friendly sequence, generated by DB, never written by the app
  @Column({ type: 'bigint', generated: 'identity', insert: false, update: false })
  orderNumber!: string; // bigint arrives as string in node-postgres
}

@Entity({ name: 'payments' })
export class Payment {
  // Generate UUIDv7 in the application so the id is known before insert
  @PrimaryColumn('uuid')
  id: string = uuidv7();
}
```

Note the `bigint` as `string` detail: node-postgres returns `bigint` as a string because JavaScript numbers lose precision above 2^53. TypeORM follows that. Do not declare `bigint` columns as `number` in TypeScript unless you configure a parser and accept the risk.

#### Sequelize example

```ts
import { DataTypes, Model, Sequelize } from 'sequelize';

export class Order extends Model {
  declare id: string;
  declare orderNumber: string;
}

Order.init(
  {
    id: { type: DataTypes.UUID, primaryKey: true, defaultValue: DataTypes.UUIDV4 },
    // For UUIDv7, use defaultValue: () => uuidv7() instead of DataTypes.UUIDV4
    orderNumber: { type: DataTypes.BIGINT, autoIncrement: true, unique: true, field: 'order_number' },
  },
  { sequelize, tableName: 'orders', underscored: true },
);
```

#### Production scenario

A marketplace at 50 million orders with random UUIDv4 keys on `orders`, `order_items` and `payments` had 14 GB of primary-key indexes on 9 GB of table data. `shared_buffers` was 8 GB. Insert p99 latency was 40 ms and rising. Migrating new rows to UUIDv7 (old rows stayed v4; both are valid `uuid`) brought the right-edge inserts back into cache, and p99 fell to 6 ms within a week as the hot region of the index shrank.

#### Failure scenario

"At 02:14 the on-call got paged: `integer out of range` on `INSERT INTO events`." The `events.id` column was `serial` (32-bit). It reached 2,147,483,647 after four years. Every insert failed; the ingestion pipeline backed up; the fix (`ALTER COLUMN id TYPE bigint`) rewrote a 900 GB table and took eleven hours with the table locked. The senior lesson: never use `serial` or `integer` for a primary key. `bigint` costs 4 extra bytes per row and removes the question forever.

#### Edge cases & failure modes

- Integer overflow at 2^31 with `serial`/`integer` PKs. Use `bigint`.
- Sequences are not transactional: a rolled-back insert consumes the number. Gaps in `order_number` are normal, and any process that assumes no gaps is wrong.
- Random UUID as a clustered ordering: `ORDER BY id` is meaningless for v4 and only "roughly by time" for v7. Always order by a timestamp column with a tiebreaker.
- UUIDs as strings: storing a UUID in `text` or `varchar(36)` costs 37 bytes instead of 16, compares byte-by-byte instead of as two 64-bit integers, and allows invalid values. Always use the `uuid` type.
- Passing a UUID parameter typed as text (`WHERE id = $1` with `$1::text`) can defeat the index. Part 21 covers implicit casts.
- Exposing sequential ids in public URLs leaks volume and enables enumeration attacks. If you must, add a separate public slug.

#### How a Senior Backend Engineer thinks about this

The decision table they use:

| Situation | Choice | Why |
|---|---|---|
| Id exposed in URLs / to third parties | `uuid` (v7 if possible) | unguessable, no volume leak, client can pre-generate |
| Id generated by multiple services or offline clients | `uuid` | no central coordination |
| Internal, high-volume child table (items, events, logs) | `bigint` identity | 8 bytes, dense index, fast joins |
| Human-readable reference needed | `bigint` identity as a second unique column | keep uuid as PK |
| Existing `integer` PK approaching 1.5 billion | migrate to `bigint` now, not at 2.1 billion | rewriting is the only fix |

They also refuse `serial` (legacy, creates an implicit sequence with odd ownership semantics) in favor of `GENERATED ALWAYS AS IDENTITY`, which is SQL-standard and prevents accidental explicit ids.

#### Common mistakes

- `varchar(36)` for UUIDs.
- `integer` PKs "because we'll never have 2 billion rows". Events tables do.
- Random UUIDv4 on a 10-billion-row time-series table, then wondering why the index is larger than the data.
- Using the UUID for ordering.

#### Interview questions

1. Why do random UUIDs hurt B-tree insert performance? Expected: every insert lands on a random leaf page; cache misses, 50/50 splits, index bloat, WAL growth. Follow-up: how does UUIDv7 fix this?
2. When would you still pick a `bigint` identity? Expected: internal high-volume tables where compactness and join speed matter.
3. What happens when a `serial` column overflows, and how long does the fix take?
4. Why does node-postgres return `bigint` as a string?

#### Practical exercise

Create the three `orders_v*` tables above, insert 5 million rows each, and compare index size, insert time, and `EXPLAIN (ANALYZE, BUFFERS)` for a point lookup. Acceptance criteria: a table of measurements and a one-paragraph recommendation for your team.

### 20.4.2 Money: numeric vs float

#### Concept

`numeric(precision, scale)` stores exact decimal numbers. `real` and `double precision` (float) store binary approximations. Money must be exact. `numeric(12,2)` holds up to 10 digits before the decimal point and exactly 2 after, which covers 9,999,999,999.99, enough for order totals in any currency with two minor units.

#### Why does it exist?

Binary floating point cannot represent 0.1 exactly. `0.1 + 0.2` is `0.30000000000000004`. Multiply that by a million transactions and your ledger does not balance. Auditors do not accept "floating point" as an explanation.

#### How it works

`numeric` is stored as a variable-length array of base-10,000 digits with a sign and a scale. Arithmetic is done in software, so it is roughly 3 to 10 times slower than float arithmetic, which is irrelevant for order totals and highly relevant for scientific computation. Comparison and indexing work normally. Division produces as many digits as needed up to an internal limit, so always round explicitly when storing results of division.

#### PostgreSQL example

```sql
SELECT 0.1::float8 + 0.2::float8;          -- 0.30000000000000004
SELECT 0.1::numeric + 0.2::numeric;        -- 0.3

-- Tax computation: round explicitly, at the boundary you control
SELECT round(1999.99 * 0.18, 2) AS gst;    -- 360.00 (exactly 359.9982 rounded)

-- Sum of a million 0.1 values
SELECT sum(0.1::float8) FROM generate_series(1, 1000000);   -- 100000.00000133288
SELECT sum(0.1::numeric) FROM generate_series(1, 1000000);  -- 100000.0
```

#### TypeORM example

TypeORM returns `numeric` as a string, to preserve exactness. Convert with a decimal library, never `parseFloat`.

```ts
import { Column, Entity } from 'typeorm';
import Big from 'big.js';

@Entity({ name: 'order_items' })
export class OrderItem {
  @Column({ type: 'numeric', precision: 12, scale: 2 })
  unitPrice!: string; // "1999.99" - keep as string until arithmetic is needed

  lineTotal(quantity: number): string {
    return new Big(this.unitPrice).times(quantity).toFixed(2);
  }
}
```

An alternative many payment teams prefer: store minor units as `bigint` (`amount_paise bigint`). Integer arithmetic in JavaScript is exact up to 2^53, no library needed, and the type makes "this is not a float" impossible to get wrong. The reference schema uses `numeric(12,2)` because it reads naturally in reports; either is correct, mixing them is not.

#### Sequelize example

```ts
unitPrice: { type: DataTypes.DECIMAL(12, 2), allowNull: false, field: 'unit_price',
  get() { return this.getDataValue('unitPrice'); } }, // returns string; do not parseFloat
```

#### Edge cases & failure modes

- `parseFloat("1999.99") * 3` in JavaScript gives `5999.969999999999`. The string from the driver is exact until someone parses it.
- Currency with three minor units (KWD, BHD) or zero (JPY): `numeric(12,2)` is wrong there. If you go multi-currency, store `numeric(14,4)` or minor units plus a currency code.
- Rounding rules: banker's rounding vs half-up differ in the last cent. Decide once, implement in the database with `round()`, and test it.
- `money` type in PostgreSQL: locale-dependent formatting, fixed two decimals, painful to cast. Avoid.

#### Interview questions

1. Why not store prices as `double precision`? Expected: 0.1 is not representable; sums drift; audits fail.
2. `numeric(12,2)` or `bigint` minor units? Expected: both exact; minor units avoid driver string handling; numeric reads naturally. Pick one.

### 20.4.3 Time: timestamptz vs timestamp

#### Concept

`timestamptz` ("timestamp with time zone") stores an absolute instant in UTC and converts to the session's time zone on output. `timestamp` ("without time zone") stores a wall-clock reading with no idea which zone it was read in. Despite the name, `timestamptz` does not store a time zone; it stores a point on the global timeline, which is exactly what you want for "when did this happen".

#### Why does it exist?

An order placed at "14:30" is meaningless without a zone. Was that Mumbai or Frankfurt? With `timestamp`, the answer depends on the server's `TimeZone` setting at insert time, which changes when you move to a new cloud region or a developer runs the migration from a laptop. With `timestamptz` the instant is unambiguous forever.

#### How it works

Both types are 8 bytes (microseconds since 2000-01-01). The difference is purely in conversion: `timestamptz` input is interpreted in the session `TimeZone` (or the explicit offset in the literal) and stored as UTC; output is converted back. `timestamp` input and output are stored and shown verbatim.

```sql
SET TimeZone = 'Asia/Kolkata';
SELECT '2026-03-01 14:30'::timestamptz;           -- 2026-03-01 14:30:00+05:30
SELECT '2026-03-01 14:30'::timestamptz AT TIME ZONE 'UTC';  -- 2026-03-01 09:00:00 (timestamp)
SELECT '2026-03-01 14:30+00'::timestamptz;        -- 2026-03-01 20:00:00+05:30

-- Comparing timestamptz with a date literal: the literal is interpreted in session zone
SELECT count(*) FROM orders WHERE placed_at >= '2026-03-01';   -- midnight in session TZ
```

#### Production scenario

Node's `Date` is an absolute instant, so it maps cleanly to `timestamptz`. Set the session zone to UTC from the application (`options: '-c TimeZone=UTC'` in the connection string, or `SET TIME ZONE 'UTC'` on connect) so every `DATE`-literal comparison and `date_trunc` in raw SQL behaves the same in every environment. Do reporting in the customer's zone explicitly: `date_trunc('day', placed_at AT TIME ZONE 'Asia/Kolkata')`.

#### Failure scenario

A daily revenue report for "yesterday" showed a 4-hour hole every day. The report used `placed_at::date = current_date - 1` on a `timestamp` column. Production had migrated from a server in `Europe/Berlin` to one in `UTC`; old rows were stored as Berlin wall-clock, new rows as UTC wall-clock, and no row carried enough information to tell which. It took a week of forensics using payment-provider timestamps to rebuild. The fix was `timestamptz` and a UTC session zone, but the old data could only be corrected approximately.

#### Edge cases & failure modes

- Daylight saving: `timestamp + interval '1 day'` across a DST boundary in `timestamptz` context yields the same wall-clock time next day (23 or 25 hours later). If you need exactly 24 hours, add `interval '24 hours'`.
- `now()` is the transaction start time, constant within a transaction. `clock_timestamp()` is the real current time. Long transactions inserting `now()` rows all carry the same timestamp.
- Index on `date(placed_at)` vs `placed_at::date`: the cast of `timestamptz` to `date` depends on the session zone, so it is not immutable and cannot be indexed directly. Index `(placed_at AT TIME ZONE 'UTC')::date` or a range predicate instead.
- Storing "date of birth" or "delivery slot 9 to 11 AM local" is wall-clock data, and `date` or `timestamp` plus a zone column is correct there. `timestamptz` is for instants.

#### Interview questions

1. Does `timestamptz` store the time zone? Expected: no, it stores UTC instants and converts on I/O.
2. Why set the session time zone to UTC from the application?
3. What is the difference between `now()` and `clock_timestamp()`?

### 20.4.4 Text: text vs varchar(n) vs char(n)

#### Concept

In PostgreSQL, `text`, `varchar`, and `varchar(n)` share one storage format and one performance profile. `varchar(n)` only adds a length check. `char(n)` pads with spaces to exactly n characters and is almost never what you want.

#### Why does it exist?

`varchar(n)` exists for SQL-standard compatibility and for one legitimate purpose: a hard length limit that should be enforced at the database (a two-letter country code, a 3-letter currency code). For everything else, `text` is idiomatic PostgreSQL.

#### How it works

Values up to about 2 KB live inline in the row. Larger values are compressed and, if still large, moved out of line into a TOAST table (The Oversized-Attribute Storage Technique), transparently. A `text` column can hold up to 1 GB. `varchar(255)` is not faster than `text`; it is a MySQL habit.

```sql
-- Length rule as a CHECK: change it without a type rewrite
ALTER TABLE users ADD CONSTRAINT users_full_name_len CHECK (length(full_name) BETWEEN 1 AND 200);

-- Changing varchar(50) to varchar(100) on PG is a metadata-only change (fast), but
-- changing varchar(100) to varchar(50) rescans the table to validate. A CHECK can be added NOT VALID and validated later.
```

#### Edge cases & failure modes

- `char(2)` with a one-character value stores `'A '` and comparisons ignore trailing spaces, which surprises string functions and JSON output. The reference schema uses `char(2)` and `char(3)` for ISO codes only because they are always exactly that length.
- Collation: sorting and `LIKE` depend on the database collation. `en_US.UTF-8` sorts case-insensitively-ish but compares with case; `C` collation is byte-order and enables `LIKE 'abc%'` to use a plain B-tree index. If you need `LIKE` prefix search on a non-C collation, create the index with `text_pattern_ops`.
- Case-insensitive uniqueness: index `lower(email)` (as the reference schema does) or use the `citext` extension.

#### Interview questions

1. Is `varchar(255)` faster than `text` in PostgreSQL? Expected: no; identical storage; the limit is a check.
2. When is `varchar(n)` justified? Expected: hard domain limits like ISO codes.

### 20.4.5 jsonb: when it is right and when it is a smell

#### Concept

`jsonb` stores JSON in a decomposed binary format that can be indexed and queried with operators (`->`, `->>`, `@>`, `?`, `jsonb_path_query`). `json` (without b) stores the raw text and is only useful for preserving exact formatting. Use `jsonb`.

#### Why does it exist?

Some data is genuinely schema-less or varies per row: product attributes (a phone has `ram_gb`, a shoe has `size_eu`), a webhook payload from a third party, a notification template's variables. Forcing that into columns means either hundreds of nullable columns or an entity-attribute-value table that is painful to query. `jsonb` gives you a document inside a relational row, with the row still carrying the relational guarantees.

#### Mental model

Imagine a well-organized filing cabinet (the table) where each folder (row) has labeled tabs (columns) and one pocket in the back where you can drop any loose notes (jsonb). The pocket is useful. A cabinet that is all pockets and no tabs is a pile of paper.

#### How it works

1. On write, the JSON text is parsed, keys are deduplicated (last wins), and the object is stored as a binary tree. Key order is not preserved. Whitespace is dropped.
2. Operators: `->` returns `jsonb`, `->>` returns `text`. `@>` is containment ("does this document contain this sub-document"). `?` tests key existence.
3. A GIN index on the column makes `@>`, `?`, `?|`, `?&` and `jsonb_path_ops` queries fast (tens of milliseconds on millions of rows). A B-tree index on an expression `(attributes->>'brand')` makes equality and range queries on that one key fast.
4. Updating one key rewrites the whole value (PostgreSQL rows are immutable versions; MVCC). A 50 KB jsonb document updated 100 times per day generates 5 MB of dead tuples per day for that one row.

#### PostgreSQL example

```sql
-- Products with attributes: legitimate jsonb use
INSERT INTO products (sku, name, category_id, price, attributes)
VALUES ('PHN-001', 'Phone X', 3, 49999.00,
        '{"brand": "Acme", "ram_gb": 8, "colors": ["black", "blue"]}');

-- Containment query: uses products_attributes_gin
SELECT id, name FROM products WHERE attributes @> '{"brand": "Acme"}';

-- Key extraction with a targeted expression index
CREATE INDEX products_attr_brand_idx ON products ((attributes->>'brand'));
SELECT id FROM products WHERE attributes->>'brand' = 'Acme';

-- Range on a numeric key: cast in the index expression
CREATE INDEX products_attr_ram_idx ON products (((attributes->>'ram_gb')::int));
SELECT id FROM products WHERE (attributes->>'ram_gb')::int >= 8;

-- Guard against garbage: CHECK on shape
ALTER TABLE products ADD CONSTRAINT products_attributes_is_object
  CHECK (jsonb_typeof(attributes) = 'object');
```

#### When jsonb is a schema-avoidance smell

The red flags a senior looks for:

- You `JOIN` on a value inside jsonb (`ON o.meta->>'user_id' = u.id::text`). That is a foreign key hiding in a document, with no referential integrity and a text comparison instead of a uuid comparison.
- You need a `NOT NULL` or `UNIQUE` on a key inside the document.
- Every row has the same keys. That is a table with extra steps.
- The document is updated frequently in small pieces (counters, statuses). Each update rewrites the whole document.
- Reports group by a jsonb key. It works, but it is slower than a column and the planner has poor statistics for it.

The decision table:

| Data | Column(s) | jsonb |
|---|---|---|
| Queried by equality/range often, filtered in WHERE, joined | yes | no |
| Sparse, per-row-varying attributes | no | yes |
| Third-party payload kept for audit | no | yes |
| Needs UNIQUE / FK / NOT NULL | yes | no |
| Updated in small pieces frequently | yes | no |
| Read as a whole, written as a whole | either | yes |

#### TypeORM example

```ts
@Column({ type: 'jsonb', default: () => "'{}'::jsonb" })
attributes!: Record<string, unknown>;

// Query with containment (raw operator; TypeORM has no typed jsonb operators)
const acme = await productRepo
  .createQueryBuilder('p')
  .where('p.attributes @> :filter', { filter: JSON.stringify({ brand: 'Acme' }) })
  .getMany();
```

#### Sequelize example

```ts
attributes: { type: DataTypes.JSONB, allowNull: false, defaultValue: {} },

// Sequelize supports nested key queries on JSONB for PostgreSQL:
const acme = await Product.findAll({ where: { 'attributes.brand': 'Acme' } });
// Generates: WHERE ("attributes"#>>'{brand}') = 'Acme'  (expression index needs to match this form)
```

#### Failure scenario

A notification service stored delivery attempts inside `notifications.payload` as an array that grew on every retry. Retries ran every minute for failed rows. After a month, some documents were 2 MB, each update rewrote 2 MB, the table had 60 GB of dead tuples, autovacuum could not keep up, and `SELECT ... WHERE status = 'pending'` slowed from 2 ms to 900 ms because the partial index pointed at bloated heap pages. The fix was a separate `notification_attempts` table with one narrow row per attempt. jsonb was not the problem; unbounded growth of a value that is rewritten on each change was.

#### Edge cases & failure modes

- `NULL` vs JSON null vs missing key are three different states. `->>` returns SQL `NULL` for the last two.
- Numbers in JSON are arbitrary precision in `jsonb`, but `->>` returns text; cast explicitly and expect cast errors on bad data.
- GIN index maintenance is expensive on write-heavy tables (`fastupdate` pending list helps; tune `gin_pending_list_limit`).
- `jsonb` columns bigger than 2 KB go to TOAST; reading any key decompresses the whole document.
- Duplicate keys are silently collapsed on insert.

#### Interview questions

1. When is `jsonb` the right choice? Expected: sparse, per-row-varying, read-whole/write-whole data; not for keys you join, constrain, or update in pieces.
2. What index do you add for `attributes @> '{"brand":"Acme"}'`, and for `attributes->>'brand' = 'Acme'`? Expected: GIN on the column; B-tree on the expression.
3. Why is updating one key in a large jsonb document expensive? Expected: MVCC rewrites the whole row version.

### 20.4.6 Arrays

#### Concept

PostgreSQL columns can be arrays of any type (`text[]`, `int[]`, `uuid[]`). They are indexable with GIN and support operators like `@>` (contains), `&&` (overlaps), and `= ANY(...)`.

#### Why does it exist?

Small, unordered sets of scalar values that belong to a row, are queried by membership, and never need their own attributes or foreign keys: product tags, allowed roles, a list of applied coupon codes. Modeling those as a join table is correct in pure normalization terms and often over-engineering.

#### PostgreSQL example

```sql
-- Tags on products: text[] with a GIN index (already in the reference schema)
SELECT id, name FROM products WHERE tags @> ARRAY['sale'];        -- contains 'sale'
SELECT id, name FROM products WHERE tags && ARRAY['sale', 'new']; -- overlaps either

-- Passing a list parameter: ANY beats IN for prepared statements (one parameter, any length)
SELECT id, name FROM products WHERE id = ANY($1::uuid[]);

-- Unnest to rows when you need to aggregate per tag
SELECT tag, count(*) FROM products, unnest(tags) AS tag GROUP BY tag ORDER BY 2 DESC;
```

#### When not to use arrays

If the elements need attributes (when was the tag added, by whom), a foreign key (tags must exist in a `tags` table), or you need to find "all products with tag X" in a way that must stay fast at 100 million rows with heavy writes, use a join table. Arrays of foreign keys (`category_ids bigint[]`) have no referential integrity and are the most common array misuse.

#### Interview questions

1. `tags text[]` or a `product_tags` join table? Expected: array when tags are simple labels queried by membership; table when they need attributes, FK integrity, or high-cardinality reverse lookups.

### 20.4.7 Enums vs lookup tables vs CHECK constraints

#### Concept

Three ways to restrict a column to a fixed set of values:

1. `CREATE TYPE ... AS ENUM` — a real type with an ordered, named set of labels stored as 4-byte OIDs.
2. `text` with `CHECK (status IN (...))` — plain text, validated by a constraint.
3. A lookup table with a foreign key — values are rows, can have attributes, can be added by an INSERT.

#### How it works and the tradeoffs

| Property | ENUM | text + CHECK | Lookup table + FK |
|---|---|---|---|
| Storage | 4 bytes | length of text (`'pending'` = 8 bytes) | 4 or 8 bytes FK |
| Add a value | `ALTER TYPE ... ADD VALUE` (cannot run inside a transaction block before PG12; new value not usable in same transaction) | `ALTER TABLE ... DROP CONSTRAINT` then `ADD CONSTRAINT` (validates whole table unless `NOT VALID`) | `INSERT INTO statuses` |
| Remove/rename a value | Rename yes; remove: not supported (recreate type) | Replace constraint | `DELETE` (if no FK references) |
| Ordering | By declaration order (`ORDER BY status` follows enum order) | Alphabetical | By a sort column you add |
| Extra attributes (label, description, is_terminal) | no | no | yes |
| ORM friendliness | TypeORM `enum` type works; migrations awkward | trivial | join or cache needed |
| Readability in `psql` | good | good | needs join |

The reference schema uses `text + CHECK` for `orders.status`, `payments.status`, `shipments.status` because order statuses change as the business evolves (a "returned" state gets added, "refunded" gets split into partial and full) and constraint replacement is a fast, transactional, rollback-able migration. It uses a real `ENUM` for `notification_channel` because the set (`email`, `sms`, `push`) is tiny, stable, and used in a high-volume table where 4 bytes versus 5 to 8 bytes per row matters slightly.

#### PostgreSQL example

```sql
-- Evolving a CHECK-constrained status safely, without a full-table scan blocking writers
ALTER TABLE orders DROP CONSTRAINT orders_status_check;
ALTER TABLE orders ADD CONSTRAINT orders_status_check
  CHECK (status IN ('pending','paid','shipped','delivered','cancelled','refunded','returned')) NOT VALID;
-- Existing rows are trusted; new writes are validated. Validate later, with only a SHARE UPDATE EXCLUSIVE lock:
ALTER TABLE orders VALIDATE CONSTRAINT orders_status_check;

-- Evolving an ENUM
ALTER TYPE notification_channel ADD VALUE IF NOT EXISTS 'whatsapp';
-- PG12+: allowed inside a transaction, but the new value cannot be used until that transaction commits.
-- Removing 'sms' later: no ALTER TYPE DROP VALUE. You must create a new type, cast the column, drop the old type.
```

#### TypeORM example

```ts
export enum OrderStatus { Pending = 'pending', Paid = 'paid', Shipped = 'shipped',
  Delivered = 'delivered', Cancelled = 'cancelled', Refunded = 'refunded' }

@Column({ type: 'text' })                 // DB enforces via CHECK; TS enum for the app
status!: OrderStatus;

// If you use a real PG enum:
@Column({ type: 'enum', enum: NotificationChannel, enumName: 'notification_channel' })
channel!: NotificationChannel;
```

#### Failure scenario

A team ran `ALTER TYPE order_status ADD VALUE 'returned'` inside their migration framework, which wraps each migration in a transaction. On PostgreSQL 11 it failed outright ("ALTER TYPE ... ADD VALUE cannot run inside a transaction block"). After upgrading to PG12 it succeeded, but the same migration then ran `UPDATE orders SET status = 'returned' WHERE ...` and failed with "unsafe use of new value". The migration had to be split into two deploys. With `text + CHECK` this would have been one transactional migration.

#### Interview questions

1. Enum or CHECK for an order status? Expected: CHECK for evolving sets (transactional changes, removals); enum for tiny stable sets in huge tables.
2. What is the operational cost of removing an enum value? Expected: not supported directly; recreate the type and rewrite the column.
3. Why add a CHECK constraint as `NOT VALID` first? Expected: avoids a full-table validation scan under a heavy lock; validate later with a weaker lock.

#### Practical exercise

Take the `orders.status` column and implement it three ways in three copies of the table. For each, write the migration that adds a `returned` state and the migration that removes `refunded`. Time each on a 10-million-row table and note which locks are taken (`SELECT * FROM pg_locks` from a second session). Acceptance criteria: a decision matrix with your own measured numbers.
